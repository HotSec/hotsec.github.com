# 分布式系统

## CAP 定理

分布式系统无法同时满足以下三个特性，最多同时满足两个：

- **Consistency（一致性）**：所有节点在同一时刻看到相同的数据
- **Availability（可用性）**：每个请求都能在合理时间内得到非错误响应
- **Partition Tolerance（分区容错）**：网络分区时系统仍能继续运行

实际选择：网络分区不可避免，因此通常在 CP 和 AP 之间权衡。

| 模式 | 场景 | 典型系统 |
|------|------|----------|
| CP | 金融交易、配置中心 | ZooKeeper、etcd、HBase |
| AP | 社交、购物车、内容 | Cassandra、DynamoDB、Eureka |
| CA | 单机数据库（无分区） | MySQL 单机 |

## BASE 理论

CAP 的实践补充，面向大型分布式系统：

- **Basically Available（基本可用）**：允许响应时间增加或功能降级
- **Soft State（软状态）**：允许中间状态，数据副本允许暂时不同
- **Eventually Consistent（最终一致性）**：经过一段时间后，所有副本最终一致

## 一致性模型

### 强一致性

- 线性一致性（Linearizability）：操作看起来在某个时间点原子生效
- 顺序一致性（Sequential Consistency）：所有进程看到相同的操作顺序

### 弱一致性

- 因果一致性：有因果关系的操作顺序一致
- 最终一致性：一段时间后数据一致
- 读己之写：写入后自己立即可读
- 单调读：不会读到更旧的数据
- 单调写：写操作顺序一致

## 分布式共识算法

### Raft

- **角色**：Leader / Follower / Candidate
- **Leader 选举**：心跳超时 → Candidate → 获得多数投票 → Leader
- **日志复制**：Leader 接收请求 → 追加日志 → 复制到 Follower → 多数确认 → 提交
- **安全性**：Leader 完整性、日志匹配、选举限制
- 应用：etcd、Consul、TiKV

### Paxos

- Basic Paxos：Proposer / Acceptor / Learner，两阶段提交
- Multi-Paxos：优化版，省略 Prepare 阶段
- 应用：Google Chubby、Spanner

### ZAB（ZooKeeper Atomic Broadcast）

- 崩溃恢复模式 + 消息广播模式
- 应用：ZooKeeper

## 分布式事务

### 2PC（两阶段提交）

```
协调者 → 参与者1: Prepare → OK
协调者 → 参与者2: Prepare → OK
协调者 → 所有参与者: Commit
```

- 优点：强一致性
- 缺点：同步阻塞、单点故障（协调者）、数据不一致风险

### 3PC（三阶段提交）

- CanCommit → PreCommit → DoCommit
- 引入超时机制减少阻塞，但仍有数据不一致风险

### TCC（Try-Confirm-Cancel）

- **Try**：预留资源（冻结金额）
- **Confirm**：确认执行（扣款）
- **Cancel**：取消执行（解冻）
- 适用：业务层面保证一致性，对业务侵入性强

### Saga

- 长事务拆分为多个本地事务，每个事务有补偿操作
- 正向执行：T1 → T2 → T3 → ...
- 异常补偿：T3⁻¹ → T2⁻¹ → T1⁻¹
- 协调方式：编排式（Choreography）/ 协调式（Orchestration）
- 适用：跨服务长流程业务

## 分布式 ID

### Snowflake（雪花算法）

```
| 1 bit | 41 bit 时间戳 | 10 bit 机器ID | 12 bit 序列号 |
```

- 64 位整数，趋势递增，不依赖数据库
- 时钟回拨问题：等待 / 拒绝服务 / 使用历史最大时间戳

### 其他方案

| 方案 | 特点 |
|------|------|
| UUID | 无中心化，无序，索引性能差 |
| 数据库自增 | 简单，单点瓶颈 |
| 号段模式 | 预分配号段，减少 DB 压力（美团 Leaf） |
| Redis INCR | 高性能，依赖 Redis |
| ULID | 有序 + 随机，可排序 |

## 分布式锁

### Redis 实现

```python
import redis

r = redis.Redis()

def acquire_lock(key, value, expire=10):
    return r.set(key, value, nx=True, ex=expire)

def release_lock(key, value):
    script = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """
    r.eval(script, 1, key, value)
```

- 注意：超时续期（Watchdog）、Redlock 算法

### etcd 实现

- 基于 Lease + Revision 实现分布式锁
- 天然支持 TTL，更可靠

## 一致性哈希

- 将哈希值空间组织为虚拟环（0 ~ 2³²-1）
- 节点和数据都映射到环上
- 数据顺时针找到最近的节点
- **虚拟节点**：解决数据倾斜问题

## 分布式时钟

### Lamport 时间戳

- 逻辑时钟，保证因果顺序
- 每个事件递增计数器，消息传递时携带并取最大值

### 向量时钟

- 每个进程维护一个向量，记录所有进程的逻辑时间
- 可检测并发事件

### 混合逻辑时钟（HLC）

- 结合物理时钟和逻辑时钟
- 应用：CockroachDB、MongoDB

## Gossip 协议

- 最终一致性传播协议
- 每个节点随机选择其他节点传播信息
- 病毒式传播，收敛时间 O(log N)
- 应用：Cassandra、Consul、Redis Cluster
