# 系统架构设计

## 架构设计概念

### 架构定义

- 软件架构是系统的组织结构，包含软件构件、构件的外部可见属性及构件之间的关系
- 架构定义了系统的计算构件和构件之间的交互
- 架构是系统的高层抽象，关注整体结构而非局部细节
- 架构涉及的关键要素：构件、连接件、约束

### 架构与设计的区别

| 维度 | 架构 | 设计 |
|------|------|------|
| 关注点 | 全局结构、高层决策 | 局部细节、具体实现 |
| 抽象层次 | 系统级 | 模块/类级 |
| 影响范围 | 全系统，难以变更 | 局部，较易变更 |
| 决策内容 | 架构风格、构件划分、通信机制 | 算法选择、数据结构、接口细节 |
| 利益相关者 | 所有干系人 | 开发人员 |
| 变更代价 | 极高 | 较低 |

### 架构师角色与职责

- 架构师核心职责
    - 确定系统架构风格与总体结构
    - 进行架构决策与权衡
    - 定义构件接口与交互协议
    - 保障质量属性达成
    - 进行架构评估与演进
- 架构师能力模型
    - 技术能力：架构设计、技术选型、性能优化
    - 管理能力：项目规划、团队协调、风险管理
    - 沟通能力：需求沟通、方案汇报、跨团队协作
- 架构师在不同阶段的工作
    - 需求阶段：参与需求分析，识别质量属性需求
    - 设计阶段：制定架构方案，进行架构评审
    - 实现阶段：指导开发，确保架构落地
    - 维护阶段：架构演进，技术债务管理

## 架构风格

### 架构风格分类总览

| 大类 | 子风格 | 核心思想 |
|------|--------|----------|
| 数据流风格 | 管道-过滤器、批处理 | 数据在构件间流动驱动计算 |
| 调用/返回风格 | 主程序-子程序、面向对象、层次结构 | 显式调用机制协调计算 |
| 独立构件风格 | 进程通信、事件驱动 | 构件独立运行，间接交互 |
| 虚拟机风格 | 解释器、规则系统 | 通过虚拟机间接执行 |
| 仓库风格 | 数据库系统、黑板系统 | 以数据为中心组织计算 |

### 数据流风格

**管道-过滤器**

- 每个构件有一组输入和输出，构件读取输入数据流并产生输出数据流
- 构件之间通过管道连接，数据在管道中流动
- 特点
    - 松耦合：过滤器独立工作，互不依赖
    - 可组合：过滤器可自由组合
    - 可重用：单个过滤器可复用
    - 并发性：过滤器可并行执行
- 缺点
    - 不适合交互式应用
    - 数据转换开销大
    - 难以增量式显示结果

**批处理**

- 数据整体处理，步骤之间无交互
- 每一步处理完整数据集后再传递给下一步
- 特点
    - 适合大规模数据处理
    - 步骤间完全解耦
- 缺点
    - 延迟高，无实时性
    - 无法交互

### 调用/返回风格

**主程序-子程序**

- 单线程控制，主程序调用子程序执行
- 特点：结构清晰、易于理解
- 缺点：扩展困难、耦合度高

**面向对象**

- 通过对象封装数据和操作，通过方法调用交互
- 特点
    - 封装性、继承性、多态性
    - 符合人类思维
- 缺点
    - 对象间耦合（方法调用需知道对象标识）
    - 并发控制复杂
    - 继承带来的脆弱基类问题

**层次结构**

- 系统分层组织，每层为上层提供服务，使用下层服务
- 特点
    - 支持增量开发
    - 层次间可替换
- 缺点
    - 并非所有系统都适合分层
    - 层次间性能开销
    - 严格分层可能导致效率低下

### 独立构件风格

**进程通信**

- 构件通过消息传递进行交互
- 方式：同步消息、异步消息、RPC
- 特点：构件高度独立、可分布部署
- 缺点：通信开销、一致性管理复杂

**事件驱动（隐式调用）**

- 构件不直接调用，而是声明事件或订阅事件
- 事件触发时系统自动调用已注册的处理程序
- 特点
    - 构件高度解耦
    - 构件可动态增删
    - 支持复用
- 缺点
    - 构件放弃了对计算的控制
    - 数据交换困难
    - 难以测试和调试
    - 无法保证执行顺序

### 虚拟机风格

**解释器**

- 包含解释引擎、被解释程序、程序状态
- 解释引擎逐条读取并执行被解释程序的指令
- 特点：灵活性高、可定制
- 缺点：性能低、实现复杂

**规则系统**

- 基于规则的知识库 + 推理引擎
- 适合专家系统、决策支持系统
- 特点：业务规则与代码分离、易于修改规则
- 缺点：推理效率低、规则冲突处理复杂

### 仓库风格

**数据库系统**

- 以数据为中心，构件通过共享数据库交互
- 特点：数据集中管理、一致性保障
- 缺点：数据库成为瓶颈、耦合于数据模式

**黑板系统**

- 知识源 + 黑板数据 + 控制器
- 知识源独立，通过黑板共享数据
- 控制器决定哪个知识源在何时执行
- 适用场景：信号处理、模式识别、语音识别
- 特点：适合非确定性问题、知识源可增删
- 缺点：控制逻辑复杂、调试困难

### 各风格优缺点对比表

| 架构风格 | 优点 | 缺点 | 典型应用 |
|----------|------|------|----------|
| 管道-过滤器 | 松耦合、可组合、可重用、并发 | 不适合交互、转换开销大 | 编译器、数据处理 |
| 批处理 | 简单、步骤解耦 | 延迟高、无交互 | ETL、报表生成 |
| 主程序-子程序 | 结构清晰、易理解 | 扩展困难、耦合高 | 小型系统 |
| 面向对象 | 封装、继承、多态 | 对象耦合、并发复杂 | 通用业务系统 |
| 层次结构 | 增量开发、层可替换 | 非普适、性能开销 | 网络协议栈、OS |
| 进程通信 | 高度独立、可分布 | 通信开销、一致性难 | 分布式系统 |
| 事件驱动 | 解耦、动态扩展 | 控制丧失、难调试 | GUI、IoT |
| 解释器 | 灵活、可定制 | 性能低、实现复杂 | 脚本语言 |
| 规则系统 | 规则与代码分离 | 推理效率低、规则冲突 | 专家系统 |
| 数据库系统 | 数据集中、一致性好 | 瓶颈、模式耦合 | MIS、ERP |
| 黑板系统 | 适合非确定性问题 | 控制复杂、调试难 | AI、信号处理 |

## 特定领域架构DSSA

### DSSA基本概念

- DSSA（Domain Specific Software Architecture）是专用于特定领域的软件架构
- 目标：在特定领域内实现软件复用，降低开发成本，提高质量
- 特征
    - 领域性：针对特定问题域
    - 复用性：提供可复用的架构组件
    - 标准性：定义领域标准接口

### DSSA三个活动

| 活动 | 输入 | 输出 | 说明 |
|------|------|------|------|
| 领域分析 | 领域专家知识、现有系统 | 领域模型、字典 | 识别领域共性需求和变化性 |
| 领域设计 | 领域模型 | DSSA参考架构 | 设计可复用的架构方案 |
| 领域实现 | DSSA参考架构 | 可复用构件 | 开发具体可复用组件 |

### DSSA参考模型

- 参考需求：领域内系统的共性需求，包括功能需求和质量属性需求
- 参考架构：满足参考需求的架构方案，是领域内系统的架构模板
- 参考架构的组成
    - 固定部分：领域内所有系统共有的构件
    - 可变部分：通过参数化或插件机制适应不同系统

### DSSA参与角色

| 角色 | 职责 |
|------|------|
| 领域专家 | 提供领域知识，验证模型正确性 |
| 领域分析师 | 执行领域分析，构建领域模型 |
| 领域设计者 | 设计DSSA参考架构 |
| 领域实现者 | 开发可复用构件 |
| 应用工程师 | 基于DSSA开发具体应用 |

## ABSD基于架构软件开发方法

### ABSD核心思想

- ABSD（Architecture-Based Software Development）是架构驱动的软件开发方法
- 三个驱动要素
    - 架构驱动：以架构为核心组织开发活动
    - 用例驱动：通过用例发现和验证架构决策
    - 视角与视图：从不同视角描述架构

### ABSD开发过程

| 阶段 | 活动 | 产出 |
|------|------|------|
| 架构需求 | 需求获取、需求建模、需求评审 | 架构需求规格说明 |
| 架构设计 | 架构风格选择、构件划分、接口定义 | 架构设计文档 |
| 架构文档化 | 编写架构文档、视图描述 | 架构文档 |
| 架构复审 | 架构评审、原型验证 | 评审报告 |
| 架构实现 | 构件开发、构件组装 | 可执行系统 |
| 架构演化 | 架构调整、重构 | 演化后的架构 |

### 视角与视图

- 视角（Perspective）：特定干系人关注架构的角度
- 视图（View）：从某个视角对架构的具体描述
- 常用视角
    - 功能视角：关注系统功能分解
    - 并发视角：关注并发与同步
    - 部署视角：关注物理部署
    - 数据视角：关注数据流与存储
    - 开发视角：关注代码组织

## 4+1视图模型

### 视图总览

| 视图 | 对应UML图 | 关注点 | 干系人 |
|------|-----------|--------|--------|
| 逻辑视图 | 类图、对象图、状态图 | 功能需求、系统内部协作 | 最终用户 |
| 实现视图（开发视图） | 组件图、包图 | 代码组织、模块划分、配置管理 | 程序员 |
| 进程视图 | 活动图、序列图 | 并发、同步、性能、可伸缩性 | 系统集成者 |
| 部署视图 | 部署图 | 拓扑、安装、通信、节点分布 | 系统工程师 |
| 用例视图（场景） | 用例图 | 系统核心功能、架构验证 | 所有干系人 |

### 各视图详解

**逻辑视图**

- 采用面向对象风格，以对象模型描述系统
- 关注系统内部功能分解和类间协作
- 主要元素：类、对象、接口、协作

**实现视图**

- 关注程序模块的组织结构
- 描述源代码的组织方式和模块间依赖
- 主要元素：包、子系统、层、组件

**进程视图**

- 关注系统的并发和同步
- 描述运行时进程/线程的结构和通信
- 主要元素：进程、线程、通信机制、同步机制
- 解决性能、可用性、可伸缩性等质量属性

**部署视图**

- 关注软件到硬件的映射
- 描述节点、连接和部署配置
- 主要元素：节点、处理器、设备、通信路径

**用例视图**

- 是其他四个视图的驱动因素
- 通过场景验证架构设计的正确性
- 一个场景是特定用例的实例

## 架构质量属性

### 质量属性总览

| 质量属性 | 定义 | 关键度量 |
|----------|------|----------|
| 性能 | 系统响应事件的速度 | 响应时间、吞吐量 |
| 可靠性 | 系统故障频率与影响 | MTTF、MTBF、MTTR |
| 可用性 | 系统正常运行时间比例 | 可用率（如99.99%） |
| 安全性 | 抵御攻击的能力 | 机密性、完整性、可用性 |
| 可修改性 | 修改系统的难易程度 | 修改时间、修改成本 |
| 可移植性 | 跨平台运行的能力 | 迁移工作量 |
| 可测试性 | 验证系统正确性的难易 | 测试覆盖率、缺陷发现率 |
| 互操作性 | 与其他系统交互的能力 | 接口标准化程度 |

### 性能战术

- 资源需求
    - 提高计算效率：优化算法
    - 减少计算开销：缓存结果
    - 控制资源需求：限流、削峰
- 资源管理
    - 引入并发：多线程、多进程
    - 维持数据副本：读写分离
    - 增加可用资源：水平扩展
- 资源仲裁
    - 调度策略：FIFO、优先级队列
    - 负载均衡：轮询、最少连接

### 可靠性战术

- 故障检测
    - 心跳机制、Ping/Echo
    - 异常检测、超时检测
- 故障恢复
    - 冗余：主动冗余（热备）、被动冗余（冷备）、温备
    - 回滚：状态检查点、事务回滚
    - 降级：功能降级、服务降级
- 故障预防
    - 事务机制、进程监控
    - 异常处理、输入验证

### 可用性战术

- 错误检测
    - 命令/响应（心跳）、异常检测
    - 超时、冗余比较
- 错误恢复
    - 表决（N版本编程）：N≥3，多数一致
    - 主动冗余（热备）：所有副本同时运行
    - 被动冗余（冷备）：主故障后切换
    - 备件（温备）：待命状态
    - 状态同步：检查点、影子操作
- 错误预防
    - 事务、进程监控器
    - 互斥机制、看门狗

### 安全性战术

- 抵抗攻击
    - 身份认证：密码、证书、多因素
    - 授权：访问控制列表、基于角色
    - 数据加密：传输加密、存储加密
    - 数据完整性：数字签名、消息摘要
    - 资源限制：限流、隔离
- 检测攻击
    - 入侵检测系统IDS
    - 审计日志、异常行为检测
- 从攻击中恢复
    - 识别攻击来源、恢复状态
    - 审计追踪

### 可修改性战术

- 局部化修改
    - 维持语义一致性：高内聚
    - 预期期望变更：预留扩展点
    - 泛化模块：抽象、接口
    - 限制可能变更：配置化
- 防止连锁反应
    - 信息隐藏：封装实现细节
    - 维持接口不变：接口隔离
    - 限制通信路径：中介者模式
    - 仲裁者：适配器、桥接
- 延迟绑定时间
    - 运行时注册：插件机制
    - 配置文件驱动
    - 多态、依赖注入

### 可测试性战术

- 输入/输出
    - 记录/回放：捕获输入用于重放测试
    - 接口与实现分离
- 内部监控
    - 内置监控点
    - 诊断模式、日志输出

### 互操作性战术

- 位置透明：服务发现、命名服务
- 协议标准化：REST、SOAP
- 数据转换：适配器、中间件

## 架构评估

### 架构评估方法总览

| 方法 | 全称 | 核心思想 | 关注点 |
|------|------|----------|--------|
| ATAM | 架构权衡分析法 | 场景驱动，评估质量属性权衡 | 多质量属性权衡 |
| SAAM | 软件架构分析法 | 场景驱动，评估架构对场景的支持 | 可修改性 |
| CBAM | 成本效益分析法 | 基于ATAM结果进行经济权衡 | 成本与收益 |

### ATAM架构权衡分析法步骤

| 步骤 | 活动 | 说明 |
|------|------|------|
| 1 | 介绍ATAM | 向干系人介绍评估方法 |
| 2 | 介绍业务驱动 | 说明业务目标、约束 |
| 3 | 介绍架构 | 架构师描述架构方案 |
| 4 | 识别架构方法 | 识别架构风格和模式 |
| 5 | 生成质量属性效用树 | 构建效用树，确定优先级 |
| 6 | 分析架构方法 | 针对高优先级场景分析 |
| 7 | 头脑风暴与场景优先排序 | 干系人提出场景并排序 |
| 8 | 再次分析架构方法 | 针对新场景分析 |
| 9 | 报告结果 | 汇总发现，输出报告 |

### 效用树

- 根节点：效用（Utility）
- 第二层：质量属性（性能、可靠性、可用性、安全性等）
- 第三层：质量属性细化
- 叶节点：具体场景
- 每个场景标注两个优先级
    - 对干系人的重要性（H/M/L）
    - 架构实现的难度（H/M/L）
- 优先分析 重要性H + 难度H 的场景

### 关键概念

| 概念 | 定义 | 示例 |
|------|------|------|
| 敏感点 | 影响某个质量属性的架构决策 | 加密算法选择影响安全性 |
| 权衡点 | 影响多个质量属性且方向相反的架构决策 | 增加冗余提高可用性但降低性能 |
| 风险点 | 可能导致不良后果的架构决策 | 单点故障未处理 |
| 非风险点 | 不会导致不良后果的架构决策 | 使用成熟的消息队列 |

### SAAM软件架构分析法

- 步骤
    1. 开发场景
    2. 描述架构
    3. 场景分类：直接场景（当前架构支持）和间接场景（需要修改架构）
    4. 单独评估场景
    5. 评估场景交互（多个场景需要修改同一构件 → 耦合度高）
    6. 形成评估报告
- 场景交互是SAAM的核心
    - 场景交互越多，说明构件耦合度越高，可修改性越差

### 场景驱动的评估方法

- 场景是对干系人关心的系统交互的简明描述
- 场景三要素
    - 刺激：触发系统的事件或条件
    - 环境：刺激发生时的系统状态
    - 响应：系统对刺激的反应
- 场景是架构评估的核心驱动力

### 中间件对比

| 中间件 | 体系 | 语言 | 通信方式 | 特点 |
|--------|------|------|----------|------|
| CORBA | OMG标准 | 多语言 | IIOP | 跨语言、ORB核心、IDL接口定义 |
| COM+ | Microsoft | Windows | DCOM | 组件化、事务支持、Windows绑定 |
| EJB | Java EE | Java | RMI | 容器管理、企业级服务 |

| SOA | 行业标准 | 多语言 | ESB | 服务编排、松耦合、粗粒度 |
| 微服务 | 行业实践 | 多语言 | REST/gRPC | 独立部署、细粒度、去中心化 |

### CORBA

- 核心组件
    - ORB（对象请求代理）：核心通信机制
    - IDL（接口定义语言）：定义接口
    - IIOP（互联网ORB间协议）：通信协议
    - POA（可移植对象适配器）：对象激活

### EJB

- 三种Bean
    - Session Bean：业务逻辑
    - Entity Bean：持久化数据
    - Message-Driven Bean：异步消息处理
- 容器提供的服务：事务管理、安全管理、生命周期管理

### SOA

- 核心原则
    - 服务是可复用的
    - 服务有明确定义的接口（契约）
    - 服务是松耦合的
    - 服务是自治的
    - 服务是粗粒度的
- 关键实现
    - 服务契约：WSDL
    - 服务注册与发现：UDDI
    - 服务通信：SOAP/REST
    - 服务编排：BPEL

### 微服务

- 与SOA对比

| 维度 | SOA | 微服务 |
|------|-----|--------|
| 粒度 | 粗粒度 | 细粒度 |
| 通信 | ESB（重量级） | 轻量级（REST/gRPC） |
| 数据 | 共享数据库 | 独立数据库 |
| 部署 | 整体部署 | 独立部署 |
| 治理 | 集中式 | 去中心化 |
| 技术 | 统一技术栈 | 技术多样性 |

### ESB企业服务总线

    - 消息路由：根据内容路由消息

    - 服务编排：组合多个服务
    - 安全控制：认证、授权、加密
    - 监控管理：服务监控、日志
- 缺点：单点故障、性能瓶颈、复杂度高

## Web架构设计

### MVC / MVP / MVVM

| 模式 | 数据流 | 耦合度 | 典型框架 |
|------|--------|--------|----------|
| MVC | View ↔ Controller ↔ Model | 中 | Spring MVC |
| MVP | View ↔ Presenter ↔ Model | 低 | Android早期 |
| MVVM | View ↔ ViewModel ↔ Model | 最低 | Vue.js、WPF |

**MVC**

- Model：数据和业务逻辑
- View：界面展示
- Controller：接收请求，调用Model，选择View
- Controller可访问Model，View可观察Model变化

**MVP**

- Model：数据和业务逻辑
- View：界面展示（被动视图）
- Presenter：完全控制View和Model的交互
- View与Model完全隔离，通过Presenter通信

**MVVM**

- Model：数据和业务逻辑
- View：界面展示
- ViewModel：View的抽象，暴露属性和命令
- View通过数据绑定自动同步ViewModel
- View与ViewModel双向绑定，无需手动更新

### RESTful设计原则

- 核心原则
    - 资源：一切皆资源，用URI标识
    - 统一接口：使用标准HTTP方法
    - 无状态：每次请求包含所有必要信息
    - 分层系统：客户端无需知道直接连接的是终端服务器
    - 缓存：响应应明确是否可缓存
    - 按需代码（可选）：服务器可扩展客户端功能

| HTTP方法 | 操作 | 幂等性 | 安全性 |
|----------|------|--------|--------|
| GET | 查询 | 幂等 | 安全 |
| POST | 新增 | 非幂等 | 不安全 |
| PUT | 全量更新 | 幂等 | 不安全 |
| PATCH | 部分更新 | 非幂等 | 不安全 |
| DELETE | 删除 | 幂等 | 不安全 |

### CDN

- CDN（Content Delivery Network）内容分发网络
- 核心机制
    - 将内容缓存到离用户最近的边缘节点
    - 用户请求被路由到最近的边缘节点
    - 减少网络延迟，提高访问速度
- 适用场景
    - 静态资源加速（图片、CSS、JS）
    - 大文件下载加速
    - 视频流媒体加速
    - 全站加速（动态+静态）

### 负载均衡算法

| 算法 | 原理 | 特点 |
|------|------|------|
| 轮询 | 依次分配 | 简单，不考虑服务器差异 |
| 加权轮询 | 按权重分配 | 适合服务器性能不同 |
| 最少连接 | 分配给连接数最少的服务器 | 适合长连接 |
| 加权最少连接 | 结合权重和连接数 | 综合考虑 |
| IP Hash | 根据客户端IP哈希分配 | 会话保持 |
| 随机 | 随机选择 | 实现简单 |
| 最少响应时间 | 选择响应最快的服务器 | 需要监测响应时间 |

- 负载均衡层次
    - DNS负载均衡：域名解析级别
    - 四层负载均衡（LVS）：传输层，基于IP+端口
    - 七层负载均衡（Nginx）：应用层，基于URL/头部

### 缓存策略

- 缓存层次

| 层次 | 技术 | 作用 |
|------|------|------|
| 浏览器缓存 | HTTP缓存头 | 减少重复请求 |
| CDN缓存 | 边缘节点缓存 | 就近访问 |
| 反向代理缓存 | Nginx缓存 | 减少应用服务器压力 |
| 应用缓存 | 本地缓存/分布式缓存 | 减少数据库压力 |
| 数据库缓存 | 查询缓存/Buffer Pool | 减少磁盘IO |

- 缓存问题

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 缓存穿透 | 查询不存在的数据 | 布隆过滤器、缓存空值 |
| 缓存击穿 | 热点key过期 | 互斥锁、永不过期 |
| 缓存雪崩 | 大量key同时过期 | 过期时间加随机值、多级缓存 |
| 缓存一致性 | 缓存与数据库不一致 | 延迟双删、监听binlog |

### 数据库读写分离与分库分表

**读写分离**

- 主库负责写操作，从库负责读操作
- 主从同步：异步复制、半同步复制
- 适用场景：读多写少
- 注意事项
    - 主从延迟问题
    - 读写路由中间件
    - 事务一致性

**分库分表**

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| 垂直分库 | 按业务拆分数据库 | 业务耦合度高 |
| 垂直分表 | 将大表拆分为多表（冷热分离） | 字段过多 |
| 水平分库 | 同一表数据分散到多个库 | 单库数据量过大 |
| 水平分表 | 同一库中表数据分散到多表 | 单表数据量过大 |

- 分片键选择
    - 选择区分度高的字段
    - 避免跨片查询
    - 数据分布均匀
- 分库分表问题
    - 分布式事务
    - 跨片JOIN
    - 全局唯一ID
    - 数据迁移

## 嵌入式系统架构

### 软硬件协同设计

- 嵌入式系统是软硬件结合的系统
- 设计流程
    1. 系统需求分析
    2. 软硬件功能划分
    3. 软硬件协同设计
    4. 软硬件协同仿真
    5. 软硬件协同验证
- 功能划分原则
    - 性能需求决定哪些功能用硬件实现
    - 灵活性需求决定哪些功能用软件实现
    - 成本约束影响划分决策

### 实时系统调度

| 特性 | 硬实时 | 软实时 |
|------|--------|--------|
| 截止期限 | 必须满足 | 尽量满足 |
| 超时后果 | 系统失效 | 性能下降 |
| 典型应用 | 航空航天、医疗设备 | 视频播放、在线游戏 |

- 调度算法

| 算法 | 原理 | 特点 |
|------|------|------|
| 速率单调调度（RM） | 周期越短优先级越高 | 最优静态优先级算法 |
| 截止期限单调调度（DM） | 截止期限越短优先级越高 | 适合周期不同截止期限 |
| 最早截止期限优先（EDF） | 截止期限最近的任务优先执行 | 最优动态优先级算法 |
| 最低松弛度优先（LLF） | 松弛度最小优先 | 松弛度=截止时间-剩余执行时间 |

- 可调度性条件
    - RM调度：利用率上界 U ≤ n(2^(1/n) - 1)
    - EDF调度：利用率上界 U ≤ 1

### 安全关键系统

- 安全等级标准（IEC 61508 / ISO 26262）

| SIL等级 | 失效概率 | 典型应用 |
|---------|----------|----------|
| SIL 4 | 极低 | 核电、航空 |
| SIL 3 | 很低 | 铁路信号 |
| SIL 2 | 低 | 过程控制 |
| SIL 1 | 中低 | 一般工业 |

- 安全关键系统设计原则
    - 冗余设计：多通道、表决机制
    - 故障检测与安全降级
    - 看门狗机制
    - 内存保护：MPU/MMU隔离
    - 编码标准：MISRA C/C++

## 大数据架构

### Lambda架构

- 三层结构

| 层次 | 功能 | 技术 |
|------|------|------|
| 批处理层 | 全量数据离线计算 | Hadoop/Spark |
| 速度层 | 实时增量计算 | Storm/Flink |
| 服务层 | 合并批处理与实时结果 | HBase/Redis |

- 优点：兼顾实时与离线，容错性好
- 缺点：维护两套计算逻辑，数据一致性复杂

### Kappa架构

- 统一流处理：所有数据通过流处理引擎处理
- 通过回放历史数据实现重计算
- 优点：一套代码，维护简单
- 缺点：流处理引擎要求高，历史数据处理效率低

### Lambda vs Kappa

| 维度 | Lambda | Kappa |
|------|--------|-------|
| 计算模型 | 批处理+流处理 | 纯流处理 |
| 代码维护 | 两套逻辑 | 一套逻辑 |
| 实时性 | 好 | 更好 |
| 历史数据 | 批处理层高效 | 回放流数据 |
| 复杂度 | 高 | 低 |
| 容错 | 天然容错 | 依赖流引擎 |

### 数据湖

- 数据湖是存储企业所有原始数据的大型存储库
- 特点
    - 原始数据存储：保留数据原始格式
    - Schema-on-Read：读取时定义模式
    - 多数据类型：结构化、半结构化、非结构化
    - 支持多种计算引擎
- 与数据仓库对比

| 维度 | 数据湖 | 数据仓库 |
|------|--------|----------|
| 数据类型 | 所有类型 | 结构化 |
| 模式 | 读时模式 | 写时模式 |
| 处理方式 | 批处理+流处理 | 批处理 |
| 用户 | 数据科学家 | 业务分析师 |
| 成本 | 低 | 高 |

### 流批一体

- 统一流处理和批处理的编程模型
- 同一套API同时支持流和批处理
- 代表技术：Flink、Spark Structured Streaming
- 核心思想
    - 批是流的特例（有界流）
    - 统一编程模型
    - 统一调度与资源管理

## 架构文档化

### ADL架构描述语言

- ADL（Architecture Description Language）用于形式化描述软件架构
- ADL三要素
    - 构件：计算或数据的单元
    - 连接件：构件间的交互模型
    - 架构配置：构件与连接件的拓扑结构
- 常见ADL

| ADL | 特点 |
|-----|------|
| Wright | 基于CSP，描述连接件行为 |
| Acme | 通用ADL，支持风格定义 |
| UniCon | 支持构件组装 |
| C2 | 基于消息的层次风格 |
| Aesop | 支持风格定制 |

- ADL与UML对比

| 维度 | ADL | UML |
|------|-----|-----|
| 目的 | 专门描述架构 | 通用建模语言 |
| 形式化程度 | 高 | 中 |
| 构件语义 | 严格定义 | 较弱 |
| 连接件 | 一等实体 | 无直接支持 |
| 分析能力 | 强 | 弱 |

### 架构文档结构

- 架构文档核心内容
    1. 架构概述：背景、目标、约束
    2. 架构决策：关键决策及理由
    3. 架构视图：多视图描述
    4. 架构质量属性：如何满足质量属性需求
    5. 架构评估：评估结果与改进
- 视图文档化要点
    - 模块视图：模块分解、使用关系、层次结构
    - 构件-连接件视图：构件类型、连接件类型、拓扑
    - 分配视图：软件到环境的映射
- 文档编写原则
    - 从读者角度编写
    - 避免不必要的重复
    - 记录决策理由
    - 保持文档与实现一致

## 软件架构复用

### 架构复用的三个层次

| 层次 | 复用范围 | 复用粒度 | 典型形式 | 复用程度 |
|------|---------|---------|---------|---------|
| 代码复用 | 函数/类/方法 | 细粒度 | 库函数、工具类、代码片段 | 低 |
| 设计复用 | 设计方案/模式 | 中粒度 | 设计模式、框架设计、类图 | 中 |
| 架构复用 | 整体架构 | 粗粒度 | 架构风格、架构模式、参考架构 | 高 |

- 代码复用：直接复用已有代码实现，最常见但层次最低
- 设计复用：复用设计方案和设计模式，关注构件间协作方式
- 架构复用：复用整体架构方案，复用程度最高，影响全局

### 架构复用方式

| 复用方式 | 说明 | 特点 |
|---------|------|------|

| 模式 | 经过验证的解决方案模板 | 抽象级别高，需具体实现 |
| 模板 | 可参数化的半成品代码/架构 | 直接实例化使用，复用效率高 |

- 框架复用：如Spring框架提供IoC容器和MVC架构，开发者基于框架开发
- 组件复用：如COM/JavaBean组件，通过接口规范实现即插即用
- 模式复用：如MVC模式、分层模式，提供架构设计方案
- 模板复用：如项目脚手架、代码生成模板，直接参数化使用

## ABSD方法详解

### ABSD六个阶段详解

**阶段一：架构需求**

- 需求获取：从干系人获取功能需求和质量属性需求
- 需求建模：构建需求模型，识别约束和优先级
- 需求评审：评审需求的完整性和一致性
- 产出：架构需求规格说明

**阶段二：架构设计**

- 选择架构风格：根据质量属性需求选择合适的架构风格
- 构件划分：将系统分解为构件，定义构件职责
- 接口定义：定义构件之间的接口和交互协议
- 产出：架构设计文档

**阶段三：架构文档化**

- 编写架构文档：记录架构决策、视图、质量属性方案
- 视图描述：从多个视角描述架构（逻辑视图、进程视图、部署视图等）
- 文档受众：面向不同干系人编写不同层次的文档
- 产出：架构文档

**阶段四：架构复审**

- 架构评审：由外部评审团队对架构进行正式评审
- 原型验证：通过原型验证关键架构决策的可行性
- 评审重点：质量属性是否满足、架构风险、权衡点
- 产出：评审报告

**阶段五：架构实现**

- 构件开发：按照架构设计开发具体构件
- 构件组装：将构件按架构规约组装为系统
- 架构一致性验证：确保实现与架构设计一致
- 产出：可执行系统

**阶段六：架构演化**

- 架构调整：根据需求变化调整架构
- 重构：在不改变外部行为的前提下改善内部结构
- 演化评估：评估演化后的架构是否满足新需求
- 产出：演化后的架构

### ABSD关键原则

- 架构驱动：架构是开发活动的核心，所有活动围绕架构展开
- 用例驱动：用例用于发现和验证架构决策
- 视角与视图：从不同干系人视角描述架构，确保全面性
- 迭代与增量：架构开发是迭代过程，逐步细化和完善

## 架构演化过程

### 架构演化六步法

| 步骤 | 活动 | 说明 | 产出 |
|------|------|------|------|
| 1 | 需求变化 | 识别新的功能需求或质量属性需求 | 变更需求列表 |
| 2 | 架构修改 | 根据需求变化修改架构方案，调整构件和连接件 | 修改后的架构方案 |
| 3 | 构件修改 | 根据架构修改方案，修改或新增具体构件 | 修改后的构件 |
| 4 | 系统重构 | 将修改后的构件重新组装，调整构件间关系 | 重构后的系统 |
| 5 | 测试 | 对重构后的系统进行功能测试和质量属性测试 | 测试报告 |
| 6 | 演化后评估 | 评估演化后的架构是否满足新需求，是否引入新风险 | 评估报告 |

### 架构演化类型

| 类型 | 说明 | 特点 |
|------|------|------|
| 静态演化 | 在系统停止运行时进行架构调整 | 安全性高，但需停机 |
| 动态演化 | 在系统运行时进行架构调整 | 不停机，但技术复杂度高 |

### 架构演化策略

- 架构扩展：新增构件或连接件，不修改已有结构
- 架构重构：重新组织已有构件和连接件的关系
- 架构替换：替换部分构件的实现
- 架构退化：简化架构，移除不再需要的功能

## 企业架构框架

### TOGAF

- TOGAF（The Open Group Architecture Framework）是业界最广泛使用的企业架构框架
- 核心组成部分
    - 架构开发方法（ADM）：TOGAF的核心，循环迭代的企业架构开发方法
    - 架构内容框架：定义架构工作的产出物
    - 参考模型：技术参考模型TRM和集成信息基础设施参考模型III-RM
    - 架构能力框架：建立和运营架构实践的能力

### ADM架构开发方法8阶段

| 阶段 | 名称 | 主要活动 |
|------|------|---------|
| 预备阶段 | Preliminary | 准备组织架构实践，定义原则 |
| A | 架构愿景 | 确定架构愿景、干系人、业务原则 |
| B | 业务架构 | 描述业务策略、组织、流程 |
| C | 信息系统架构 | 描述数据架构和应用架构 |
| D | 技术架构 | 描述技术基础设施和平台 |
| E | 机会与解决方案 | 识别实施项目，确定实施策略 |
| F | 迁移规划 | 制定详细实施计划和迁移路线图 |
| G | 实施治理 | 指导实施过程，确保架构合规 |
| H | 架构变更管理 | 管理架构变更，评估变更影响 |

- ADM是迭代循环过程，各阶段可反复执行
- 需求管理贯穿ADM所有阶段

### Zachman框架

- Zachman框架是企业架构的逻辑分类框架

| | 数据（What） | 功能（How） | 网络（Where） | 人员（Who） | 时间（When） | 动机（Why） |

| 设计者（系统模型） | 逻辑数据模型 | 应用架构 | 分布式系统架构 | 人机接口架构 | 处理结构 | 业务规则模型 |
| 实现者（技术模型） | 物理数据模型 | 系统设计 | 技术架构 | 表示架构 | 控制结构 | 规则设计 |
| 子构造者（详细表述） | 数据定义 | 程序 | 网络架构 | 安全架构 | 时序定义 | 规则说明 |
| 运行者（运行企业） | 数据 | 功能 | 网络 | 组织 | 时间表 | 策略 |

- Zachman框架不提供开发方法，仅提供分类视角
- 强调不同干系人从不同角度描述企业架构

## SOA详解

### SOA核心概念

| 概念 | 说明 |
|------|------|
| 服务契约 | 服务的接口定义和行为约定，包括WSDL描述、消息格式、通信协议 |
| 服务发现 | 服务消费者通过注册中心查找所需服务，UDDI是标准实现 |
| 服务编排 | 将多个服务按业务流程组合编排，BPEL是标准编排语言 |
| 服务组合 | 多个服务组合形成新的服务，提供更粗粒度的功能 |

### ESB企业服务总线详解

- ESB是SOA的核心基础设施，提供服务间通信和集成的中间件
- 核心功能

| 功能 | 说明 |
|------|------|
| 消息路由 | 根据消息内容或规则将消息路由到目标服务 |
| 消息转换 | 协议转换（SOAP↔REST）、数据格式转换（XML↔JSON） |
| 服务编排 | 将多个服务组合为业务流程 |
| 安全控制 | 认证、授权、加密、审计 |
| 监控管理 | 服务监控、性能统计、日志管理 |
| 服务注册 | 服务的注册与发现 |

- ESB实现产品：Mule ESB、Apache ServiceMix、IBM WebSphere ESB

### SCA/SDO/WS-*协议栈

**SCA（Service Component Architecture）**

- 服务组件架构，定义服务组件的组装模型
- 核心概念
    - 组件：SCA的基本单元，实现业务逻辑
    - 复合：组件的组装单元，定义组件间连接
    - 绑定：组件的访问方式（WebService绑定、JMS绑定等）
- 特点：语言无关、技术无关，支持多种实现语言和通信协议

**SDO（Service Data Objects）**

- 服务数据对象，统一的数据访问模型
- 核心概念
    - 数据图：数据的容器，包含数据对象及其变更摘要
    - 数据对象：数据的统一表示，支持离线操作
- 特点：统一访问不同数据源（数据库、XML、Web服务），支持断开连接的数据操作

**WS-*协议栈**

| 协议 | 功能 | 说明 |
|------|------|------|
| WSDL | 服务描述 | 描述服务的接口、操作、消息格式 |
| SOAP | 消息传输 | 基于XML的消息传输协议 |
| UDDI | 服务注册与发现 | 服务的注册、查询和绑定 |
| WS-Security | 安全 | 消息级安全，加密、签名、令牌 |
| WS-ReliableMessaging | 可靠消息 | 保证消息的可靠传递 |
| WS-Coordination | 协调 | 分布式活动的协调框架 |
| WS-Transaction | 事务 | 分布式事务的原子性保证 |
| WS-Policy | 策略 | 服务的策略和能力声明 |
| WS-BPEL | 业务流程 | 服务编排和业务流程定义 |

## 微服务架构详解

### 服务拆分原则

| 原则 | 说明 |
|------|------|
| 单一职责 | 每个微服务只负责一个业务能力 |
| 业务边界 | 按业务领域拆分，而非技术层 |
| 自治性 | 每个服务可独立开发、部署、运行 |
| 数据独立 | 每个服务拥有自己的数据库 |
| 粒度适中 | 过粗则失去微服务优势，过细则增加运维复杂度 |
| 限界上下文 | 基于DDD的限界上下文确定服务边界 |

### API网关

- API网关是微服务架构的统一入口
- 核心功能

| 功能 | 说明 |
|------|------|
| 请求路由 | 将请求路由到对应的微服务 |
| 负载均衡 | 对后端服务实例进行负载均衡 |
| 认证授权 | 统一的身份认证和权限校验 |
| 限流熔断 | 请求限流、服务熔断和降级 |
| 协议转换 | 外部协议与内部协议的转换 |
| 日志监控 | 统一的请求日志和监控 |
| 响应聚合 | 聚合多个微服务的响应 |

- 常见实现：Kong、Nginx、Spring Cloud Gateway、Zuul

### 服务发现

| 模式 | 说明 | 代表产品 |
|------|------|---------|
| 客户端发现 | 客户端查询注册中心获取服务实例列表，自行选择 | Eureka、Nacos |
| 服务端发现 | 客户端请求负载均衡器，由负载均衡器查询注册中心 | Nginx、Kubernetes Service |

- 服务注册：服务启动时向注册中心注册自己的地址和元数据
- 服务心跳：服务定期向注册中心发送心跳，注册中心据此判断服务健康状态
- 常见注册中心：Eureka、Consul、Nacos、ZooKeeper

### 配置中心

- 集中管理所有微服务的配置
- 核心功能

| 功能 | 说明 |
|------|------|
| 集中配置 | 统一管理所有服务的配置 |
| 动态刷新 | 配置变更后无需重启服务即可生效 |
| 环境隔离 | 支持dev/test/prod等不同环境的配置 |
| 版本管理 | 配置的版本控制和回滚 |
| 灰度发布 | 按比例或规则推送新配置 |

- 常见实现：Spring Cloud Config、Nacos、Apollo

### 熔断降级

- 熔断器模式（Circuit Breaker）

| 状态 | 说明 |
|------|------|
| 关闭（Closed） | 正常状态，请求正常通过 |
| 打开（Open） | 熔断状态，请求直接失败，不调用下游服务 |
| 半开（Half-Open） | 允许少量请求通过，测试下游是否恢复 |

- 降级策略
    - 返回默认值/缓存数据
    - 调用备用服务
    - 功能裁剪，返回简化结果
- 常见实现：Hystrix、Sentinel、Resilience4j

### 链路追踪

- 在分布式系统中追踪一个请求经过的所有服务
- 核心概念

| 概念 | 说明 |
|------|------|
| Trace | 一次完整请求的追踪链路 |
| Span | 链路中的一个服务调用 |
| Annotation | Span中的事件标注（cs/sr/ss/cr） |
| Sampling | 采样策略，避免全量采集影响性能 |

- 常见实现：Zipkin、Jaeger、SkyWalking

### 容器化部署

| 技术 | 说明 |
|------|------|
| Docker | 容器化运行环境，保证环境一致性 |
| Kubernetes | 容器编排平台，管理容器生命周期 |
| Helm | Kubernetes的包管理器 |
| Istio | 服务网格，提供流量管理、安全、可观测性 |

- Kubernetes核心概念

| 概念 | 说明 |
|------|------|
| Pod | 最小部署单元，包含一个或多个容器 |
| Service | 服务的稳定访问入口 |
| Deployment | 无状态应用部署和管理 |
| StatefulSet | 有状态应用部署和管理 |
| ConfigMap/Secret | 配置和敏感信息管理 |
| Ingress | 外部流量入口路由规则 |

## 消息队列对比

### 主流消息队列对比

| 维度 | Kafka | RabbitMQ | RocketMQ | ActiveMQ |
|------|-------|----------|----------|----------|
| 开发语言 | Scala/Java | Erlang | Java | Java |
| 吞吐量 | 极高（百万级/s） | 中（万级/s） | 高（十万级/s） | 低（万级/s） |
| 延迟 | ms级 | μs级 | ms级 | ms级 |
| 可靠性 | 高（副本机制） | 高（镜像队列） | 极高（同步刷盘+副本） | 一般 |
| 消息顺序性 | 分区内有序 | 队列有序 | 队列有序 | 队列有序 |
| 消息回溯 | 支持（按偏移量） | 不支持 | 支持（按时间戳） | 不支持 |
| 事务消息 | 支持（0.11+） | 不支持 | 支持 | 支持 |
| 消息过滤 | 简单 | 不支持 | 支持（Tag/SQL92） | 不支持 |
| 适用场景 | 大数据/日志/流处理 | 中小规模业务系统 | 电商/金融/高可靠场景 | 传统企业应用 |

### 选型建议

| 场景 | 推荐 | 原因 |
|------|------|------|
| 日志采集/大数据 | Kafka | 吞吐量极高，支持消息回溯 |
| 业务解耦/异步处理 | RabbitMQ | 延迟低，功能丰富，社区成熟 |
| 电商/金融交易 | RocketMQ | 高可靠，事务消息，消息过滤 |
| 传统JMS应用 | ActiveMQ | JMS规范兼容 |

### 消息队列核心指标

| 指标 | 说明 | 考量因素 |
|------|------|---------|
| 吞吐量 | 单位时间处理消息数 | 系统负载能力 |
| 延迟 | 消息从发送到消费的时间 | 实时性要求 |
| 可靠性 | 消息不丢失的能力 | 业务重要性 |
| 消息顺序 | 消息的消费顺序保证 | 业务逻辑依赖 |
| 消息去重 | 防止重复消费 | 幂等性设计 |
| 水平扩展 | 集群扩展能力 | 未来增长预期 |
