# 软件工程

## 软件过程模型

| 模型 | 核心思想 | 特点 | 适用场景 |
|------|----------|------|----------|
| 瀑布模型 | 线性顺序推进 | 阶段明确、文档驱动、缺乏灵活性 | 需求明确、技术成熟的项目 |
| 原型模型 | 构建原型逐步细化 | 降低需求不确定性、用户参与度高 | 需求模糊的项目 |
| 螺旋模型 | 风险驱动迭代 | 每轮含风险分析、迭代递增 | 高风险大型项目 |
| 增量模型 | 分批交付 | 先核心后扩展、可提前交付 | 需求大体明确但需分批交付 |
| 喷泉模型 | 面向对象迭代 | 迭代无间隙、各阶段可重叠 | 面向对象开发项目 |
| V模型 | 测试与开发对应 | 每个开发阶段有对应测试阶段 | 对质量要求高的项目 |
| 敏捷模型 | 个体互动、响应变化 | 迭代短、用户参与、拥抱变化 | 需求变化频繁的小团队 |
| DevOps | 开发运维一体化 | 持续集成/交付/部署、自动化 | 互联网产品、快速迭代 |

### V模型测试阶段对应关系

| 开发阶段 | 对应测试阶段 |
|----------|--------------|
| 需求分析 | 验收测试 |
| 概要设计 | 系统测试 |
| 详细设计 | 集成测试 |
| 编码 | 单元测试 |

## 需求工程

### 需求层次

| 层次 | 说明 | 示例 |
|------|------|------|
| 业务需求 | 组织高层目标 | 提升客户满意度20% |
| 用户需求 | 用户完成任务的需要 | 用户能在线查询订单 |
| 功能需求 | 系统应具备的功能 | 系统提供订单查询接口 |

### 需求获取方法

| 方法 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| 用户访谈 | 与用户面对面交流，深入挖掘需求 | 灵活深入、可追问细节、获取隐性需求 | 耗时、样本有限、访谈者需有技巧 |
| 问卷调查 | 设计问卷分发给大量用户 | 覆盖面广、成本低、可量化分析 | 问题固定无法追问、回收率低、答案可能不真实 |
| 现场观察 | 到用户工作现场观察实际操作 | 获取真实工作流程、发现用户未表达的需求 | 耗时长、用户可能因被观察而改变行为 |
| 文档分析 | 分析现有系统文档、业务表单等 | 基于客观资料、不干扰用户工作 | 文档可能过时或不完整 |
| 原型法 | 构建系统原型让用户试用反馈 | 直观形象、用户参与度高、减少误解 | 构建原型需时间、用户可能关注界面忽略功能 |
| JAD联合应用开发 | 用户、开发者、管理层联合会议 | 高效达成共识、减少沟通成本 | 组织难度大、需经验丰富的主持人 |
| 快速原型法 | 快速构建可运行原型迭代确认 | 快速验证需求、降低开发风险 | 原型代码质量可能不高、可能偏离最终系统 |

### 结构化方法

### SD结构化设计详解

#### 变换流与事务流

| 数据流类型 | 特征 | 示例 |
|------------|------|------|
| 变换流 | 数据沿输入路径进入系统，经过加工处理，沿输出路径离开 | 计算类系统：输入数据→计算→输出结果 |
| 事务流 | 数据沿输入路径到达事务中心，根据事务类型选择多条动作路径之一 | 菜单驱动系统：选择命令→分发到不同处理 |

#### 变换设计步骤

1. 复审基本系统模型
2. 复审并精化数据流图
3. 确定数据流图是变换流还是事务流
4. 确定输入流和输出流的边界，找出变换中心
5. 设计第一级分解：将系统分为输入模块、变换模块、输出模块
6. 设计第二级分解：对每个模块进一步分解
7. 精化软件结构

#### 事务设计步骤

1. 复审基本系统模型
2. 复审并精化数据流图
3. 确定数据流图是变换流还是事务流
4. 识别事务中心和各事务路径
5. 设计第一级分解：将系统分为接收模块、事务中心模块、各动作模块
6. 设计第二级分解：对每个动作路径进一步分解
7. 精化软件结构

#### 模块划分原则

- 核心原则：高内聚、低耦合
- 模块规模适中（约50~100行）
- 深度、宽度、扇出、扇入适当
- 模块的作用域应在控制域之内

#### 内聚类型（由低到高）

| 内聚类型 | 说明 | 考点 |
|----------|------|------|
| 偶然内聚 | 模块内各处理元素之间没有联系 | 最差 |
| 逻辑内聚 | 逻辑上相关的功能放在同一模块 | 如：所有输入操作 |
| 时间内聚 | 同一时间执行的功能放在同一模块 | 如：初始化模块 |
| 过程内聚 | 按特定次序执行的功能放在同一模块 | 如：按步骤处理 |
| 通信内聚 | 使用相同输入/输出数据的功能放在同一模块 | 如：操作同一数据结构 |
| 顺序内聚 | 前一功能的输出是后一功能的输入 | 如：读数据→处理数据 |
| 功能内聚 | 完成单一功能，各部分不可或缺 | 最佳 |

#### 耦合类型（由高到低）

| 耦合类型 | 说明 | 考点 |
|----------|------|------|
| 内容耦合 | 一个模块直接访问另一个模块内部数据 | 最差 |
| 公共耦合 | 多个模块访问同一全局数据结构 | 如：全局变量 |
| 外部耦合 | 模块间通过外部环境（如文件格式）关联 | 如：共享外部文件 |
| 控制耦合 | 一个模块通过传递控制信息控制另一个模块 | 如：传递标志位 |
| 标记耦合 | 模块间通过数据结构（记录）传递数据 | 如：传递结构体 |
| 数据耦合 | 模块间通过简单数据参数传递 | 如：传递基本类型参数 |
| 非直接耦合 | 模块间没有直接关系，通过主模块调用 | 最佳 |

### 面向对象方法

| 阶段 | 方法 | 产出 |

| OOA（面向对象分析） | 识别类与对象 | 用例图、类图 |

#### OOA面向对象分析

OOA的三个主要活动：

1. **认定对象**：从问题域中识别出客观存在的对象，确定类的属性和操作
2. **组织对象**：分析对象间的关系，建立一般-特殊结构（继承）、整体-部分结构（组合）
3. **描述对象间的交互**：定义对象间的消息传递和协作关系

#### OOD面向对象设计

OOD的四个主要活动：

| 设计活动 | 说明 |
|----------|------|
| 问题域设计 | 将OOA结果直接映射为OOD的问题域部分，调整和补充设计细节 |
| 人机交互设计 | 设计用户界面，包括窗口、菜单、对话框等交互元素 |
| 任务管理设计 | 识别并发任务，设计任务协调和同步机制 |
| 数据管理设计 | 设计数据存储方案，如文件系统或数据库映射 |

#### 多态详解

| 多态类型 | 说明 | 绑定时机 |
|----------|------|----------|
| 重载（静态多态） | 同一类中方法名相同、参数列表不同 | 编译时绑定 |
| 覆盖（动态多态） | 子类重写父类方法，调用时执行子类版本 | 运行时绑定 |
| 动态绑定 | 程序运行时根据对象实际类型决定调用哪个方法 | 运行时绑定 |

- 重载是编译时多态，覆盖是运行时多态
- 动态绑定是实现覆盖多态的底层机制

| 命令 | 行为型 | 请求封装为对象 | 撤销/重做、任务队列 |

#### 创建型模式

**单例模式（Singleton）**

- 意图：确保一个类只有一个实例，并提供全局访问点

| 实现方式 | 说明 | 线程安全 | 特点 |
|----------|------|----------|------|
| 饿汉式 | 类加载时即创建实例 | 安全 | 简单直接，但可能浪费资源 |
| 懒汉式 | 首次使用时创建实例 | 不安全（需加锁） | 延迟加载，但需处理并发 |
| 双重检查锁 | 加锁前后两次检查 | 安全 | 兼顾性能和线程安全 |

- 饿汉式：利用类加载机制保证线程安全
- 懒汉式：延迟初始化，但需synchronized保证线程安全
- 双重检查锁：先判空再加锁，加锁后再判空，避免重复创建

**工厂方法模式（Factory Method）**

- 意图：定义创建对象的接口，让子类决定实例化哪个类
- 结构：抽象产品、具体产品、抽象工厂、具体工厂
- 优点：遵循开闭原则，新增产品只需新增工厂类
- 缺点：每增加一个产品需增加一个工厂类

**抽象工厂模式（Abstract Factory）**

- 意图：创建一族相关或相互依赖的对象，无需指定具体类
- 与工厂方法的区别：工厂方法创建一种产品，抽象工厂创建一族产品
- 优点：保证产品族一致性
- 缺点：增加新产品类型需修改所有工厂

**建造者模式（Builder）**

- 意图：将复杂对象的构建与表示分离，使同样的构建过程可创建不同表示
- 结构：Director（指挥者）+ Builder（建造者）+ Product（产品）
- 适用场景：构建复杂对象，如SQL查询构建器、文档生成器
- 与工厂模式的区别：建造者关注构建过程，工厂关注创建结果

#### 结构型模式

**适配器模式（Adapter）**

- 意图：将一个类的接口转换为客户期望的另一个接口

| 类型 | 说明 |
|------|------|
| 类适配器 | 通过多重继承实现，适配器继承被适配类并实现目标接口 |
| 对象适配器 | 通过组合实现，适配器持有被适配对象的引用 |

- 类适配器使用继承，对象适配器使用组合
- 对象适配器更灵活，推荐优先使用

**装饰器模式（Decorator）**

- 意图：动态地给对象添加额外职责，比生成子类更灵活
- 结构：Component（抽象组件）+ ConcreteComponent（具体组件）+ Decorator（装饰器）
- 特点：装饰器和具体组件都实现相同接口，装饰器持有组件引用
- 与继承的区别：装饰器是动态扩展，继承是静态扩展
- 典型应用：Java I/O流（BufferedInputStream装饰FileInputStream）

**代理模式（Proxy）**

- 意图：为其他对象提供代理以控制对这个对象的访问

| 代理类型 | 说明 |
|----------|------|
| 静态代理 | 编译时确定代理类，代理类和被代理类实现相同接口 |
| 动态代理 | 运行时动态生成代理类，如JDK动态代理、CGLIB |

- JDK动态代理：基于接口，使用Proxy类和InvocationHandler
- CGLIB动态代理：基于继承，生成目标类的子类

**外观模式（Facade）**

- 意图：为子系统中的一组接口提供统一的高层接口，简化子系统使用
- 优点：降低客户端与子系统的耦合度，客户端无需了解子系统内部复杂性
- 缺点：不符合开闭原则，修改外观类需修改源码

#### 行为型模式

**观察者模式（Observer）**

- 意图：定义对象间一对多的依赖关系，当一个对象状态改变时所有依赖者收到通知
- 结构：Subject（主题）+ Observer（观察者）
- 推模式：主题主动推送数据给观察者
- 拉模式：主题通知观察者，观察者主动获取数据
- 典型应用：事件监听、MVC中的Model-View

**策略模式（Strategy）**

- 意图：定义一系列算法，将每个算法封装起来，使它们可以互换
- 结构：Context（上下文）+ Strategy（策略接口）+ ConcreteStrategy（具体策略）
- 优点：算法可独立变化，避免多重条件判断
- 典型应用：支付方式选择、排序算法切换

**模板方法模式（Template Method）**

- 意图：定义算法骨架，将某些步骤延迟到子类实现
- 结构：AbstractClass（抽象类，定义模板方法）+ ConcreteClass（具体类，实现步骤）
- 钩子方法：在抽象类中提供默认实现，子类可选择覆盖
- 好莱坞原则：不要调用我们，我们会调用你

**命令模式（Command）**

- 意图：将请求封装为对象，从而可用不同的请求对客户进行参数化
- 结构：Command（命令接口）+ ConcreteCommand（具体命令）+ Receiver（接收者）+ Invoker（调用者）
- 优点：支持撤销/重做、请求排队、日志记录
- 典型应用：菜单操作、宏命令、事务管理

**状态模式（State）**

- 意图：允许对象在内部状态改变时改变其行为，对象看起来似乎修改了其类
- 与策略模式的区别：状态模式中状态间可自动转换，策略模式由客户端选择策略
- 优点：将状态转换逻辑分布到各个状态类中，避免大量条件判断
- 典型应用：订单状态流转、TCP连接状态

## 软件测试

### 白盒测试覆盖标准（由弱到强）

| 覆盖类型 | 说明 |
|----------|------|
| 语句覆盖 | 每条语句至少执行一次（最弱） |
| 判定覆盖（分支覆盖） | 每个判定的真假分支至少执行一次 |
| 条件覆盖 | 每个条件的真假至少取一次 |
| 判定-条件覆盖 | 同时满足判定覆盖和条件覆盖 |
| 条件组合覆盖 | 每个条件的各种组合至少出现一次 |
| 路径覆盖 | 覆盖所有可能路径（最强） |

### 黑盒测试方法

| 方法 | 说明 |
|------|------|
| 等价类划分 | 将输入划分为有效/无效等价类 |
| 边界值分析 | 取边界及附近值测试 |
| 因果图 | 分析输入条件间的因果关系 |
| 判定表 | 列出条件组合与动作的对应关系 |
| 错误推测法 | 基于经验推测可能出错的情况 |

### McCabe环路复杂度

- 公式：V(G) = E - N + 2
  - E：有向图中边数
  - N：有向图中节点数
- 也可计算：V(G) = 判定节点数 + 1
- V(G) ≤ 10 为合理复杂度

### 测试阶段

| 阶段 | 对象 | 方法 | 人员 |
|------|------|------|------|
| 单元测试 | 模块/函数 | 白盒为主 | 开发人员 |
| 集成测试 | 模块间接口 | 白盒+黑盒 | 开发+测试 |
| 系统测试 | 整个系统 | 黑盒为主 | 测试人员 |
| 验收测试 | 交付系统 | 黑盒 | 用户/客户 |

### 集成测试策略

- 自顶向下：需编写桩模块（Stub）
- 自底向上：需编写驱动模块（Driver）
- 大爆炸集成：一次性集成所有模块
- 三明治集成：自顶向下与自底向上结合

## 软件维护

### 维护类型及占比

| 类型 | 占比 | 说明 | 触发原因 |
|------|------|------|----------|
| 完善性维护 | 50%~66% | 增加功能、改善性能 | 用户提出新需求 |
| 适应性维护 | 18%~25% | 适应环境变化 | 运行环境改变（OS升级、法规变化等） |
| 改正性维护 | 17%~21% | 修复缺陷 | 发现程序错误 |
| 预防性维护 | 4%左右 | 提高可维护性 | 主动改进（为未来维护做准备） |

- 记忆口诀：完善最多、适应次之、改正第三、预防最少
- 完善性维护是软件维护的主要工作

### 可维护性决定因素

| 因素 | 说明 |
|------|------|
| 可理解性 | 他人能理解软件的结构、接口和内部处理过程 |
| 可测试性 | 诊断和测试软件缺陷的容易程度 |
| 可修改性 | 修改软件的容易程度，与模块独立性直接相关 |
| 可靠性 | 软件在规定条件下完成规定功能的能力 |
| 可移植性 | 软件从一种环境转移到另一种环境的能力 |
| 可使用性 | 用户使用软件的方便程度 |

- 可维护性 = 可理解性 + 可测试性 + 可修改性 + 可靠性 + 可移植性 + 可使用性
- 提高可维护性的方法：建立明确的软件质量目标、使用先进的开发技术、进行周期性维护审查

## 净室工程CSE

### 核心思想

- 通过数学验证代替传统测试，追求零缺陷交付
- 核心理念：预防胜于消除，在开发过程中避免引入缺陷

### 盒结构规约

盒结构从外到内逐步细化，每一步增加更多设计细节：

| 盒类型 | 说明 | 对应 |
|--------|------|------|
| 黑盒 | 只描述外部可见行为（输入→输出），不涉及内部实现 | 对应需求规约 |
| 状态盒 | 在黑盒基础上增加内部状态描述，定义状态转换 | 对应高层设计 |
| 透明盒（清晰盒） | 在状态盒基础上描述具体的处理过程和逻辑 | 对应详细设计 |

- 黑盒→状态盒→透明盒，逐步求精
- 每一步变换都保持行为等价性

### 正确性验证

- 用数学证明替代传统单元测试
- 对透明盒中的每条执行路径进行正确性证明
- 验证过程：对每个函数的输入输出关系进行形式化推理
- 团队评审验证：由开发团队集体走查证明逻辑

### 统计使用测试

- 不做传统的穷举测试，而是基于使用模型的统计抽样测试
- 建立使用模型（Markov链），描述用户可能的操作序列及概率
- 根据使用模型生成测试用例，进行统计抽样
- 通过统计推理得出软件的质量置信度
- 测试目的：验证软件在预期使用环境下的可靠性，而非发现缺陷

### 增量开发

- 将系统划分为多个增量，逐步开发和交付
- 每个增量都经过完整的盒结构规约和正确性验证
- 增量间有明确的使用依赖关系
- 优点：早期交付、逐步积累质量、降低风险

## 逆向工程与重构

### 逆向工程

#### 四级抽象（由低到高）

| 级别 | 说明 | 产出 |
|------|------|------|
| 实现级 | 抽象出程序和数据结构 | 源代码、数据结构定义 |
| 结构级 | 反映程序分量间关系 | 调用图、结构图 |
| 功能级 | 反映程序功能与功能间关系 | 功能规约、处理逻辑 |
| 领域级 | 反映程序与业务领域的关系 | 领域模型、业务规则 |

- 抽象级别越高，还原度越低
- 逆向工程产出不唯一（同一源码可得出不同抽象结果）
- 逆向工程本身不改变系统，仅进行分析和理解

### 重构

- 在不改变软件外部行为的前提下改善内部结构
- 目的：提高可理解性、可维护性、降低复杂度
- 常见手法：提取方法、重命名变量、消除重复代码、简化条件表达式

### 再工程（Reengineering）

| 概念 | 说明 | 是否改变系统 |
|------|------|--------------|
| 逆向工程 | 分析现有系统，提取抽象信息 | 否，仅分析 |
| 重构 | 改善内部结构，不改变外部行为 | 是，但行为不变 |
| 再工程 | 逆向工程 + 重构/重新设计，在逆向理解基础上重新构建 | 是，可能改变行为 |

- 再工程 = 逆向工程 + 新需求的重新开发
- 再工程目的：在保留系统核心功能的前提下，提高可维护性和可演化性
- 再工程过程：先逆向理解→再重构/重写
