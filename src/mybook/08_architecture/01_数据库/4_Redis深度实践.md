# Redis 深度实践：8 大核心主题

Redis（Remote Dictionary Server，远程字典服务）是一个开源的、基于内存的键值对存储系统，常被用作数据库、缓存和消息中间件。本文从概述、集群架构、Pub/Sub、批量操作、缓存一致性、缓存问题、缓存利用率、分布式锁 8 个维度深度解析 Redis。

---

## 一、概述

### 1.1 为什么使用 Redis

| 场景 | 说明 |
|------|------|
| 高性能缓存 | 数据存内存，微秒级读写，拦截高频请求，降低数据库压力 |
| 高并发 | 单线程内存操作模型，轻松应对秒杀、抢购等瞬时超高并发 |
| 丰富数据结构 | String/Hash/List/Set/ZSet/Bitmap/GEO/HyperLogLog/Stream，内置原子操作 |

### 1.2 Redis vs Memcached

| 维度 | Redis | Memcached |
|------|-------|-----------|
| 核心定位 | 多功能内存数据存储（缓存/数据库/消息中间件） | 纯高性能键值缓存 |
| 数据结构 | 丰富（String/Hash/List/Set/ZSet/Bitmap 等） | 单一（仅 String） |
| 持久化 | 支持（RDB + AOF） | 不支持 |
| 网络模型 | 单线程 Reactor（6.0 后网络 I/O 多线程） | 多线程 |
| 集群 | 原生 Redis Cluster | 无原生集群 |
| 内存管理 | 精细控制，淘汰策略，编码优化 | Slab Allocation，可能内存碎片 |

### 1.3 性能优化设计

1. **基于内存存储**：内存读写纳秒级（~100ns），磁盘毫秒级（~10ms），差 5 个数量级
2. **高效数据结构**：zipList/intSet/skiplist 等底层编码优化
3. **单线程事件循环**：核心命令单线程执行，避免上下文切换和锁竞争
4. **I/O 多路复用**：epoll 管理成千上万连接，单线程不阻塞

### 1.4 单线程模型演进

| 版本 | 模型 | 说明 |
|------|------|------|
| 6.0 之前 | 经典单线程 Reactor | 接收→解析→执行→返回全由主线程串行完成 |
| 6.0+ | 网络 I/O 多线程 + 核心命令单线程 | I/O 线程处理读写，主线程顺序执行命令 |

> 引入网络 I/O 多线程是为了解决网络吞吐瓶颈，而非并行执行命令。避免锁竞争、保证命令原子性的单线程命令执行模型没有改变。

### 1.5 数据类型

| 类型 | 特点 | 典型场景 |
|------|------|----------|
| String | 最简单键值对，最大 512MB | 缓存、计数器（INCR）、分布式锁（SETNX） |
| Hash | 键值对集合，最多 2^32-1 字段 | 存储对象信息，部分读写 |
| List | 有序双向队列 | 消息队列（LPUSH+BRPOP）、时间线 |
| Set | 无序唯一集合，支持交并差 | 去重、共同关注、随机抽奖 |
| Sorted Set | 有序集合，元素关联 Score | 排行榜、带权重队列、范围查询 |
| Bitmap | String 视为位数组 | 二值状态统计（签到）、大数据量是否判断 |
| GEO | 底层 Sorted Set，经纬度编码 | 附近的人/商家、距离计算 |
| HyperLogLog | 基数估计，固定约 12KB，误差 0.81% | 海量 UV 统计 |
| Stream | 持久化消息队列，消费者组 | 异步消息通信、事件流 |

### 1.6 持久化机制

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **RDB** | 定时快照到二进制文件 | 恢复快，适合备份 | 可能丢失较多数据，fork 可能阻塞 |
| **AOF** | 追加写操作命令到日志 | 数据安全性高（最多丢 1 秒） | 文件大，恢复慢 |
| **混合持久化**（4.0+） | RDB 头 + AOF 尾 | 兼具两者优势 | AOF 可读性变差 |

**AOF 刷盘策略**：

| 策略 | 安全性 | 性能 |
|------|--------|------|
| always | 最高 | 最差 |
| everysec（默认） | 折衷 | 折衷 |
| no | 最低 | 最好 |

**AOF 重写**：压缩冗余命令（100 次 INCR → 1 条 SET），fork 子进程扫描内存生成新文件，重写期间新命令同时写入当前 AOF 和重写缓冲区。

### 1.7 数据过期策略

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 惰性删除 | 访问时检查过期则删除 | CPU 友好 | 内存不友好，过期键长期占内存 |
| 定期删除 | 周期性随机抽查过期键删除 | 折中方案 | 概率性清理，无法保证立即删除 |

两者配合在 CPU 消耗和内存释放及时性之间取得平衡。

### 1.8 内存淘汰策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| noeviction | 不淘汰，直接报错 | 数据不允许丢失 |
| allkeys-lru | 所有键 LRU 淘汰 | **纯缓存场景最常用** |
| volatile-lru | 有过期时间的键 LRU 淘汰 | 混合存储（保护持久状态） |
| allkeys-random | 所有键随机淘汰 | 访问完全随机 |
| volatile-random | 有过期时间的键随机淘汰 | 临时数据重要性相同 |
| volatile-ttl | 淘汰 TTL 最短的键 | 希望尽快释放即将过期空间 |
| allkeys-lfu（4.0+） | 所有键 LFU 淘汰 | 根据长期访问频率淘汰 |
| volatile-lfu（4.0+） | 有过期时间的键 LFU 淘汰 | 临时数据中淘汰低频 |

## 二、集群架构

### 2.1 单节点弊端

| 弊端 | 说明 |
|------|------|
| 单点故障 | 服务器宕机 → 服务完全不可用 |
| 容量有限 | 单机内存有限，数据量超限无法写入 |
| 数据丢失 | 异步持久化，宕机可能丢失最后一次持久化后的数据 |

### 2.2 三种集群架构

| 架构 | 核心思想 | 解决问题 | 局限 |
|------|---------|---------|------|
| **主从复制** | 一主多从，异步复制命令流 | 数据备份、读扩展 | 写能力和存储容量未变 |
| **哨兵** | 主从 + 哨兵监控 + 自动故障转移 | 单点故障自动切换 | 写能力和存储容量未变 |
| **Redis Cluster** | 16384 哈希槽分片 + 主从复制 + 故障转移 | 高可用 + 数据分片 + 数据副本 | 最完整方案 |

## 三、Pub/Sub 机制

### 3.1 核心机制

- **PUBLISH** 向频道发消息
- **SUBSCRIBE** 订阅频道
- **PSUBSCRIBE** 模式订阅（通配符 `*` 和 `?`）

### 3.2 优缺点

| 优点 | 缺点 |
|------|------|
| 实时性高（推送模型） | 消息不持久化 |
| 完全解耦 | 无消息堆积能力 |
| 部署简单 | 缺乏消费者负载均衡 |
| 一对多广播 | 客户端断连期间消息丢失 |

### 3.3 四种消息机制对比

| 特性 | Redis List | Redis Pub/Sub | Redis Stream | 专业消息中间件 |
|------|-----------|---------------|--------------|--------------|
| 模型 | 点对点队列 | 发布/订阅 | 支持消费者组 | 发布/订阅+分区 |
| 持久化 | 支持 | 不支持 | 支持 | 磁盘持久化 |
| 消费确认 | 无 | 无 | ACK | ACK |
| 负载均衡 | 不支持 | 不支持 | 消费者组 | 分区级均衡 |
| 消息回溯 | 不支持 | 不支持 | 按ID读取 | 按偏移量 |
| 复杂度 | 低 | 低 | 中 | 高 |

## 四、批量操作

### 4.1 四种方式对比

| 方式 | 核心思想 | 原子性 | 网络开销 | 灵活性 | 适用场景 |
|------|---------|--------|---------|--------|---------|
| 原子操作指令 | 服务器原生批量命令 | 单命令原子 | 1 次往返 | 低，固定命令 | 同类型简单批量读写 |
| Pipeline | 缓冲多命令批量通信 | 无 | 1 次往返 | 高，任意组合 | 大批量读写，无需原子性 |
| 事务（MULTI/EXEC） | 命令入队串行执行 | 执行连续，无回滚 | 多次往返 | 中，可组合命令 | 需连续执行不被干扰 |
| Lua 脚本 | 服务器端执行脚本 | 脚本原子执行 | 1 次往返 | 极高，可编程 | 需原子性且逻辑复杂 |

### 4.2 关键区别

- **Pipeline 非原子**：执行过程中其他客户端命令可穿插
- **Redis 事务无回滚**：某条命令失败不回滚已执行命令，继续执行后续
- **Lua 脚本最强**：原子执行 + 可编程逻辑 + 一次网络通信

## 五、缓存数据库一致性

### 5.1 CAP 与 BASE

- **CAP**：分布式系统最多同时满足 C/A/P 中两项，P 必选，在 CP 和 AP 间选择
- **BASE**：AP 方案的补充——基本可用、软状态、最终一致性

### 5.2 五种缓存模式

| 模式 | 读数据库 | 写数据库 | 核心特征 | CAP 倾向 |
|------|---------|---------|---------|---------|
| **旁路缓存** | 应用 | 应用 | 先更 DB 后删缓存 | AP + BASE |
| **读穿透** | 缓存 | 应用 | 缓存层负责回源加载 | AP + BASE |
| **写穿透** | 缓存 | 缓存 | 缓存同步写 DB | 倾向 CP |
| **写回** | 缓存 | 缓存 | 缓存异步批量写 DB | 极致 AP + BASE |
| **CDC** | 应用 | 应用 | Binlog → MQ → 更新缓存 | AP + BASE |

### 5.3 旁路缓存核心原则

- **先更 DB 后删缓存**（非更新缓存）：避免并发写冲突 + 懒加载节能 + 删除幂等
- **删除而非更新缓存**：避免并发覆盖、减少资源浪费、降低维护复杂度

### 5.4 缓存穿透应对

| 方案 | 原理 |
|------|------|
| 缓存空值 | 查不到也缓存空标记，短 TTL |
| 布隆过滤器 | 前置拦截"一定不存在"的请求 |
| 请求限流 | 同一 Key 只允许一个请求回源 |
| 本地缓存 L1 | 应用实例内缓存空标记，减轻公共缓存压力 |

### 5.5 CDC + 异步更新

应用只更 DB → Canal 监听 Binlog → Kafka 投递 → 独立消费者更新/删除缓存

## 六、缓存击穿、穿透、雪崩

### 6.1 三大问题对比

| 问题 | 核心特征 | 形象比喻 | 典型后果 |
|------|---------|---------|---------|
| **缓存击穿** | 单个热点 Key 突然过期 | VIP 休息室突然关门 | 重建缓存并发量巨大，压垮 DB |
| **缓存穿透** | 查询不存在的数据 | 捣乱分子点不存在的菜 | 每次穿透缓存打 DB，缓存被闲置 |
| **缓存雪崩** | 大批量 Key 同时失效或 Redis 宕机 | 所有闸机同时停电 | 海量流量涌向 DB，DB 崩溃 |

### 6.2 缓存击穿解决方案

| 方案 | 核心思想 | 优点 | 缺点 |
|------|---------|------|------|
| 过期时间加随机值 | 分散失效时间 | 简单低成本 | 无法解决单个热点 Key |
| 热点 Key 永不过期 | 不设 TTL，后台异步更新 | 彻底解决击穿 | 一致性维护成本高 |
| 互斥锁（串行重建） | SETNX 只允许一个请求重建 | 强一致性 | 性能损耗，死锁风险 |
| 逻辑过期 | 数据内嵌过期时间，过期返回旧数据 + 后台异步重建 | 性能最高 | 数据一致性弱 |

### 6.3 缓存穿透解决方案

| 方案 | 核心思想 | 优点 | 缺点 |
|------|---------|------|------|
| 参数校验 | 源头拦截非法请求 | 成本最低效率最高 | 只能防明显非法参数 |
| 缓存空对象 | 查不到也缓存空标记 | 实现简单 | 内存浪费，短时不一致 |
| 布隆过滤器 | 前置拦截"一定不存在" | 内存极小，拦截高效 | 存在误判率，不支持删除 |

### 6.4 缓存雪崩解决方案

| 方案 | 核心思想 | 适用场景 |
|------|---------|---------|
| 过期时间加随机值 | 错峰失效 | Key 集中过期 |
| 高可用集群 | 主从 + 哨兵/Cluster 自动故障转移 | Redis 宕机 |

## 七、缓存利用率

### 7.1 缓存命中率

命中率 = 命中次数 / (命中次数 + 未命中次数) × 100%

命中率过低 → 响应延迟增加 → DB 负载过载 → 系统不稳定

### 7.2 提高命中率手段

| 维度 | 手段 |
|------|------|
| 数据类型选择 | 对象存储用 Hash 而非 String JSON，节省内存 |
| 缓存粒度 | 只缓存常用字段，避免全量缓存 |
| 缓存预热 | 系统启动/大促前提前加载热点数据 |
| 过期机制 | 根据更新频率和业务容忍度合理设置 TTL |
| 淘汰策略 | allkeys-lru 保证热点数据留在缓存 |

### 7.3 缓存预热

| 时机 | 方式 |
|------|------|
| 系统启动/重启后 | 脚本批量加载 |
| 大促活动前 | 手动触发预热 |
| 定时任务 | Crontab/Scheduled 低峰期自动执行 |
| 数据变更后 | MQ 异步加载 |

### 7.4 BigKey 问题

**判定标准**：String > 10KB，集合 > 5000 元素

| 危害 | 说明 |
|------|------|
| 阻塞主线程 | 操作大 Key 占用大量 CPU 时间 |
| 网络拥塞 | 巨大数据包占用带宽 |
| 内存倾斜 | 集群中某节点内存远高于其他 |

**解决方案**：

| 方案 | 说明 |
|------|------|
| 拆分 | 大对象拆为多个子 Key，大集合按取模拆分 |
| 清理修剪 | LTRIM/ZREMRANGEBYRANK 控制长度，设 TTL |
| 压缩 | Protobuf/MsgPack/GZIP 减少 Value 体积 |
| 监控 | `redis-cli --bigkeys` 扫描，代码层门禁检查 |

## 八、分布式锁

### 8.1 核心要求

| 要求 | 说明 |
|------|------|
| 互斥性 | 任意时刻最多一个客户端持有锁 |
| 安全性 | 锁只能由加锁客户端释放 |
| 死锁避免 | 锁持有者崩溃后锁必须能自动释放 |
| 高可用 | 锁服务本身不应成为单点故障 |

### 8.2 常见方案对比

| 方案 | 代表 | 特点 |
|------|------|------|
| 内存数据库 | Redis | 高性能，最终一致 |
| 关系型数据库 | MySQL | 唯一索引/行级锁，强一致但性能低 |
| 分布式协调服务 | ZooKeeper/Etcd | 强一致，临时有序节点/租约 |

### 8.3 Redis 分布式锁演进

| 方案 | 命令 | 原子性 | 死锁风险 | 推荐度 |
|------|------|--------|---------|--------|
| SETNX + EXPIRE | 两步操作 | 非原子 | **存在**（SETNX 成功后崩溃） | ❌ 不推荐 |
| Lua 脚本 | EVAL SETNX+EXPIRE | 原子 | 无 | ⚠️ 旧版本可用 |
| **SET NX PX** | 一条命令 | 原子 | 无 | ✅ **标准方案** |
| **Redlock** | 多数派 N/2+1 | 原子 | 无 | ✅ 高可靠场景 |

### 8.4 SET NX PX 标准方案

```bash
SET {lock_key} {unique_client_value} NX PX {timeout_ms}
```

- **NX**：仅当键不存在时设置（互斥性）
- **PX**：设置毫秒级过期时间（死锁避免）
- **释放锁**：Lua 脚本验证 value 后删除（安全性）

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

### 8.5 Redlock 算法

部署 N 个（建议 5 个）独立 Redis 主节点：

1. 记录当前时间 T1
2. 依次向 N 个实例发送 SET NX PX
3. 计算获取锁耗时 T2
4. 成功条件：① 多数派（≥ N/2+1）成功 ② T2 < 锁自动释放时间
5. 释放锁：向所有 N 个实例发送释放请求

| 优点 | 缺点 |
|------|------|
| 更高可靠性，容忍少数节点故障 | 架构复杂，成本高 |
| 解决主从切换锁丢失 | 性能开销大，延迟增加 |
| 依然非强一致 | 对系统时钟依赖性强 |

## 九、核心命题

> Redis 的"快"来自内存 + 单线程 + I/O 多路复用；"稳"来自主从/哨兵/Cluster 三级集群；"安全"来自 RDB+AOF 混合持久化 + 过期/淘汰策略 + 分布式锁。

8 大主题贯穿一条主线：**在性能与一致性之间做权衡**。旁路缓存选 AP+BASE，写穿透选 CP，写回选极致 AP，Redlock 在性能和可靠性间折中。理解这些权衡点，比记住命令更重要。
