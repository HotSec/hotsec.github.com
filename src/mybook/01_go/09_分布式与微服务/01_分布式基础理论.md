# 分布式基础理论

## ACID

数据库事务的四个特性：

- **Atomicity（原子性）**：事务中的所有操作，要么全部完成，要么全部不完成。如果有一个操作失败，整个事务回滚到开始前的状态。
- **Consistency（一致性）**：事务执行前后，数据库从一个一致性状态转换到另一个一致性状态。约束（外键/唯一键等）始终满足。
- **Isolation（隔离性）**：并发事务之间相互隔离。一个事务在提交前，其修改对其他事务不可见。
- **Durability（持久性）**：事务一旦提交，修改永久保存。即使系统崩溃，数据也不会丢失。

## CAP 定理

分布式系统最多只能同时满足以下三项中的两项：

- **Consistency（一致性）**：所有节点在同一时间看到的数据完全一致。
- **Availability（可用性）**：每个请求都能获得（非错误的）响应，但不保证数据最新。
- **Partition tolerance（分区容错性）**：系统在遇到网络分区故障时，仍能正常运作。

```
         C
        / \
       /   \
      /     \
     /  CA   \      CA：传统关系型数据库（MySQL 单机）
    /         \     CP：HBase / ZooKeeper / etcd
   A-----------P    AP：Cassandra / DynamoDB / CouchDB
```

> 网络分区不可避免，因此分布式系统必须在 CP 或 AP 之间做权衡。

## BASE 理论

对 CAP 中 AP 的延伸，牺牲强一致性换取可用性：

- **Basically Available（基本可用）**：系统故障时，核心功能可用，非关键功能可能降级。
- **Soft state（软状态）**：允许系统中的数据存在中间状态，数据副本同步存在延迟。
- **Eventually consistent（最终一致性）**：经过一段时间后，所有数据副本最终达到一致。

## 共识算法

### Paxos

Leslie Lamport 提出的经典共识算法。

**角色**：
- Proposer：提出提案
- Acceptor：批准提案
- Learner：学习已批准的提案

**两阶段提交**：
1. Prepare 阶段：Proposer 发送提案编号，Acceptor 承诺不再接受更小编号的提案
2. Accept 阶段：Proposer 发送提案值，Acceptor 接受并广播

### Raft

更易理解的共识算法，将共识分解为三个子问题：

- **Leader 选举**：通过心跳机制维持 Leader，Leader 失效时发起选举
- **日志复制**：Leader 接收客户端请求，将日志复制到 Follower
- **安全性**：保证所有节点具有相同的复制日志，确保最终状态一致

**Go 实现**：`hashicorp/raft`、`etcd/raft`

```go
import "github.com/hashicorp/raft"

config := raft.DefaultConfig()
config.LocalID = raft.ServerID("node1")

store := raft.NewInmemStore()
snapStore := raft.NewInmemSnapshotStore()
transport, _ := raft.NewTCPTransport(":7000", nil, 3, 10*time.Second, os.Stderr)

r, _ := raft.NewRaft(config, fsm, store, store, snapStore, transport)
```
