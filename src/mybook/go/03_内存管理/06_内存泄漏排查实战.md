# 内存泄漏排查实战

Go 有 GC，但仍可能发生内存泄漏。本文介绍常见泄漏场景和排查方法。

---

## 一、常见内存泄漏场景

### 1.1 Goroutine 泄漏

```go
func leak() {
    ch := make(chan int)
    go func() {
        <-ch
    }()
}
```

- goroutine 永远阻塞在 channel 上
- goroutine 持有的内存无法释放

排查方法：

```bash
pprof -http=:8080 http://localhost:6060/debug/pprof/goroutine
```

### 1.2 无限增长的切片/Map

```go
var cache = make(map[string][]byte)

func addToCache(key string, data []byte) {
    cache[key] = data
}
```

- 只增不减，内存持续增长
- 需要定期清理或使用 LRU 缓存

### 1.3 未关闭的资源

```go
func processFile(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }

    if someCondition {
        return errors.New("early return")
    }

    f.Close()
    return nil
}
```

修复：

```go
func processFile(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()

    if someCondition {
        return errors.New("early return")
    }
    return nil
}
```

### 1.4 字符串/切片引用

```go
func getSubstring(s string) string {
    return s[:100]
}
```

- 子字符串引用原字符串的底层数组
- 原字符串无法被 GC

修复：

```go
func getSubstring(s string) string {
    return strings.Clone(s[:100])
}
```

### 1.5 Finalizer 泄漏

```go
func setFinalizer(obj *Object) {
    runtime.SetFinalizer(obj, func(o *Object) {
        time.Sleep(time.Hour)
    })
}
```

- Finalizer 执行时间过长
- 对象无法被 GC

## 二、排查工具

### 2.1 pprof 内存分析

```go
import _ "net/http/pprof"

func main() {
    go func() {
        http.ListenAndServe("localhost:6060", nil)
    }()
}
```

访问分析页面：

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
go tool pprof -http=:8080 http://localhost:6060/debug/pprof/heap
```

常用命令：

```
(pprof) top10
(pprof) list functionName
(pprof) web
```

### 2.2 对比内存快照

```bash
curl -o heap1 http://localhost:6060/debug/pprof/heap
sleep 30
curl -o heap2 http://localhost:6060/debug/pprof/heap

go tool pprof -base heap1 heap2
```

### 2.3 runtime.ReadMemStats

```go
func printMemStats() {
    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    fmt.Printf("Alloc = %v MiB\n", m.Alloc/1024/1024)
    fmt.Printf("TotalAlloc = %v MiB\n", m.TotalAlloc/1024/1024)
    fmt.Printf("Sys = %v MiB\n", m.Sys/1024/1024)
    fmt.Printf("NumGC = %v\n", m.NumGC)
}
```

### 2.4 GODEBUG=gctrace=1

```bash
GODEBUG=gctrace=1 ./app
```

输出示例：

```
gc 1 @0.003s 0%: 0.018+0.23+0.003 ms clock, 0.14+0.11/0.23/0.043+0.024 ms cpu, 4->4->0 MB, 5 MB goal, 8 P
```

## 三、排查流程

### 3.1 确认泄漏

1. 监控内存使用趋势
2. 触发 GC 后观察内存是否下降
3. 对比不同时间点的堆快照

### 3.2 定位泄漏源

1. 使用 pprof 查看 top 分配
2. 分析对象类型和来源
3. 检查相关代码

### 3.3 常见检查点

- [ ] goroutine 数量是否持续增长
- [ ] 是否有未关闭的 channel
- [ ] 是否有未关闭的连接/文件
- [ ] 缓存是否有清理机制
- [ ] 是否有全局变量持续增长

## 四、案例分析

### 4.1 案例：时间定时器泄漏

```go
func bad() {
    for {
        select {
        case <-time.After(1 * time.Second):
            doSomething()
        }
    }
}
```

- 每次循环创建新的 `time.After` channel
- 旧的 timer 无法被 GC

修复：

```go
func good() {
    ticker := time.NewTicker(1 * time.Second)
    defer ticker.Stop()
    for {
        select {
        case <-ticker.C:
            doSomething()
        }
    }
}
```

### 4.2 案例：context 泄漏

```go
func bad(ctx context.Context) {
    ctx, cancel := context.WithTimeout(ctx, time.Hour)
    go func() {
        doWork(ctx)
    }()
}
```

- `cancel` 未被调用
- context 相关资源无法释放

修复：

```go
func good(ctx context.Context) {
    ctx, cancel := context.WithTimeout(ctx, time.Hour)
    defer cancel()
    go func() {
        doWork(ctx)
    }()
}
```

## 五、预防措施

1. **代码审查**：关注 goroutine 生命周期
2. **使用 defer**：确保资源释放
3. **设置超时**：避免无限等待
4. **监控告警**：内存/goroutine 数量异常告警
5. **压力测试**：模拟生产场景验证内存行为
