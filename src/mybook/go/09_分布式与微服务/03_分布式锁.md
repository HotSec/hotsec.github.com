# 分布式锁

在分布式系统中，多个服务实例可能同时访问共享资源，需要分布式锁来保证互斥访问。

---

## 一、分布式锁的核心要求

1. **互斥性**：同一时刻只有一个客户端持有锁
2. **安全性**：锁只能被持有者释放
3. **可用性**：锁服务不能成为单点故障
4. **容错性**：持有锁的客户端崩溃后锁能自动释放

---

## 二、Redis 分布式锁

### 2.1 基本实现（SET NX EX）

```go
func acquireLock(rdb *redis.Client, key string, value string, ttl time.Duration) (bool, error) {
    ctx := context.Background()
    result, err := rdb.SetNX(ctx, key, value, ttl).Result()
    return result, err
}
```

### 2.2 安全释放（Lua 脚本）

```go
var releaseScript = redis.NewScript(`
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end
`)

func releaseLock(rdb *redis.Client, key string, value string) (bool, error) {
    ctx := context.Background()
    result, err := releaseScript.Run(ctx, rdb, []string{key}, value).Int()
    return result == 1, err
}
```

- 使用 Lua 脚本保证 GET + DEL 的原子性
- value 使用唯一标识（UUID），防止误删其他客户端的锁

### 2.3 完整示例

```go
type RedisLock struct {
    rdb   *redis.Client
    key   string
    value string
    ttl   time.Duration
}

func NewRedisLock(rdb *redis.Client, key string, ttl time.Duration) *RedisLock {
    return &RedisLock{
        rdb:   rdb,
        key:   key,
        value: uuid.New().String(),
        ttl:   ttl,
    }
}

func (l *RedisLock) Lock(ctx context.Context) (bool, error) {
    return l.rdb.SetNX(ctx, l.key, l.value, l.ttl).Result()
}

func (l *RedisLock) Unlock(ctx context.Context) (bool, error) {
    result, err := releaseScript.Run(ctx, l.rdb, []string{l.key}, l.value).Int()
    return result == 1, err
}

func (l *RedisLock) TryLock(ctx context.Context, interval time.Duration) error {
    ticker := time.NewTicker(interval)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            ok, err := l.Lock(ctx)
            if err != nil {
                return err
            }
            if ok {
                return nil
            }
        }
    }
}
```

### 2.4 Redlock 算法

```go
func redLock(instances []*redis.Client, key, value string, ttl time.Duration) (bool, error) {
    quorum := len(instances)/2 + 1
    acquired := 0
    start := time.Now()

    for _, rdb := range instances {
        ok, err := rdb.SetNX(context.Background(), key, value, ttl).Result()
        if err == nil && ok {
            acquired++
        }
    }

    elapsed := time.Since(start)
    remaining := ttl - elapsed
    if remaining <= 0 {
        return false, nil
    }

    if acquired >= quorum {
        return true, nil
    }

    for _, rdb := range instances {
        releaseScript.Run(context.Background(), rdb, []string{key}, value)
    }
    return false, nil
}
```

- 使用 N 个（通常 5 个）独立的 Redis 实例
- 向所有实例请求加锁，获得过半数成功即为加锁成功
- 适用于对安全性要求极高的场景

## 三、etcd 分布式锁

### 3.1 基于 lease + revision

```go
import (
    "go.etcd.io/etcd/client/v3/concurrency"
)

func etcdLock() {
    cli, _ := clientv3.New(clientv3.Config{
        Endpoints: []string{"localhost:2379"},
    })
    defer cli.Close()

    session, _ := concurrency.NewSession(cli)
    defer session.Close()

    mutex := concurrency.NewMutex(session, "/my-lock/")

    if err := mutex.Lock(context.Background()); err != nil {
        log.Fatal(err)
    }
    defer mutex.Unlock(context.Background())

    doWork()
}
```

### 3.2 etcd 锁的优势

- 基于 Raft 共识，强一致性
- lease 机制自动过期释放
- revision 机制保证公平性（FIFO）
- 天然支持 watch，可监控锁状态

## 四、ZooKeeper 分布式锁

### 4.1 临时顺序节点

```text
/locks/resource-
  ├── /locks/resource-0000000001  ← 获得锁
  ├── /locks/resource-0000000002  ← 等待
  └── /locks/resource-0000000003  ← 等待
```

- 创建临时顺序节点
- 序号最小的获得锁
- 监听前一个节点的删除事件
- 客户端断开连接，临时节点自动删除

## 五、分布式锁对比

| 特性 | Redis | etcd | ZooKeeper |
|------|-------|------|-----------|
| 一致性 | 最终一致 | 强一致（Raft） | 强一致（ZAB） |
| 性能 | 高 | 中 | 低 |
| 公平性 | 非公平 | 公平 | 公平 |
| 自动续期 | 需自行实现 | lease 自动 | 临时节点自动 |
| 适用场景 | 高性能、允许极端情况丢失 | 强一致性要求 | 强一致性要求 |

## 六、自动续期

### 6.1 看门狗模式

```go
func (l *RedisLock) StartWatchdog(ctx context.Context) {
    ticker := time.NewTicker(l.ttl / 3)
    go func() {
        defer ticker.Stop()
        for {
            select {
            case <-ctx.Done():
                return
            case <-ticker.C:
                l.rdb.Expire(ctx, l.key, l.ttl)
            }
        }
    }()
}
```

- 每隔 TTL/3 时间续期一次
- 持有锁的客户端崩溃后，锁在 TTL 后自动释放
- 类似 Redisson 的看门狗机制

## 七、最佳实践

1. **锁的 TTL 要合理**：太短容易误释放，太长崩溃后等待太久
2. **释放锁要验证身份**：使用 Lua 脚本或唯一 value
3. **考虑锁的可重入**：同一线程/进程多次加锁
4. **设置获取锁超时**：避免无限等待
5. **业务操作要幂等**：锁可能因网络问题失效
