# 分布式理论

---

## 一、CAP 定理

```
┌─────────────────────────────┐
│         CAP 定理             │
│                             │
│    Consistency (一致性)      │
│         /\                  │
│        /  \                 │
│       /    \                │
│      /______\               │
│  Availability  Partition    │
│  (可用性)      Tolerance    │
│               (分区容错)     │
│                             │
│  最多同时满足 2 个           │
└─────────────────────────────┘
```

| 组合 | 说明 | 典型系统 |
|------|------|----------|
| CP | 一致性 + 分区容错 | ZooKeeper, etcd, HBase |
| AP | 可用性 + 分区容错 | Cassandra, DynamoDB, Eureka |
| CA | 一致性 + 可用性 | 单机数据库（无分区） |

> 分布式系统必须满足 P，所以实际选择只有 CP 和 AP。

## 二、BASE 理论

| 概念 | 说明 |
|------|------|
| **B**asically Available | 基本可用，允许响应时间增加或功能降级 |
| **S**oft State | 软状态，允许中间状态 |
| **E**ventually Consistent | 最终一致性，一段时间后达到一致 |

BASE 是 CAP 中 AP 的延伸，是大多数互联网系统的选择。

## 三、一致性模型

### 3.1 强一致性

```
Client A: Write(x=1) → 确认
Client B: Read(x) → 1 (立即可见)
```

### 3.2 最终一致性

```
Client A: Write(x=1) → 确认
Client B: Read(x) → 0 (暂时不可见)
         ... 延迟 ...
Client B: Read(x) → 1 (最终可见)
```

### 3.3 一致性模型层级

```
强一致性 (Linearizability)
    ↑
顺序一致性 (Sequential Consistency)
    ↑
因果一致性 (Causal Consistency)
    ↑
最终一致性 (Eventual Consistency)
```

## 四、共识算法

### 4.1 Raft

```
┌───────────┐  心跳  ┌───────────┐  心跳  ┌───────────┐
│  Leader   │──────→│ Follower  │←──────│ Follower  │
│           │       │           │       │           │
└───────────┘       └───────────┘       └───────────┘
      │                   ↑
      │  超时未收到心跳    │
      └─── 发起选举 ──────┘

角色:
- Leader: 处理所有写请求，同步日志
- Follower: 接收 Leader 日志，响应读请求
- Candidate: 选举中的 Follower

选举流程:
1. Follower 超时未收到心跳 → 变为 Candidate
2. 自增 term，投自己一票
3. 向其他节点请求投票
4. 获得多数票 → 变为 Leader

日志复制:
1. Client 写请求 → Leader
2. Leader 追加日志
3. Leader 将日志复制到 Follower
4. 多数 Follower 确认 → Leader 提交
5. 响应 Client
```

### 4.2 Paxos vs Raft

| 维度 | Paxos | Raft |
|------|-------|------|
| 理解难度 | 极高 | 较低 |
| 工程实现 | 困难 | 较易 |
| Leader | 无固定 Leader | 强 Leader |
| 日志顺序 | 可能乱序 | 严格有序 |
| 典型应用 | Google Chubby | etcd, Consul |

## 五、分布式 ID

### 5.1 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| UUID | 随机生成 | 简单 | 无序，存储空间大 |
| 数据库自增 | AUTO_INCREMENT | 有序 | 单点，性能瓶颈 |
| 号段模式 | 批量取号段 | 高性能 | 不严格递增 |
| 雪花算法 | 时间+机器+序列 | 有序，高性能 | 时钟回拨问题 |
| Redis | INCR | 高性能 | 依赖 Redis |

### 5.2 雪花算法

```
┌──────────────────────────────────────────────────┐
│ 1 bit  │    41 bits     │  10 bits  │  12 bits  │
│ 符号位  │   时间戳(ms)    │  机器ID   │  序列号    │
│   0    │  69年不重复     │ 1024台机器 │ 4096/ms   │
└──────────────────────────────────────────────────┘

每毫秒可生成 4096 个 ID
支持 1024 台机器
可用 69 年
```

## 六、分布式事务

### 6.1 两阶段提交 (2PC)

```
协调者              参与者A           参与者B
  │                    │                 │
  │─── Prepare ──────→│                 │
  │─── Prepare ────────────────────────→│
  │←── Yes ───────────│                 │
  │←── Yes ────────────────────────────│
  │─── Commit ───────→│                 │
  │─── Commit ────────────────────────→│
  │←── ACK ───────────│                 │
  │←── ACK ────────────────────────────│

问题: 同步阻塞、单点故障、数据不一致风险
```

### 6.2 TCC (Try-Confirm-Cancel)

```
Try:    预留资源（冻结金额）
Confirm: 确认操作（扣款）
Cancel:  取消操作（解冻）

示例：转账
Try:     A 冻结 100 元，B 准备接收
Confirm: A 扣除 100 元，B 增加 100 元
Cancel:  A 解冻 100 元，B 取消接收
```

### 6.3 Saga 模式

```
正向操作 + 补偿操作

T1(创建订单) → T2(扣款) → T3(扣库存) → 完成
                ↓ 失败
            C2(退款) → C1(取消订单)

两种编排:
- 编排式: 中心协调器控制流程
- 协同式: 事件驱动，各服务自行决定
```

### 6.4 本地消息表

```
1. 业务操作 + 写本地消息表（同一事务）
2. 后台任务扫描消息表
3. 发送消息到 MQ
4. 消费者处理 + 更新消息状态
5. 失败重试 + 幂等保证
```

## 七、分布式锁

### 7.1 Redis 分布式锁

```go
func AcquireLock(key string, ttl time.Duration) (bool, error) {
    return rdb.SetNX(ctx, "lock:"+key, uuid, ttl).Result()
}

func ReleaseLock(key string, uuid string) error {
    script := `
    if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
    else
        return 0
    end`
    rdb.Eval(ctx, script, []string{"lock:" + key}, uuid)
    return nil
}
```

### 7.2 etcd 分布式锁

```go
import "go.etcd.io/etcd/client/v3/concurrency"

session, _ := concurrency.NewSession(client)
mutex := concurrency.NewMutex(session, "/lock/my-resource")

mutex.Lock(ctx)
// 临界区
mutex.Unlock(ctx)
```

## 八、脑裂问题

```
网络分区导致:

┌──────────┐          ┌──────────┐
│ Node A   │    ✗     │ Node B   │
│ (Leader) │ ←─────→ │ (Leader) │
│          │  网络断开  │          │
└──────────┘          └──────────┘

两个 Leader 同时接受写入 → 数据不一致

解决:
1. 多数派投票 (Raft)
2. Fencing Token
3. 租约 (Lease)
```
