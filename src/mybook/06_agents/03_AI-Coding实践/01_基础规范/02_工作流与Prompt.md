# AI Coding — 工作流与 Prompt 工程

## AI 辅助编码工作流

### 0. 范式选择

AI Coding 不是单一工具形态，而是一组从低自主性到高自主性的开发范式。开始任务前先判断要用哪种范式，比直接写 Prompt 更重要。

| 范式 | 典型形态 | 适合场景 | 关键风险 |
|------|----------|----------|----------|
| 自动补全（Autocomplete） | GitHub Copilot Tab 补全 | 局部代码、样板代码、已知 API 调用 | 容易补出看似合理但不符合项目约束的代码 |
| 对话式辅助（Chat / Assisted Edit） | IDE Chat、局部编辑 | 解释代码、生成函数、修复小问题 | 上下文不足时容易误判架构意图 |
| 代理编程（Agentic Coding） | Claude Code、Codex、OpenCode、Aider | 多文件改动、测试修复、重构、端到端任务 | 任务边界不清会导致改动扩散 |
| 多代理编排（Multi-Agent Orchestration） | OMC、OmO、Team/Ultrawork 模式 | 大任务拆分、代码审查、并行验证 | 没有规范和验收标准时成本高、噪声大 |

推荐判断顺序：

1. **单行或局部模式明确**：用自动补全。
2. **需要解释、生成片段或比较方案**：用对话式辅助。
3. **需要读代码、改代码、跑测试形成闭环**：用代理编程。
4. **任务可拆成多个独立子任务，且需要规划/执行/审查分工**：用多代理编排。

### 0.1 Vibe Coding

Vibe Coding 强调用自然语言快速表达意图，让 AI 先产出可运行原型，再通过人工审查和测试收敛。它适合探索型场景：

- 快速验证 UI、交互或脚手架可行性
- 写一次性脚本、Demo、内部工具
- 需求尚未完全稳定，但需要看到东西再讨论

不适合直接用于高风险生产改动。进入生产代码前，必须补齐边界条件、错误处理、安全审查和测试验证。

### 0.2 Spec-Driven Development（SDD）

SDD 的核心是 **Spec 即 Prompt**：先把需求、接口、数据约束、验收标准写成结构化规范，再让 AI 按规范实现。它适合：

- 跨模块功能
- 需要兼容旧行为的改动
- 多 Agent 或长时间任务
- 团队协作下的可审查交付

最小流程：

1. 探索：只读代码，确认现状和约束。
2. 规划：写清目标、非目标、接口变化、验收标准。
3. 实现：按任务清单小步修改。
4. 验证：运行测试、构建、lint、关键手工场景。
5. 同步：把新约定写回 AGENTS.md、规范文档或项目 README。

### 1. 需求分析

```
Prompt: 分析以下需求，拆解为技术任务
需求：用户注册功能，支持邮箱和手机号注册
```

AI 输出：
- 数据模型设计（User 表）
- API 接口定义（POST /api/v1/auth/register）
- 参数验证规则
- 密码加密策略
- 邮箱/手机验证流程
- 错误码定义

### 2. 代码生成

```
Prompt: 根据 AGENTS.md 中的项目规范，实现用户注册功能
要求：
1. 使用 internal/handler, internal/service, internal/repo 分层
2. 参数验证使用 validator
3. 密码使用 bcrypt 加密
4. 返回标准错误码
```

### 3. 代码审查

```
Prompt: 审查以下代码，关注：
1. 安全漏洞（SQL注入、XSS等）
2. 错误处理是否完善
3. 是否符合项目编码规范
4. 性能问题
5. 可测试性
```

### 4. 测试生成

```
Prompt: 为以下函数生成表驱动测试，覆盖：
1. 正常路径
2. 边界条件
3. 错误路径
4. 并发安全
```

### 5. 文档生成

```
Prompt: 根据代码生成 API 文档，格式为 OpenAPI 3.0
```

## Agentic Coding 工作流

代理编程的工作流重点不是“让 AI 一次写完”，而是把 Agent 放进可验证的工程闭环里。

### 推荐闭环

1. **只读探索**：让 Agent 先读相关文件、测试、配置和历史约束，不立即改代码。
2. **明确验收**：要求输出目标、边界、风险点和验证命令。
3. **小步实现**：一次只改一个行为面，避免跨领域大改。
4. **本地验证**：运行项目指定测试、lint、构建或端到端脚本。
5. **审查差异**：用 `git diff` 检查是否有无关改动、重复代码、遗漏测试。
6. **沉淀规则**：如果同类问题重复出现，更新 AGENTS.md / CLAUDE.md / Rules。

### 多 Agent 编排

多 Agent 适合把复杂任务拆成规划、探索、实现、审查、验证等职责。典型分工：

| 角色 | 职责 | 输出 |
|------|------|------|
| Planner / Architect | 梳理需求、方案、依赖和风险 | 计划、设计、任务清单 |
| Explorer | 只读搜索代码库，回答具体问题 | 文件路径、现有模式、约束 |
| Executor | 按计划实现代码或文档 | 小范围补丁 |
| Reviewer / Critic | 找缺陷、遗漏、兼容性问题 | 审查意见 |
| Verifier | 运行测试和手工验证 | 验证结果、失败日志 |

使用多 Agent 前要先准备：清晰任务边界、文件所有权、验收标准、禁止回滚他人改动的规则。否则并行只会放大混乱。

### 范式选择决策框架

| 任务特征 | 推荐方式 |
|----------|----------|
| 只需要补全熟悉 API | 自动补全 |
| 需要理解一段代码或生成模板 | Chat / Assisted Edit |
| 涉及 2-10 个文件且能本地验证 | Agentic Coding |
| 涉及多个子系统、需要反复审查 | SDD + Agentic Coding |
| 任务可拆分且互不阻塞 | SDD + 多 Agent 编排 |
| 目标还不稳定，只想快速试错 | Vibe Coding，之后再规范化 |

## Prompt 工程最佳实践

### 结构化 Prompt

```
## 角色
你是一个 Go 后端开发专家

## 上下文
项目使用 Gin 框架，PostgreSQL 数据库

## 任务
实现 JWT 认证中间件

## 要求
1. 支持 Access Token + Refresh Token
2. Token 黑名单机制
3. 优雅的错误响应

## 输出格式
1. 完整代码
2. 单元测试
3. 使用示例
```

### 常用模式

| 模式 | 描述 | 示例 |
|------|------|------|
| Chain of Thought | 分步推理 | "一步步分析..." |
| Few-shot | 提供示例 | "参考以下示例..." |
| Role Play | 角色扮演 | "你是安全专家..." |
| Self-Critique | 自我审查 | "审查你的回答..." |
| Decomposition | 任务分解 | "将需求拆解为..." |

### 代码相关 Prompt 模板

**Bug 修复**：
```
## Bug 描述
[描述问题现象]

## 复现步骤
1. ...
2. ...

## 期望行为
[描述期望的正确行为]

## 相关代码
[粘贴代码]

请分析根因并修复。
```

**重构**：
```
## 重构目标
[描述重构目的]

## 当前代码
[粘贴代码]

## 约束
1. 不改变外部行为
2. 保持向后兼容
3. 提高可测试性

请重构并说明改动。
```

**性能优化**：
```
## 性能问题
[描述瓶颈]

## 当前实现
[粘贴代码]

## 性能指标
- 当前 QPS: 100
- 目标 QPS: 1000
- P99 延迟: 500ms → 50ms

请优化并解释原理。
```
