# 规范驱动开发框架综合指南

本文档整合了 OpenSpec 和 GitHub Spec Kit 两大规范驱动开发（SDD）框架，帮助开发者在写代码之前先建立清晰的规范和计划。

---

## 一、SDD 核心理念：权力反转

### 1.1 传统开发 vs SDD

| 维度 | 传统开发 | SDD |
|------|---------|-----|
| 真理之源 | 代码是唯一真相 | 规范是唯一真相 |
| 文档地位 | 脚手架，用完即弃 | 核心资产，持续维护 |
| 需求变更 | 手动传播到文档→设计→代码 | 修改规范→自动重新生成 |
| 开发者角色 | 敲代码的打字员 | 定义意图的设计师与指挥家 |

### 1.2 终结"氛围编程"

**氛围编程的灾难**：随口给 AI 几句提示词，几秒生成几千行代码 → 代码结构混乱、难以维护。

**SDD 的解法**：给 AI 提供边界和约束——在写代码之前，先将模糊想法转化为清晰、无歧义的结构化规范。

## 二、OpenSpec：轻量级 SDD 框架

### 2.1 项目定位

OpenSpec 是面向**棕地项目**的轻量级 SDD 框架，专为在已有代码基础上开发的团队设计。

### 2.2 核心工作流

```
提案（propose）→ 应用（apply）→ 归档（archive）
```

**详细流程**：
```
你：/opsx:propose add-dark-mode

AI 自动创建：
openspec/changes/add-dark-mode/
├── proposal.md ← 为什么要做？改变什么？
├── specs/      ← 需求规格和使用场景
├── design.md   ← 技术方案设计
└── tasks.md    ← 实现任务清单
```

### 2.3 OPSX 命令全景

| 命令 | 作用 |
|------|------|
| `/opsx:propose` | 一键创建变更 + 生成规划工件（默认快速路径） |
| `/opsx:explore` | 头脑风暴、调研问题、澄清需求 |
| `/opsx:new` | 启动新的变更脚手架（扩展工作流） |
| `/opsx:continue` | 创建下一个工件（扩展工作流） |
| `/opsx:apply` | 实现任务，按需更新工件 |
| `/opsx:verify` | 对照工件验证实现 |
| `/opsx:sync` | 同步增量规格到主规格 |
| `/opsx:archive` | 完成后归档 |

### 2.4 安装与使用

```bash
# 安装
npm install -g @fission-ai/openspec@latest

# 初始化项目
openspec init

# 快速规划
/opsx:propose add-dark-mode

# 执行实现
/opsx:apply

# 归档变更
/opsx:archive
```

## 三、GitHub Spec Kit：完整 SDD 工具集

### 3.1 项目定位

GitHub Spec Kit 是 GitHub 官方开源的完整 SDD 工具集，更适合**绿地项目**从零开始构建。

### 3.2 核心工作流

```
/speckit.constitution → /speckit.specify → /speckit.clarify → /speckit.plan → /speckit.tasks → /speckit.implement
```

### 3.3 工作流详解

| 阶段 | 命令 | 产出 |
|------|------|------|
| Constitution | `/speckit.constitution` | 项目治理原则和开发指南 |
| Specify | `/speckit.specify` | 功能规范（用户故事 + 验收标准） |
| Clarify | `/speckit.clarify` | 澄清模糊点（可选） |
| Plan | `/speckit.plan` | 技术实现计划 + API 契约 + 数据模型 |
| Tasks | `/speckit.tasks` | 可执行任务列表 |
| Implement | `/speckit.implement` | 代码实现 |

### 3.4 安装与使用

```bash
# 需要 uv
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@vX.Y.Z

# 初始化项目
specify init my-project --integration copilot
cd my-project

# 定义规范
/speckit.specify Build a photo album organizer

# 制定计划
/speckit.plan Vite + vanilla HTML/CSS/JS

# 执行实现
/speckit.implement
```

## 四、OpenSpec vs GitHub Spec Kit 对比

| 维度 | OpenSpec | GitHub Spec Kit |
|------|---------|----------------|
| 作者 | Fission AI | GitHub 官方 |
| 核心语言 | TypeScript | TypeScript |
| 适用场景 | 棕地项目（存量代码库） | 绿地项目（从零开始） |
| 工作流 | propose→apply→archive（轻量） | constitution→specify→plan→tasks→implement（完整） |
| 规格存储 | 代码库内 Git 管理 | specs/ 目录 |
| 扩展系统 | - | Extension + Preset |
| 哲学 | 流动、迭代、轻量 | 规范即代码、权力反转 |
| 成本优势 | 降低 75%-87% | 显著减少前期准备时间 |

## 五、SDD 六大核心原则

| 原则 | 含义 |
|------|------|
| 规范即通用语言 | 规范是首要产物，代码是其在特定语言/框架中的表达 |
| 可执行规范 | 规范必须精确、完整、无歧义，足以生成工作系统 |
| 持续精炼 | 一致性验证持续进行，不是一次性门控 |
| 研究驱动上下文 | 研究代理持续收集技术选项、性能影响、组织约束 |
| 双向反馈 | 生产现实反馈到规范演进 |
| 分支探索 | 从同一规范生成多种实现方案 |

## 六、实战示例：聊天功能

### 传统方式 vs SDD

| 步骤 | 传统方式 | SDD + Spec Kit |
|------|---------|----------------|
| 写 PRD | 2-3 小时 | 5 分钟 `/speckit.specify` |
| 设计文档 | 2-3 小时 | 5 分钟 `/speckit.plan` |
| 项目结构 | 30 分钟 | 自动生成 |
| 技术规范 | 3-4 小时 | 自动生成 |
| 测试计划 | 2 小时 | 自动生成 |
| **总计** | **~12 小时** | **~15 分钟** |

```bash
# SDD 工作流
/speckit.specify Real-time chat with message history
/speckit.plan WebSocket + PostgreSQL + Redis
/speckit.tasks
/speckit.implement
```

## 七、SDD 与其他方法论对比

| 维度 | Vibe Coding | TDD | BDD | SDD |
|------|------------|-----|-----|-----|
| 驱动源 | 随意 prompt | 测试用例 | 行为场景 | 结构化规范 |
| 核心产物 | 代码 | 测试代码 | Gherkin 特性文件 | spec.md + plan.md |
| AI 角色 | 代码生成器 | 辅助写测试 | 辅助写场景 | 规范编译器 |
| 一致性 | 低 | 中 | 中高 | 高 |
| 可追溯性 | 无 | 测试→代码 | 场景→代码 | 需求→计划→任务→代码 |
| Pivot 成本 | 极高 | 高 | 中 | 低 |

## 八、适用场景与注意事项

### 8.1 适用人群

- **全栈开发者**：需要快速实现完整功能模块
- **技术团队负责人**：希望统一团队的 AI 协作规范
- **个人开发者**：想要提升单兵作战效率
- **开源项目维护者**：需要规范贡献流程

### 8.2 挑战与局限

1. **规范质量决定一切**：垃圾规范 → 垃圾代码
2. **过度规范的风险**：规范太细等于用自然语言写代码
3. **现有代码库适配难**：SDD 最适合 Greenfield 项目
4. **团队文化转变**：从"代码为王"到"规范为王"
5. **AI 生成代码审查**：仍需人类审查逻辑完整性和安全性

---

## 九、最佳实践建议

1. **从最小规范开始**：不要一开始就写几百行规范
2. **规范必须可验证**：每个用户故事要有验收条件
3. **保持规范更新**：规范需要与代码同步演进
4. **善用工具集成**：将 SDD 工具与 CI/CD 流水线集成
5. **定期审查规范**：团队定期回顾和优化规范质量
