# Claude Code 源码架构

> 来源：[面试官："简历写着用过 Claude Code，那源码看过吗？"](https://mp.weixin.qq.com/s/qGfSdDEjzKM6zrtaPBM-7w)

Claude Code 是 Anthropic 官方推出的编程 Agent 工具，因 npm 打包配置失误导致 51 万行核心源码泄漏。本文基于泄漏源码，深入剖析其架构设计、Agent 工作模式、System Prompt 构造、记忆系统和上下文管理机制。

---

## 一、Claude Code 是什么

Claude Code 是一个能直接在终端里干活的 AI 程序员，能读代码、改文件、跑命令、管理 Git。

其本质是一个 **AI Agent**，与 ChatBot 和 Copilot 的区别：

| 类型 | 模式 | 特点 |
|------|------|------|
| ChatBot | 一问一答 | 一次性问答 |
| Copilot | 补全建议 | 一次性预测 |
| Agent | 感知-决策-行动循环 | 自主决定工具调用，循环直到任务完成 |

Agent 循环的关键：**大模型自己决定下一步做什么**，不是按预定义流程图走，而是每次看到当前对话上下文后自主判断。

## 二、四层分层架构

```
┌─────────────────────────────────────────┐
│         安全与治理层（横切所有层）          │
│  权限系统 / Hook系统 / Bash安全模块       │
├─────────────────────────────────────────┤
│              引擎层（大脑）               │
│  协调 → 分发 → 决策                      │
├─────────────────────────────────────────┤
│              工具层（能力）               │
│  40+ 工具，每个工具强制定义3个安全属性      │
├─────────────────────────────────────────┤
│              服务层（基础设施）            │
│  API调用 / 上下文压缩 / MCP协议           │
└─────────────────────────────────────────┘
```

### 2.1 引擎层

Agent 的「大脑」，关键原则：**不包含任何业务逻辑**。只做三件事：

1. **协调**：把用户输入、系统指令、历史对话拼在一起，发给大模型
2. **分发**：大模型说「我要用某个工具」时，找到对应工具并执行
3. **决策**：根据大模型返回决定是继续循环还是结束对话

设计好处：**新增能力只需新增工具，引擎层完全不用改**

### 2.2 工具层

40 多个工具，每个工具遵循统一规范，强制定义三个安全属性（类型系统强制要求，漏了编译不过）：

| 属性 | 含义 |
|------|------|
| 只读/可写 | 这个工具是只读的还是会改东西的？ |
| 破坏性 | 是否具有破坏性需要额外确认？ |
| 并发安全 | 能不能和其他工具同时执行？ |

**每一把刀都有刀鞘，从出厂就配好了安全机制。**

### 2.3 服务层

所有层共享的「基础设施」：

- **API 调用**：主循环、子 Agent 都走这一层
- **上下文压缩**：五步压缩策略
- **MCP 协议**：和外部工具服务器通信的标准接口

### 2.4 安全与治理层

像安全网罩在所有层上面：

- **权限系统**：决定哪些操作需要用户确认
- **Hook 系统**：工具执行前后插入自定义行为
- **Bash 安全模块**：对 Shell 命令做语法级分析，检测命令注入、路径逃逸

## 三、Agent 工作模式：Tool-Use Loop

Claude Code **没有用 ReAct**，而是用了更简洁的 **Tool-Use Loop**。

### 3.1 ReAct 的问题

ReAct（Reasoning + Acting）每一步拆成 Thought → Action → Observation 三阶段：

| 问题 | 说明 |
|------|------|
| Token 浪费 | 每轮输出 Thought 文本，50 轮累计好几万 Token |
| 应用层复杂 | 需要解析模型输出区分 Thought/Action，格式不标准就崩 |
| 为弱模型设计 | 强模型推理能力足够，不需要显式 Thought |

### 3.2 Tool-Use Loop

核心就是一个 `while(true)` 循环：

```
while (true) {
    1. 压缩上下文（五步从轻到重）
    2. 调用大模型 API，流式接收
    3. 分析模型返回：
       - end_turn → 跳出循环，返回结果
       - tool_use → 执行工具，更新 state，继续循环
}
```

核心哲学：**信任模型的推理能力，保持应用层框架尽可能简单**

- 模型通过 **Extended Thinking** 在内部完成推理（不占上下文空间）
- API 原生支持 `tool_use`，不需要正则解析
- `end_turn` 作为天然终止信号

### 3.3 ReAct vs Tool-Use Loop 对比

| 维度 | ReAct | Tool-Use Loop |
|------|-------|---------------|
| 推理方式 | 显式 Thought 文本 | 模型内部 Extended Thinking |
| 工具调用 | 解析文本提取 Action | API 原生 tool_use |
| 终止判断 | 检测 "Final Answer" | API 原生 end_turn |
| Token 开销 | 每轮输出 Thought | 无额外开销 |
| 编排复杂度 | 高 | 低（只需 if/else） |
| 适合场景 | 弱模型 + 简单工具 | 强模型 + 复杂工具集 |

### 3.4 Plan Mode

复杂任务先规划再执行，通过 `EnterPlanMode` / `ExitPlanMode` 两个工具实现：

1. **模型自主进入或用户手动触发**（Shift+Tab）
2. **只读探索 + 设计方案**：权限降为只读，只能用 Read/Grep/Glob，计划写入 `.claude/plans/`。每 5 轮系统提醒「你还在 Plan Mode」
3. **用户审批后实施**：`ExitPlanMode` 需要用户确认

设计精髓：**工具即能力** — Plan Mode 不是模式切换，只是调用了两个工具，引擎层不需要任何特殊处理。

## 四、System Prompt 的构造

System Prompt 是**动态组装**的，由十几个 Section 拼接，并做了精巧的**缓存优化**。

### 4.1 角色定义与安全红线

```
你是一个交互式代理（interactive agent），帮助用户完成软件工程任务。
重要：你绝对不能为用户生成或猜测 URL，除非你确信这些 URL 是为了帮助用户完成编程任务。
```

关键点：定位为 `interactive agent`（暗示主动行动），立刻划安全红线。

安全约束用「先肯定再约束」写法：

```
允许协助已授权的安全测试、防御性安全研究、CTF 挑战赛和教育场景。
拒绝涉及破坏性技术、DoS 攻击、大规模目标扫描、供应链攻击。
```

### 4.2 行为准则（精华）

**修改代码前先阅读**：

> 不要对你没有阅读过的代码提出修改建议。先读一遍，理解现有代码。

**代码风格：少即是多**：

> 不要在用户要求之外添加功能、重构代码或进行"改进"。三行相似的代码比一个过早的抽象更好。

**失败处理：先诊断再换方案**：

> 先诊断原因再决定是否换方案。不要盲目重试，也不要因为一次失败就放弃。

### 4.3 操作安全

用**可逆性**和**影响范围**两个维度判断风险：

| 维度 | 低风险（直接放行） | 高风险（需确认） |
|------|------|------|
| 可逆性 | 编辑文件、运行测试 | 删除文件、force-push、reset --hard |
| 影响范围 | 只影响本地 | 推送代码、创建/关闭 PR、上传第三方 |

**授权是一次性的、有范围的**：用户批准一次 git push 不代表以后都自动 push。

### 4.4 工具使用指南

> 当有专用工具可用时，不要用 Bash 来执行命令。

| 操作 | 用专用工具 | 不用 Bash |
|------|------|------|
| 读取文件 | Read | 不用 cat/head/tail |
| 编辑文件 | Edit | 不用 sed/awk |
| 创建文件 | Write | 不用 echo 重定向 |
| 搜索文件 | Glob | 不用 find/ls |
| 搜索内容 | Grep | 不用 grep/rg |

原因：**可审查性** + 专用工具有权限检查。

### 4.5 Git 安全协议

- 绝不修改 git config
- 绝不执行破坏性命令（push --force、reset --hard、checkout .、clean -f）
- 绝不跳过 hooks（--no-verify）
- 绝不 force push 到 main/master
- **始终创建新 commit，不用 --amend**（pre-commit hook 失败时 commit 没发生，--amend 会修改上一个不相关的 commit）

### 4.6 输出风格约束

> 工具调用之间的文字不超过 25 个词。最终回复不超过 100 个词。

25 词限制避免 Agent 话痨。

### 4.7 分割线与三级缓存

System Prompt 组装时插入分割标记 `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__`：

```
┌─────────────────────────────────────────────┐
│ [角色定义] [安全红线] [行为准则] [操作安全]    │ ← 所有用户完全一样
│ [工具使用] [Git安全] [输出风格]               │ ← 全局缓存
├──── __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__ ─────┤
│ [环境信息] [CLAUDE.md] [记忆指令] [MCP指令]   │ ← 每个用户不一样
└─────────────────────────────────────────────┘
```

**三级缓存体系**：

1. **全局缓存**：分割线之上，跨组织跨用户共享（费用降低 90%）
2. **组织缓存**：同一组织内跨会话共享
3. **会话缓存**：同一 Section 在一次会话内只计算一次

### 4.8 System Prompt 设计三原则

1. **先给范围再画红线**：先说「可以做 X」，再说「不能做 Y」
2. **用两个维度把风险分出层次**：可逆性 + 影响范围
3. **静态内容和动态内容用分割线隔开**：全球共享缓存，省 90% 费用

## 五、记忆系统

### 5.1 为什么不用向量数据库？

Agent 需要记住的大部分不是「相似的文档片段」，而是「用户说过'不要 mock 数据库'」这种**结构化的行为指令**。向量相似度检索这类指令效果很差。

### 5.2 四类型分类

```typescript
export MEMORY_TYPES = [
  'user',      // 用户画像：角色、偏好、知识水平
  'feedback',  // 行为反馈：该做什么、不该做什么
  'project',   // 项目动态：在做什么、截止日期、协作信息
  'reference', // 外部指针：哪里能找到什么信息
] as const
```

只有四种，**不能随便加新的**。限定类型逼 Agent 做分类决策，防止记忆膨胀成垃圾堆。

**Feedback 类型**要求记录三要素：

- **规则本身**：集成测试必须使用真实数据库
- **Why**：上季度 mock 测试全部通过但生产环境迁移失败了
- **How to apply**：在这个模块写测试时，始终连接真实数据库

**Project 类型**特殊要求：必须把相对日期转成绝对日期（「周四」→「2026-03-05」）。

### 5.3 排除清单

**可以从当前代码推导出来的信息，一律不存**：

- 代码模式、项目架构和文件结构（grep/git/CLAUDE.md 可获取）
- Git 历史和最近改动（git log/git blame 是权威来源）
- 调试方案和修复方法（修复已在代码里）
- CLAUDE.md 里已写的内容（避免重复）
- 临时任务状态和当前对话上下文（会话级信息）

核心原则：代码是「活的」，记忆是「死的」，过时的记忆比没有记忆更糟糕。

### 5.4 存储：索引 + 独立文件

每条记忆存为独立 `.md` 文件，开头有 YAML 元信息：

```yaml
---
name: no-mock-database
description: 集成测试必须使用真实数据库，不能用 mock
type: feedback
---
```

`MEMORY.md` 作为索引（不超过 200 行 / 25KB），始终加载到 System Prompt，独立记忆文件**按需加载**。

### 5.5 召回：Sonnet 当秘书

三步流程：

1. **扫描头部信息**：只读每个文件前 30 行（提取 frontmatter），按修改时间排序，最多 200 个
2. **Sonnet 做选择**：把清单 + 用户问题发给 Sonnet，返回最多 5 条相关记忆的文件名
3. **加载选中记忆**：读取完整内容，注入当前对话

**陈旧度检测**：超过 1 天的记忆自动附加警告，提醒模型先验证再引用。

**并行预取**：Sonnet 侧查询在用户提交消息后立刻开始，与主模型 API 调用并行执行，几乎不增加额外延迟。

### 5.6 记忆系统三句话总结

1. **记该记的，不记能推导的**：四类型封闭集合 + 排除清单
2. **存索引，按需加载详情**：MEMORY.md 常驻，具体内容按需加载
3. **用小模型做秘书，大模型做决策**：Sonnet 并行预取，Opus 做决策

## 六、上下文窗口管理（五步压缩）

核心理念：**压缩一定有信息损失，能不压就不压，必须压时从最轻的手段开始**。

| 层级 | 手段 | 信息损失 | API开销 |
|------|------|---------|---------|
| 第1层 | 大结果存磁盘 | 几乎无 | 零 |
| 第2层 | Snip 砍远古消息 | 少量 | 零 |
| 第3层 | Micro-Compact 时间衰减 | 少量 | 零 |
| 第4层 | Context Collapse 读时投影 | 中等 | 零 |
| 第5层 | Auto-Compact 全量摘要 | 最大 | 一次API调用 |

大部分场景前三层就够用，根本不需要触发昂贵的全量摘要。

### 6.1 第1层：大结果存磁盘

单个工具结果超过约 50KB → 完整内容写磁盘，消息里只留 2KB 预览。同一条消息所有工具结果总量还有 200KB 上限。

完整内容没丢，模型需要时可再次 Read。

### 6.2 第2层：Snip 砍远古消息

直接删掉对话开头的旧消息，插入边界标记。不做摘要，零 API 开销。释放的 token 数传给第5层，避免重复压缩。

### 6.3 第3层：Micro-Compact 时间衰减

距离上次 API 调用超过约 60 分钟时触发。清空「可重新获取」的工具结果（Read/Bash/Grep/Glob/Edit/Write），保留最近 5 个。子 Agent 输出、Task 状态等不可重复的结果绝不裁剪。

### 6.4 第4层：Context Collapse 读时投影

上下文达到 90% 时触发，95% 时升级。**不修改原始消息**，只在调用 API 时动态计算压缩视图。原对话历史在本地完整保留。

### 6.5 第5层：Auto-Compact 全量摘要

上下文达到 ~93%（上限减 13K）时触发，把整段对话全送进摘要器重写一份。配套做文件恢复、缓存清理、消息重组。

> 详细的 Auto-Compact 机制请参阅 [Claude Code 上下文管理](./10_ClaudeCode上下文管理.md)
