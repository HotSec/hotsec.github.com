## 五、提示词工程（AI 编程专用）

### 5.1 五大核心原则

| 原则 | 说明 | 示例 |
|------|------|------|
| 具体 > 模糊 | AI 不会读心术 | "处理 10 万条数据时从 30 秒降到 5 秒" |
| 约束 > 自由 | 明确告诉它什么不要做 | "用内存缓存，不要引入 Redis" |
| 分步 > 一次 | 复杂任务拆成步骤 | "先分析问题→给方案→确认后改代码" |
| 示例 > 描述 | 给一个例子比描述半天清楚 | 给出返回值 JSON 格式示例 |
| 参考 > 从零开始 | 指向已有代码比描述风格有效 | "参考 users.ts 的风格写 orders.ts" |

### 5.2 四种常用模式

| 模式 | 模板 |
|------|------|
| 分析模式 | 先读 [文件]，分析 [问题]，列出发现，不要改代码，等确认 |
| 实现模式 | 在 [位置] 实现 [功能]，要求 1/2/3，参考 [文件]，不要 [禁止] |
| 修复模式 | [错误日志]，先分析原因，确认根因后给方案，只改必要代码 |
| 审查模式 | 审查 [文件]，重点关注性能/安全/边界，按严重程度排序 |

### 5.3 反模式

| 反模式 | 问题 | 改成 |
|--------|------|------|
| "帮我写个网站" | 范围太大 | 拆成具体任务 |
| "优化一下" | 优化什么？ | 说清优化目标和指标 |
| "写最好的代码" | "最好"没定义 | 说清标准 |
| 一次给 10 个需求 | AI 顾此失彼 | 一次一个，做完确认 |
| 不给错误信息就说"修 bug" | AI 只能猜 | 贴上错误日志、复现步骤 |

## 六、AI 编程安全注意事项

> AI 写的代码可能包含安全漏洞。不是因为 AI 故意写不安全的代码，而是它倾向于"先让功能跑起来"，安全性往往不是它的第一优先级。

### 6.1 高频风险

| 风险 | AI 常犯错误 | 正确做法 |
|------|-----------|---------|
| 敏感信息硬编码 | `const API_KEY = "sk-xxx"` | `process.env.API_KEY` |
| SQL 注入 | `WHERE name = '${name}'` | 参数化查询 `$1` |
| 缺少权限校验 | 删除接口无 auth | 加 authMiddleware + 角色检查 |
| 敏感数据日志泄露 | `console.log({email, password})` | 脱敏打印 `password: '***'` |

### 6.2 安全规则模板（加到 CLAUDE.md / .cursorrules）

```
## 禁止
- 不要硬编码密钥、密码、token
- 不要在日志中打印敏感数据
- 不要把用户输入直接拼接到 SQL/Shell 命令中
- 不要禁用 HTTPS 验证
- 不要在前端存储敏感 token（用 httpOnly cookie）

## 必须
- 所有接口必须有权限校验
- 用户输入必须做参数校验和转义
- 文件上传必须校验类型和大小
- 密码必须 hash 存储（bcrypt/argon2）
- API 必须有速率限制
```

### 6.3 AI 代码安全审查 Prompt

```
扫描整个 src/ 目录，按 OWASP Top 10 检查：
1. 注入 2. 失效的身份认证 3. 敏感数据暴露
4. XML 外部实体 5. 失效的访问控制 6. 安全配置错误
7. 跨站脚本（XSS） 8. 不安全的反序列化
9. 使用含已知漏洞的组件 10. 不足的日志和监控

每个问题给出：文件位置、风险等级、修复建议。
```

## 八、核心命题

> 工具会换代，方法论永生。这套书的结构是：先教你方法，再用工具佐证。

三卷书的递进逻辑——入门选工具 → 工作流组合工具 → 架构接进团队——本质上是从"个人效率"到"团队治理"的升级路径。10 款工具的能力矩阵和 30 秒决策表解决了"选什么"的问题，5 条提示词原则和 4 种模式解决了"怎么用"的问题，安全规则和 OWASP 审查解决了"用得安不安全"的问题。
