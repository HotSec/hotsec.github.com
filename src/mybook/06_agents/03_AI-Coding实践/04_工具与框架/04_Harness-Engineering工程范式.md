# Harness Engineering 工程范式

## 一、概念定义

**Harness Engineering**（驾驭工程）是由 Mitchell Hashimoto（HashiCorp 联合创始人）在 2025-2026 年提出的 AI 工程新范式。

> 核心观点：软件工程师的角色从"编写代码"转变为 **"设计让 AI Agent 可靠运行的环境"**。

这不是简单的 Prompt Engineering 升级，而是一次根本性的范式转换：

| 维度 | 传统软件工程 | Harness Engineering |
|------|------------|-------------------|
| 工程师角色 | 代码编写者 | 环境设计者 |
| 核心产出 | 源代码 | 约束与工具 |
| 质量保证 | Code Review | 验证与过滤层 |
| 扩展方式 | 增加人力 | 增加Agent |
| 错误处理 | 人工修复 | 自修正机制 |

## 二、六大核心组件

### 2.1 Tool Layer（工具层）

为 AI Agent 提供可调用的工具集，定义 Agent 能做什么。

```
┌─────────────────────────────┐
│        AI Agent             │
│  ┌─────┐ ┌─────┐ ┌─────┐  │
│  │Tool1│ │Tool2│ │Tool3│  │
│  └─────┘ └─────┘ └─────┘  │
│      ↓       ↓       ↓     │
│  ┌─────────────────────┐   │
│  │   Tool Interface    │   │
│  └─────────────────────┘   │
└─────────────────────────────┘
```

设计原则：
- **最小权限**：每个工具只暴露必要的操作
- **幂等性**：重复调用产生相同结果
- **可观测**：每次调用有明确输入输出
- **可组合**：工具之间可串联完成复杂任务

### 2.2 Memory / Context（记忆与上下文）

管理 Agent 的短期工作记忆和长期知识积累。

| 类型 | 作用 | 示例 |
|------|------|------|
| 工作记忆 | 当前任务上下文 | PRD、代码变更、测试结果 |
| 情景记忆 | 历史经验 | 过去的修复方案、常见陷阱 |
| 语义记忆 | 领域知识 | 架构规范、编码标准 |

关键挑战：**上下文窗口有限**，需要智能压缩和检索策略。

### 2.3 Architectural Constraints（架构约束）

通过代码层面的约束确保 Agent 不会偏离架构设计。

实现方式：
- **类型系统**：利用编译器约束 Agent 行为
- **Lint 规则**：自动检查代码风格和模式
- **架构决策记录（ADR）**：Agent 必须遵守的架构规则
- **依赖边界**：限制模块间的依赖关系

```
Agent 生成代码
    ↓
架构约束检查
    ├── 类型检查 ✓ → 通过
    ├── 依赖边界 ✓ → 通过
    └── Lint 规则 ✗ → 拒绝 + 反馈
```

### 2.4 Task Orchestration（任务编排）

将复杂项目分解为可管理的子任务，编排 Agent 的执行顺序。

编排模式：
- **串行编排**：任务按顺序执行，前一步输出是后一步输入
- **并行编排**：独立任务同时执行，最后合并
- **条件编排**：根据中间结果决定后续路径
- **递归编排**：大任务分解为子任务，子任务可继续分解

### 2.5 Validation / Filtering（验证与过滤）

在 Agent 产出进入代码库前进行质量把关。

```
Agent 产出
    ↓
┌──────────────┐
│ 自动化测试     │ → 失败 → 反馈给 Agent 修复
├──────────────┤
│ 静态分析       │ → 失败 → 反馈给 Agent 修复
├──────────────┤
│ 安全扫描       │ → 失败 → 拒绝
├──────────────┤
│ 人工抽检       │ → 失败 → 人工干预
└──────────────┘
    ↓ 通过
合并到代码库
```

多层过滤确保：
- 第一层：自动化测试（快速反馈）
- 第二层：静态分析（代码质量）
- 第三层：安全扫描（安全合规）
- 第四层：人工抽检（最终把关）

### 2.6 Self-Correction / Entropy Management（自修正与熵管理）

Agent 在执行过程中自我修正，管理系统熵增。

**熵的来源**：
- 代码漂移：Agent 修改超出预期范围
- 上下文污染：错误信息累积导致决策偏移
- 依赖膨胀：引入不必要的依赖
- 一致性退化：风格和模式逐渐不一致

**熵管理策略**：
- **定期重置**：清理上下文，从干净状态继续
- **增量验证**：每步操作后验证整体一致性
- **回滚机制**：检测到严重偏移时回退到已知良好状态
- **约束收紧**：随着项目复杂度增加，收紧约束

## 三、OpenAI 百万行零人工代码实验

OpenAI 进行了一个里程碑实验：**100 万行代码的项目，零人工编写**。

### 3.1 实验设计

```
项目规模：~1,000,000 行代码
人工参与：0 行手写代码
Agent 数量：多个专业化 Agent
工程方法：Harness Engineering
```

### 3.2 关键发现

1. **环境设计比 Prompt 更重要**：精心设计的工具和约束比精巧的 Prompt 更有效
2. **验证层是核心**：没有验证层的 Agent 系统不可靠
3. **熵管理决定上限**：项目越大，熵管理越关键
4. **人类角色转变**：从写代码变为审查和调整环境

### 3.3 启示

- Harness Engineering 不是理论，而是已被验证的实践
- 大规模 AI 编码的关键不在于 AI 能力，而在于工程环境的设计
- 未来的软件工程师需要掌握"环境设计"这项核心技能

## 四、与其他范式的对比

| 范式 | 关注点 | 人类角色 | 适用规模 |
|------|--------|---------|---------|
| Prompt Engineering | 输入优化 | 指令编写者 | 单次交互 |
| Agentic Coding | 自主执行 | 监督者 | 中小项目 |
| Harness Engineering | 环境设计 | 环境架构师 | 大规模项目 |

三者不是替代关系，而是递进关系：
- Prompt Engineering 是基础技能
- Agentic Coding 是执行模式
- Harness Engineering 是系统级方法论

## 五、实践指南

### 5.1 评估项目是否适合 Harness Engineering

- [ ] 项目规模 > 10 万行代码
- [ ] 有完善的自动化测试体系
- [ ] 有明确的架构规范
- [ ] 需要多 Agent 协作
- [ ] 有持续集成/部署流水线

满足 3 个以上条件，建议采用 Harness Engineering 方法论。

### 5.2 实施步骤

1. **定义工具层**：梳理 Agent 需要的操作，封装为工具
2. **建立验证层**：从测试、静态分析、安全扫描三个维度建立过滤
3. **设计架构约束**：用类型系统、Lint、ADR 约束 Agent 行为
4. **实现熵管理**：建立上下文清理和回滚机制
5. **编排任务流**：将项目分解为 Agent 可执行的子任务
6. **持续优化**：根据 Agent 表现调整环境和约束

### 5.3 常见陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|---------|
| 过度约束 | Agent 无法完成任务 | 逐步放宽约束，找到平衡点 |
| 验证不足 | 低质量代码入库 | 增加验证层，提高覆盖率 |
| 忽略熵管理 | 项目后期质量下降 | 定期重置、增量验证 |
| 工具设计不当 | Agent 频繁调用错误工具 | 简化工具接口，明确文档 |
