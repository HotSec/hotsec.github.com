# 哔哩哔哩 AI 智能开发工作流

## 一、背景与动机

B站前端团队从 **Prompt Engineering** 演进到 **Harness Engineering**，构建了一套覆盖整个研发生命周期的智能开发工作流。

### 1.1 核心痛点

| 痛点 | 表现 |
|------|------|
| 节点零散 | AI 能帮忙补全代码、调试、测试，但各节点分散，需要开发者自行选择使用 |
| 流程不统一 | 不同开发者用不同 AI 方案，没有统一工具串联 TAPD → 提测全链路 |
| 缺乏标准化 | 没有标准化流程推动所有人高效利用 AI |

### 1.2 设计目标

- **简单工作**：AI 无需人工介入，从头到尾自主完成
- **复杂工作**：标准化流程，开发者在固定节点使用 AI，充分利用 AI 加速

### 1.3 核心方法论：模仿 + 拆解

> 模仿真实开发流程，拆解为 AI 可执行的步骤。

产品出 TAPD → 需求评审对齐 → 技术方案对齐 → 写代码，这个流程被拆解为 AI 可执行的子步骤，形成标准化工作流。

## 三、.workflow 知识库

### 3.1 为什么需要项目知识库？

AI 虽然能理解代码，但缺少对项目整体的结构化认知：

| 问题 | 说明 |
|------|------|
| 缺乏项目全貌 | AI 每次对话都是全新开始，不知道项目的技术栈、目录结构、编码规范 |
| 无法复用经验 | 之前的分析结果无法持久化，每次都需要重新分析 |
| 上下文受限 | 无法一次读取所有项目文件来建立完整认知 |
| 规范不一致 | 生成的代码可能与项目现有风格不一致 |

### 3.2 知识库架构

```
.workflow/
├── knowledge/               # 项目知识
│   ├── business.md          # 业务模块划分
│   ├── api.md               # API 调用规范
│   ├── components.md        # 组件清单与用法
│   └── index.md             # 知识库总览
├── rules/                   # 规则约束
│   ├── tech-stack.md        # 技术栈约束
│   ├── code-style.md        # 编码风格
│   └── naming.md            # 命名约定
├── template/                # 代码模板
├── tech/                    # 技术方案存档
├── archive/                 # 历史需求归档（用于 RAG 搜索）
└── temp/                    # 临时文件
    └── d2c/                 # D2C 中间产物
```

### 3.3 知识库与开发流程的协作

**prd-preprocess 使用知识库**：
```
prd-preprocess:
  ├─→ knowledge/business.md  → 理解业务模块划分，识别涉及模块
  ├─→ knowledge/components.md → 了解现有组件，避免重复开发
  ├─→ rules/tech-stack.md    → 确认技术栈约束
  └─→ 输出: 结构化 PRD + 技术可行性分析
```

**dev-workflow-plan 使用知识库**：
```
dev-workflow-plan:
  ├─→ knowledge/api.md       → 遵循 API 调用规范生成代码
  ├─→ knowledge/components.md → 复用现有组件，遵循 CSS 变量
  ├─→ rules/code-style.md    → 生成符合项目规范的代码
  ├─→ rules/naming.md        → 遵循命名约定
  ├─→ template/ (匹配模板)    → 基于模板生成代码
  └─→ 输出: 符合项目规范的代码
```

**archive 使用知识库**：
```
archive:
  ├─→ tech/ 目录             → 收集该需求的所有技术方案
  └─→ 输出: 整合到 archive/  → 归档文档成为知识库的一部分
                               可被 RAG 搜索用于后续开发
```

### 3.4 知识库命令

| 命令 | 作用 | 用法 |
|------|------|------|
| `workflow-init` | 深度分析项目，生成完整 `.workflow/` 知识库 | `mcp__bgent__bili-fe-workflow-init` |
| `knowledge-update` | 增量更新指定知识库文件 | `mcp__bgent__bfw-knowledge-update knowledgeFile=".workflow/knowledge/api.md"` |

**更新策略**：
- **内置知识库**：使用特定分析指令，确保分析质量一致
- **自定义知识库**：使用通用更新流程，根据文档内容确定分析范围

## 四、需求文档澄清（prd-preprocess）

### 4.1 为什么需要预处理？

原始 PRD 无法直接用于开发：

1. PRD 以产品视角描述，无法直接映射到代码模块
2. PRD 需要需求评审来进一步澄清补充
3. 涉及多项目（PC、H5、后端）时需要提取当前项目改动
4. 前端开发需要交互稿、视觉稿、后端技术方案
5. 需求评审的讨论内容往往不落实成文档，AI 无法获取

### 4.2 执行流程（四阶段）

```
阶段一：资源获取
  └─→ 收集 PRD、设计稿链接、技术方案文档

阶段二：分析需求与代码
  ├─→ 提取需求（四维度：界面改动/功能改动/交互改动/数据改动）
  └─→ 分析涉及代码
      ├─→ RAG 知识库搜索（查找历史相关需求）
      └─→ Explore/Glob/Grep 代码筛查
      输出五方向：主页面/相关组件/路由配置/API接口/工具和类型定义

阶段三：需求澄清
  ├─→ 完整性：需求是否完整
  ├─→ 一致性：需求与代码现状是否一致
  └─→ 明确性：交互细节是否明确
      输出：clarification.md

阶段四：需求拆解
  └─→ 将大需求拆分为多个子需求 PRD
      输出：多份 prd 文档 + 模块依赖关系 + 开发建议
```

### 4.3 AI 澄清的价值

AI 能发现需求评审时没有讨论到的细节问题，例如：
- "选择自定义后输入 X 天，X 的取值范围是多少？"
- "当用户从等于切换到匹配或为空时，已选择的枚举值如何处理？"

### 4.4 使用方式

```bash
# 基本用法
/prd-preprocess

# 指定需求目录
/prd-preprocess prd/20251217-new-feature/

# 通过 @ 选择文件
/prd-preprocess @prd/20251217-new-feature/original-prd.md
```

### 4.5 生成文件结构

```
prd/20251217-new-feature/
├── README.md                     # 需求概览
├── clarification.md              # 澄清记录
├── 20251217-new-feature-module-a-prd.md  # 子需求1
├── 20251217-new-feature-module-b-prd.md  # 子需求2
├── images/                       # 设计稿截图
├── backend-api.md                # 后端接口文档
└── original-prd/                 # 原始文档
```

## 五、智能开发工作流（Dev + D2C 双系统）

### 5.1 整体设计

智能开发工作流是一个顶层调度器，分析需求文档中的 Figma 解析策略，分三条路径执行：

| 策略 | 适用场景 | 执行路径 |
|------|---------|---------|
| **full** | 有设计稿 + 有逻辑 | D2C Phase 1 → logic-hints → Dev 逻辑补全 |
| **layout-only** | 有设计稿、纯布局 | D2C 独立完成 |
| **none** | 无设计稿、纯逻辑 | Dev 标准模式 |

### 5.2 两大 Skill 定位

| Skill | 定位 | 输入 → 输出 |
|-------|------|------------|
| **D2C** | 视觉驱动 | 设计稿 → UI 代码 → 逻辑补全提示 |
| **Dev** | 逻辑驱动 | 需求 → 完整可运行代码 |

## 六、D2C（Design to Code）

### 6.1 核心理念

> "设计驱动代码" — 从 Figma 设计稿自动生成高还原度的 UI 代码，将视觉还原工作自动化。

### 6.2 技能组成（6 个 Skill）

| Skill | 作用 |
|-------|------|
| figma-api-collector | 并行调用 Figma API 获取设计数据 |
| figma-design-analyzer | 提取结构化设计数据、生成样式映射 |
| component-matcher | 匹配设计组件到项目已有组件 |
| icon-matcher | 匹配图标 |
| code-generator | 生成 UI 代码 |
| manifest-builder | 生成清单文件 |

### 6.3 七步流水线

```
Step 1: Figma API 数据收集（并行 MCP 调用）
Step 2: 设计数据分析与结构化提取
Step 3: 组件识别与匹配
Step 4: 图标匹配
Step 5: 用户确认（manifest.md）
Step 6: UI 代码生成
Step 7: 生成 logic-hints.md（标记待补全的逻辑点）
```

### 6.4 关键设计点

| 设计点 | 说明 |
|--------|------|
| **并行 MCP 调用** | 所有 Figma API 调用在单条消息中并行发起，大幅缩短总耗时 |
| **单 Task 批处理** | 组件识别和图标匹配各用一个 Task 完成全部项目，避免逐个启动子代理的开销 |
| **预计算样式映射** | figma-design-analyzer 在提取阶段生成 `tw-to-css.json`，code-generator 直接查表 |
| **渐进式数据持久化** | 中间产物存入 `.workflow/temp/d2c/`，防止上下文压缩丢失 |
| **子代理上下文隔离** | D2C 在独立子代理中运行，完成后上下文自动释放 |

### 6.5 中间产物目录

```
.workflow/temp/d2c/[需求名]/
├── manifest.md          # 步骤5确认后生成
├── raw/                 # 原始 Figma JSON（完整备份）
├── extracted/           # 提取后的结构化数据
│   ├── code.html
│   ├── styles.json
│   ├── components.json
│   ├── assets.json
│   └── tw-to-css.json
└── screenshots/
```

### 6.6 logic-hints.md 内容

```
logic-hints.md:
├── 已生成文件列表
├── 已完成项（UI骨架/组件配置/样式）
├── 待补全清单（API调用/事件处理/数据源/路由）
├── 已使用组件列表
└── 补全建议
```

## 七、Dev（逻辑驱动开发）

### 7.1 核心理念

> "需求驱动，动态编排" — 分析 PRD 复杂度和特征，自动规划最优的 Skill 执行序列。

### 7.2 技能组成（7 个 Skill）

| Skill | 作用 |
|-------|------|
| feature-analyzer | 分析需求特征 |
| tech-extractor | 提取技术要点 |
| tech-learner | 学习技术实现 |
| tech-architect | 技术方案设计 |
| code-planner | 代码规划 |
| code-generator | 代码生成 |
| code-validator | 代码验证 |

### 7.3 动态规划（Step 0）

Dev 的核心设计是动态计划生成：

```
需求特征分析 → Skill 选择 → 用户确认 → 执行
```

Skill 动态选择规则根据需求复杂度、是否有设计稿、是否需要 API 对接等因素决定。

### 7.4 三级流水线（技术要点提取→学习→方案）

这是 Dev 最核心的设计——三个 Skill 形成递进式知识构建：

```
tech-extractor        tech-learner         tech-architect
  (提取技术点)    →    (学习实现)     →    (设计方案)
      ↓                    ↓                    ↓
  三级优先级          三级优先级           覆盖度校验
  🔴必须 🟡建议 ⚪可选  🔴深度 🟡了解 ⚪跳过  (发现缺口则补学)
```

**设计精髓**：
- **需求驱动过滤**：只提取与当前需求相关的技术点，不过度学习
- **三级优先级**（🔴🟡⚪）从提取阶段贯穿到学习阶段，控制学习深度
- **覆盖度校验**：tech-architect 验证方案中使用的所有技术是否都已被学习

### 7.5 三种执行策略

| 策略 | D2C 参与 | Dev 行为 |
|------|---------|---------|
| **full** | D2C Phase 1 生成 logic-hints.md | Dev 进入逻辑补全模式，各 Skill 行为调整 |
| **layout-only** | D2C 独立完成 | 不参与 |
| **none** | 不参与 | Dev 标准模式，动态规划 Skill 序列 |

## 八、自动化测试工作流

### 8.1 完整流程（七步）

```
Step 1: 调用测试工作流 → 生成测试计划
Step 2: AI 运行测试计划（操作浏览器执行用例）
Step 3: 生成测试报告
Step 4: 生成 Playwright 测试脚本
Step 5: 本地运行 → AI 调试/人工调试 → 跑通后提交
Step 6: UI 自动化平台重复跑测试
Step 7: CI 流水线配置（发 MR 时回归测试）
```

### 8.2 测试计划内容

测试计划包含：
- Frontmatter 基本信息
- 执行要求
- 每个测试用例：Ones CaseID、初始 URL、前置条件（含 3A 造数）、详细测试步骤、预期结果

### 8.3 三种执行模式

| 模式 | 适用场景 | 特点 |
|------|---------|------|
| **完整流程** | 用例 ≤ 15 个 | 传统流程，一步到底 |
| **渐进式** | 上下文易丢失 | 测完一个用例 → 生成脚本 → 验证，循环进入下一个 |
| **代码优先** | Vibe Coding | 基于 Plan 直接生成完整测试脚本，逐个运行修复 |

### 8.4 复杂场景处理

**登录态解决**：
- 本地：使用本地 Cookie/Token
- 平台：UI 自动化平台管理登录态

**前置数据准备（3A 造数）**：
- Arrange：准备测试数据
- Act：执行操作
- Assert：验证结果

## 九、AI Mock 工作流

### 9.1 核心优势

- **AI 帮你完成配置**：调用 `/bili-fe-mock-workflow-setup` 即可
- **无需额外代理软件**：集成在前端项目中，不影响业务代码
- **与 AI Agent 无缝集成**：Mock 逻辑本身即代码
- **三种模式任选**：MCP 动态添加、本地 custom-handlers、Swagger Mock

### 9.2 三种 Mock 模式

| 模式 | 方式 | 特点 |
|------|------|------|
| **MCP 动态添加** | AI 通过 MCP 动态添加 Mock | 不改本地文件 |
| **本地 custom-handlers** | AI 修改本地 handlers | Git ignored，不影响代码 |
| **Swagger Mock** | 基于 Swagger 文档生成 | 适合有接口文档的场景 |

### 9.3 使用方式

```bash
# 初始化
/bili-fe-mock-workflow-setup

# 首次使用
/bili-fe-mock-workflow 你的mock需求

# 后续直接告诉 AI 要求，无需每次都调工作流
```

### 9.4 适用场景

- 开发过程中无实际接口时 Mock
- 已有接口但需要调整数据返回测试不同 UI 场景
- 本地 UI 测试时临时 Mock
- 减少 AI 操作浏览器消耗的 Token

## 十、总结与启示

### 10.1 范式变革

> 前端工程师的价值正在从"单点编码产出"转向"问题抽象、方案设计、规则沉淀与质量把控"。

| 过去 | 未来 |
|------|------|
| 依赖个人经验推动需求落地 | 依赖规范化工作流、可复用上下文资产 |
| 单点编码产出 | 问题抽象 + 方案设计 + 规则沉淀 + 质量把控 |

### 10.2 核心原则

1. **先定义清楚问题**：通过 prd-preprocess 消除需求模糊
2. **再约束生成过程**：通过 .workflow 知识库约束 AI 行为
3. **最后标准化验证**：通过测试工作流确保结果可交付、可维护、可复用

### 10.3 工程共识

> Harness Engineering 的意义不只是提供一套更高效的开发流程，更是在团队内部建立一种新的工程共识。

- 谁能更好地**组织需求**、**编排上下文**、**制定约束**、**验证结果**，谁就能更有效地放大 AI 的能力
- 工作流的价值不仅体现在一次提效，而在于**沉淀为团队能力**
- 提效从"偶发结果"变为"组织层面的稳定能力"
