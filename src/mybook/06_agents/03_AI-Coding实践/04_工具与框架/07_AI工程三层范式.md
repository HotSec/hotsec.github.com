# AI 工程三层范式

## 一、核心论点

> **提示词工程是建立局部概率空间，上下文工程是构建信息空间，Harness 是搭建运行系统。**

2023 年 "Prompt Engineering" 无处不在；到 2025 年中 "Context Engineering" 成为主流；2026 年 "Harness Engineering" 成为关键词。三者不是竞争关系，而是**分层**——描述同一问题在不同深度上的结构。

| 范式 | 核心问题 | 本质 | 类比 |
|------|---------|------|------|
| **Prompt Engineering** | 模型"听不懂" | 建立局部概率空间 | 任务说明书 |
| **Context Engineering** | 模型"没信息" | 构建信息空间 | 参考资料包 |
| **Harness Engineering** | 模型"反复错" | 搭建运行系统 | 完整工作台 |

---

## 二、Prompt Engineering：建立局部概率空间

### 2.1 定义

Prompt Engineering 处理的是**人类意图到模型输入之间的接口**，通过措辞去激活正确的模型行为，本质上是在模型的概率空间中**划定一个高概率区域**，让输出落在期望范围内。

### 2.2 核心技术

| 技术 | 作用 |
|------|------|
| 角色设定 | 约束模型身份和输出风格 |
| 思维链（CoT） | 引导分步推理 |
| Few-shot 示例 | 用范例画像期望行为 |
| ReAct 框架 | 推理+行动交替 |
| 结构化输出 | 约束输出格式 |
| 迭代式措辞优化 | 反复测试打磨措辞 |

### 2.3 局限性

Prompt 无法解决以下问题：
- 无法注入私域知识（团队规范、内部文档）
- 无法感知外部状态（当前时间、系统日志）
- 无法处理跨会话的记忆
- 无法取代权限系统、工具可用性或错误恢复逻辑
- 按请求生效，**无状态**，优化的是单次输入-输出对

### 2.4 精心设计 vs 粗糙 Prompt

```
# 粗糙
prompt = "Fix the bug in my code"

# 精心设计
prompt = """You are a senior Python engineer reviewing a production bug.
Context:
- The bug causes a KeyError on line 47 of orders.py
- It only occurs during weekend batch processing
- The system uses PostgreSQL with a read replica

Your task:
1. First, identify the root cause without changing any code
2. Describe what data condition triggers the error
3. Propose a fix that maintains backward compatibility
4. List any tests that should be added

Do not modify any files until I confirm your diagnosis."""
```

第二个 Prompt 好得多，但如果模型访问不到 orders.py、没有工具运行测试、无法确认修复是否通过编译，Prompt 质量碰到的是**硬性天花板**。

## 三、Context Engineering：构建信息空间

### 3.1 定义

Context Engineering 问的是：**模型工作时应该处于什么信息环境里？** 上下文窗口不只是一个 Prompt，而是模型在做出每个决策时能够注意到的**全部信息**。

> Anthropic 定义：当 Agent 朝向更长的时间跨度和多轮推理演进时，核心挑战变成了"管理整个上下文状态：系统指令、工具、MCP 服务器、外部数据、消息历史"。

### 3.2 三大支柱

#### 支柱一：RAG 与检索

处理所需知识超出上下文窗口容量的场景——对知识进行索引，在需要的时刻检索最相关的片段注入上下文。

| 场景 | 有效方法 | 原因 |
|------|---------|------|
| 企业知识问答 | 向量检索 | 语义相似度匹配有效 |
| 代码调试 | grep/git log/结构化搜索 | 信号是调用链、符号定义，非语义相似度 |
| 策略问答 | 向量检索 | 文档型知识匹配 |

**关键洞察**：调试场景里的信号不是"与错误消息的语义相似度"，而是调用链、git blame、三个文件之外的符号定义以及迁移历史——更接近 grep、glob 和结构化搜索，而非向量相似度。

#### 支柱二：工具

没有工具的 LLM 没有当前时间，不能读写文件，不能运行命令，无法访问外部 API。Context Engineering 的工作范畴包括：

- 决定暴露哪些工具
- 如何描述工具（描述质量直接影响模型选择）
- 如何防止工具过载

**工具过载问题**：接入过多 MCP 服务器会让上下文窗口被工具描述塞满，"更快地进入降智区"。建议使用一组**小而可组合的工具**：Read、Write、Grep、Glob、Bash，而非一份不断膨胀的专用工具清单。

> 如果一个 MCP 服务器复制了训练数据中已有良好表征的 CLI 功能，直接让 Agent 调用 CLI 效果更好。

#### 支柱三：记忆

模型的无状态性意味着每个会话都是冷启动。Context Engineering 在这一层要做的决策：

| 记忆类型 | 作用 | 实现方式 |
|---------|------|---------|
| 短期记忆 | 对话缓冲区 | 消息历史 |
| 长期记忆 | 用户偏好、项目规则、跨会话决策记录 | CLAUDE.md、task_plan.md、结构化存储 |

### 3.3 上下文腐蚀（Context Rot）

针堆找针类基准揭示了一个现象：**上下文腐蚀**——随着上下文窗口中的 tokens 增加，模型从上下文中准确回忆信息的能力反而下降。

原因：
- Transformer 让每个 token 与上下文中所有 token 建立关联（n² 注意力关系），随着长度增长建模能力被"拉薄"
- 模型对短序列的训练经验远多于长序列
- 位置编码插值等技术牺牲部分位置精确理解

**上下文必须被视作一种有限资源，且具有边际收益递减。**

### 3.4 有效上下文的"解剖学"

在"有限注意力预算"的约束下，优秀的上下文工程目标是：**用尽可能少、但高信号密度的 tokens，最大化获得期望结果的概率。**

| 组件 | 设计原则 | 常见误区 |
|------|---------|---------|
| 系统提示 | 信息层级"刚刚好"，分区组织 | 过度硬编码 if-else / 过于空泛 |
| 工具 | 职责单一、低重叠、接口语义清晰 | 臃肿工具集，选哪个工具都不清楚 |
| 示例 | 精挑多样且典型的示例 | 把所有边界条件罗列塞进提示 |

> 如果人类工程师都说不准用哪个工具，别指望智能体做得更好。

### 3.5 JIT 上下文 vs 预加载

工程实践正在从"推理前一次性检索"过渡到"**及时（Just-in-time, JIT）上下文**"：

| 方式 | 做法 | 特点 |
|------|------|------|
| 预加载 | 推理前一次性检索所有相关数据 | 快但可能过时 |
| JIT 上下文 | 维护轻量化引用，运行时动态加载 | 按需获取，渐进式披露 |

混合策略更有效：前置加载少量"高价值"上下文保证速度，同时提供 glob、grep 等原语让智能体即时检索。

### 3.6 长时程任务的上下文工程

| 方法 | 适用场景 | 核心思想 |
|------|---------|---------|
| **压缩整合（Compaction）** | 需要长对话连续性 | 接近上限时高保真总结，用摘要重启新窗口 |
| **结构化笔记** | 有里程碑的迭代式开发 | 关键信息写入上下文外的持久化存储 |
| **子代理架构** | 复杂研究与分析 | 主代理规划，子代理在干净窗口中深挖 |

### 3.7 Context Engineering 的缺口

管的是模型看到什么，不管：
- 模型出错后怎么办、怎么恢复
- 不能越过什么边界
- 系统如何验证输出的正确性

## 四、Harness Engineering：搭建运行系统

### 4.1 定义

> Harness Engineering 是对系统的设计与实现，约束 Agent 能做什么，告知它应该做什么，验证它是否正确完成，并在出错时纠正它。

> Mitchell Hashimoto："每当发现 Agent 犯了一个错误，就投入时间设计一个方案，让它不再犯同样的错。"

> coding agent = AI model(s) + harness。模型是马，Harness 是所有其他部分——缰绳、马鞍、马蹄，甚至是路。

### 4.2 Harness 比模型更重要

**LangChain 的证据**：未更换底层模型，只改了 Harness，Terminal Bench 2.0 得分从 52.8% 升至 66.5%，排名从前 30 跃至前 5。改动包括：
- 完成前运行预检清单的自我验证循环
- 启动时映射目录结构的上下文工程
- 识别重复文件编辑的循环检测中间件
- 推理预算策略（规划用高推理模型，实现切换到低推理模型）

**OpenAI 的证据**：超过一百万行代码的生产应用，零行人工代码。工程师的工作是设计 Harness，不是写代码。

**Stripe 的证据**：Minions 系统每周产出超过 1,000 个合并的 PR，从任务创建到 PR 审查无需开发者介入。

### 4.3 关键配置点

#### AGENTS.md / CLAUDE.md

将 markdown 文件确定性注入 Agent 的系统提示。苏黎世联邦理工学院研究 138 个此类文件发现：**LLM 生成的版本反而损害性能**（成本增加 20%+，Agent 多消耗 14-22% 推理 Token，解决率未提升）。

原则：**少即是多**。HumanLayer 的 CLAUDE.md 不到 60 行，只包含普遍适用的简练指令。

```markdown
## Project conventions
- All database access goes through /src/db/queries/, never raw SQL inline
- Use `pnpm run typecheck` after every change
- Never modify migration files after they've been committed

## Linear workflow
- Fetch issues: `linear get-issue ENG-XXXX`
- Update status: `linear update-status ENG-XXXX "in dev"`

## Verification
Run `pnpm run typecheck && pnpm test --changed` before stopping.
Failures are required reading - do not ignore them.
```

#### Skills（渐进式披露）

与其把全部指令预加载到系统提示中，不如在触发特定任务时才加载对应的知识。调试技能不会污染重构任务的上下文。

#### Sub-agents（上下文防火墙）

Chroma 研究表明模型性能随上下文长度增长而下降。Sub-agents 从结构层面解决：
- 每个 Sub-agent 获得全新的、小的、高相关性的上下文窗口
- 父 Agent 只接收压缩后的结果
- 中间工具调用、grep 输出、文件读取全部隔离在 Sub-agent 内部
- 成本调整：父会话用 Opus 编排，Sub-agent 用 Sonnet/Haiku 执行

#### Hooks（确定性反馈循环）

在 Agent 生命周期的特定事件中触发（文件写入后、Agent 停止前、工具调用匹配模式时）。

最有效模式：每次 Agent 停止后运行类型检查和 linter，只把错误信息返回。

```bash
#!/bin/bash
cd "$CLAUDE_PROJECT_DIR"
OUTPUT=$(bun run --parallel \
  "biome check . --write --unsafe || biome check . --write --unsafe" \
  "turbo run typecheck" 2>&1)

if [ $? -ne 0 ]; then
  echo "$OUTPUT" >&2
  exit 2  # 退出码 2 重新激活 Agent 来修复错误
fi
# 成功：静默。不污染上下文。
```

逻辑：**成功时保持安静，只有失败才出现**。错误变成反馈信号，而非用通过测试的输出淹没上下文窗口。

#### 背压机制（验证层）

代码覆盖率下降？Hook 在 Agent 停止前发出提示要求补齐。TypeScript 报错？任务在错误解决之前不能标记为完成。"大概能用"和"可证明能用"之间的鸿沟就是这样填平的。

### 4.4 记忆系统三层

| 层级 | 内容 | 类比 |
|------|------|------|
| 短期记忆 | 当前任务的上下文 | 工作记忆 |
| 中期记忆 | 项目的历史决策 | 项目经验 |
| 长期记忆 | 个人偏好和工作风格 | 职业经验 |

## 五、三层诊断框架

三个层次构成严格的层级关系，**判断错层次直接浪费精力**。

### 5.1 故障诊断

| 故障现象 | 问题层次 | 解决方向 |
|---------|---------|---------|
| 输出格式错误、范围偏差 | Prompt Engineering | 收紧指令，补上范例，约束输出格式 |
| 杜撰代码库事实、选错工具 | Context Engineering | 加检索、修工具描述、调整记忆结构 |
| 长任务漂移、循环、破坏性改动、静默失败 | Harness Engineering | 加 Sub-agent 隔离、循环检测、权限 Hook |

### 5.2 诊断代码

```python
def diagnose_agent_failure(failure_type):
    if failure_type == "wrong_output_format":
        return "Prompt Engineering - constrain output format"
    elif failure_type == "hallucinated_fact_about_codebase":
        return "Context Engineering - add retrieval or inject relevant file"
    elif failure_type == "wrong_tool_selected":
        return "Context Engineering - improve tool descriptions or reduce tool count"
    elif failure_type == "drifts_on_long_task":
        return "Harness Engineering - add sub-agent isolation or loop detection"
    elif failure_type == "destructive_action_taken":
        return "Harness Engineering - add permission hooks and approval gates"
    elif failure_type == "silent_failure_no_error_surfaced":
        return "Harness Engineering - add back-pressure verification and hooks"
    elif failure_type == "good_code_regresses_unknown":
        return "Harness Engineering - add entropy management and documentation linting"
```

### 5.3 关键洞察

> 编码 Agent 会话中期的质量下降十次有九次源自上下文窗口饱和或反馈循环缺位，而非原始指令措辞不到位。

直觉通常是重写 Prompt，但实际问题往往在更高层。

## 六、生产 Harness 配置清单

### 6.1 TypeScript Monorepo 最小非平凡配置

**Prompt 层**：
- [ ] System prompt 定义角色、范围和 Agent 不应做的事
- [ ] 输出格式约束

**Context 层**：
- [ ] AGENTS.md 不超过 60 行，只保留普遍适用的约束
- [ ] Skills：调试、重构、PR 创建、依赖审计
- [ ] MCP servers：同时只激活 2-3 个，禁用不用的
- [ ] Memory：对话缓冲区 + 结构化长期规则存储

**Harness 层**：
- [ ] Pre-commit hook：biome + typecheck
- [ ] PostToolUse hook：每次文件写入后向 Agent 报告 linter 错误
- [ ] Stop hook：只运行变更的测试文件，返回错误
- [ ] Coverage hook：覆盖率低于阈值时告警
- [ ] 循环检测：同一文件在同一会话中被编辑 3+ 次时标记
- [ ] Sub-agent 模式：研究、代码追踪、QA
- [ ] 升级规则：连续 3+ 次工具调用受阻时停止并询问

### 6.2 最佳实践（2026 年实战经验）

1. **从最小 AGENTS.md 开始**：不超过 60 行，不列目录结构，LLM 生成的文件会主动损害性能
2. **立刻加一个验证 Hook**：每次 Agent 停止后运行 typecheck 或 lint，这是杠杆最高的单项 Harness 投入
3. **只保留最常用的 2 个 MCP 工具**：工具描述膨胀是上下文饱和最常见的成因
4. **只有 Agent 因同一原因失败两次时才添加 Skill**：过早加载不适用的指令会产生负面效果
5. **超过 15 次工具调用才能解决的任务，交给 Sub-agent**：上下文腐化是可量化的实际现象
6. **把 git 当作 Agent 的原生记忆**：提交消息、小粒度 diff、分支历史——鼓励小而语义明确的提交

## 七、三层范式的关系

```
┌─────────────────────────────────────────────────┐
│           Harness Engineering（运行系统）          │
│  ┌───────────────────────────────────────────┐  │
│  │      Context Engineering（信息空间）        │  │
│  │  ┌─────────────────────────────────────┐  │  │
│  │  │   Prompt Engineering（概率空间）      │  │  │
│  │  └─────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

三者是**递进包容**关系：
- Prompt 是 Context 的子集（Context 包含 Prompt + 工具 + 记忆 + 检索）
- Context 是 Harness 的子集（Harness 包含 Context + 验证 + 约束 + 反馈循环）

缺 Context 的 Harness：受约束但无法获取所需信息
缺 Harness 的 Context：信息充分但缺乏反馈

**两者缺一不可。**

---

## 八、总结

> 2026 年底层模型越来越趋向于商品化，Harness 才是差异化所在。

核心能力要求正在重新定义：从"怎么写 Prompt"变成"怎么设计一个让 AI 可靠做对事的环境"——后者需要系统思维、架构设计、可观测性工程，以及定义停止条件和升级策略的能力。

如果正在用前沿模型而 Agent 质量仍然不稳定，模型几乎可以确定不是症结所在。**Harness 才是。而 Harness 不用等下一个模型版本就可以修。**

> Prompt Engineering 给出了更好的提问方式，Context Engineering 给出了更好的信息，Harness Engineering 给出了一个真正可以被信任去做实际工作的系统。
