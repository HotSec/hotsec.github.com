# Codex /goal 目标管理

## 一、概述

**Codex /goal** 是 OpenAI Codex CLI（v0.128.0+）引入的目标生命周期管理功能，为 AI Coding Agent 提供结构化的目标定义、追踪和审计机制。

核心理念：**将模糊的"帮我写个功能"转化为结构化的、可追踪的、有明确完成标准的目标**。

---

## 二、五段式黄金模板

Codex /goal 采用五段式模板定义目标，每个目标必须包含以下五个部分：

```
┌─────────────────────────────────────┐
│         /goal 五段式模板              │
├─────────────────────────────────────┤
│ 1. Objective    — 目标是什么         │
│ 2. Scope        — 范围边界           │
│ 3. Constraints  — 约束条件           │
│ 4. Done when    — 完成标准           │
│ 5. Stop if      — 停止条件           │
└─────────────────────────────────────┘
```

### 2.1 Objective（目标）

清晰描述要达成什么，使用动词开头：

```
Objective: 实现用户注册 API，支持邮箱和手机号两种注册方式
```

### 2.2 Scope（范围）

明确边界，定义哪些在范围内、哪些不在：

```
Scope:
  包含：注册 API 端点、输入验证、密码哈希、数据库写入
  不包含：邮箱验证、短信验证码、登录功能、前端页面
```

### 2.3 Constraints（约束）

技术和管理层面的限制条件：

```
Constraints:
  - 使用 Go 标准库，不引入第三方依赖
  - 密码使用 bcrypt 哈希，cost factor >= 12
  - API 响应时间 < 200ms
  - 必须通过所有现有测试
```

### 2.4 Done when（完成标准）

可验证的完成条件，这是退出循环的关键：

```
Done when:
  - 注册 API 可通过 curl 调用成功
  - 邮箱和手机号两种方式均可注册
  - 重复注册返回 409 错误
  - 所有单元测试通过
  - 代码通过 golangci-lint 检查
```

### 2.5 Stop if（停止条件）

异常情况下的安全退出机制：

```
Stop if:
  - 修改了超过 5 个现有文件
  - 测试连续失败超过 3 次
  - Token 消耗超过预算的 80%
  - 出现安全扫描告警
```

## 三、目标生命周期管理

### 3.1 状态机

```
                    ┌──────────┐
                    │  active  │ ← 创建/恢复
                    └────┬─────┘
                         │
              ┌──────────┼──────────┐
              ↓          ↓          ↓
        ┌──────────┐ ┌────────┐ ┌────────────┐
        │  paused  │ │achieved│ │budget_limited│
        └────┬─────┘ └────────┘ └────────────┘
             │            ↑
             └────────────┘
              恢复执行
```

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `active` | 目标正在执行 | 创建或从 paused 恢复 |
| `paused` | 目标暂停 | 用户手动暂停或遇到阻塞 |
| `achieved` | 目标已达成 | Done when 条件全部满足 |
| `unmet` | 目标未达成 | Stop if 条件触发 |
| `budget_limited` | Token 预算耗尽 | Token 消耗达到上限 |

### 3.2 持久化存储

目标状态持久化到 `.codex/` 目录：

```
.codex/
├── goals/
│   ├── active/
│   │   └── goal-20260515-001.md    # 活跃目标
│   ├── achieved/
│   │   └── goal-20260514-003.md    # 已完成目标
│   └── archived/
│       └── goal-20260510-002.md    # 归档目标
├── continuation.md                  # 续接审计文件
└── budget.json                     # Token 预算配置
```

### 3.3 Token 预算

```json
{
  "total_budget": 500000,
  "consumed": 125000,
  "warning_threshold": 0.8,
  "hard_limit": true
}
```

- `warning_threshold`：达到 80% 时发出警告
- `hard_limit`：是否在预算耗尽时强制停止

## 四、续接审计（continuation.md）

**continuation.md** 是 Codex /goal 的核心审计机制，记录目标的完整执行历史。

### 4.1 文件结构

```markdown
# Goal: 实现用户注册 API

## 执行记录

### 第 1 轮
- 时间：2026-05-15 10:00
- 操作：创建注册 API 骨架代码
- 结果：编译通过，测试未覆盖
- Token 消耗：15,000

### 第 2 轮
- 时间：2026-05-15 10:05
- 操作：添加输入验证和密码哈希
- 结果：单元测试通过 8/10
- Token 消耗：22,000

### 第 3 轮
- 时间：2026-05-15 10:12
- 操作：修复两个失败测试
- 结果：全部测试通过 ✓
- Token 消耗：8,000

## 最终状态
- 状态：achieved
- 总 Token 消耗：45,000 / 500,000
- 执行轮次：3
```

### 4.2 审计价值

1. **可追溯**：每一步操作都有记录
2. **可回溯**：出问题时可定位到具体轮次
3. **可优化**：分析 Token 消耗模式，优化目标定义
4. **可续接**：中断后可从上次状态继续

## 五、三种工作流

### 5.1 直接 /goal

最简单的用法，直接定义目标并执行：

```
/goal
Objective: 修复登录页面的 CSS 布局问题
Scope: 仅修改 login.css 和 Login.vue
Constraints: 不改变组件逻辑
Done when: 登录页面在移动端和桌面端布局正常
Stop if: 修改了超过 3 个文件
```

适用场景：小而明确的任务。

### 5.2 /plan + /goal

先用 /plan 生成计划，再用 /goal 执行：

```
# 第一步：生成计划
/plan 重构用户认证模块

# 第二步：基于计划创建目标
/goal
Objective: 按计划重构用户认证模块
Scope: auth/ 目录下的所有文件
Constraints: 保持 API 接口不变
Done when: 所有认证测试通过，API 兼容性验证通过
Stop if: 任何现有测试被破坏
```

适用场景：中等复杂度的任务，需要先规划再执行。

### 5.3 OpenSpec + /goal

使用 OpenSpec 规范定义详细规格，再创建目标：

```
# 第一步：编写 OpenSpec 规格文档
# specs/payment.md

# 第二步：基于规格创建目标
/goal
Objective: 按照 specs/payment.md 实现支付模块
Scope: payment/ 目录，新增文件
Constraints: 遵循 OpenSpec 规格中的所有约束
Done when: 规格中的所有验收条件满足
Stop if: 偏离规格定义的行为
```

适用场景：大型功能开发，需要严格的规格约束。

## 八、最佳实践

### 8.1 目标定义原则

1. **Done when 必须可验证**：避免"代码质量好"这类主观标准
2. **Stop if 必须可检测**：避免"感觉不对"这类模糊条件
3. **Scope 宁小勿大**：小目标更容易达成，大目标拆分为多个小目标
4. **Constraints 要具体**：具体到文件名、函数名、指标数值

### 8.2 常见反模式

| 反模式 | 问题 | 改进 |
|--------|------|------|
| Done when 过于模糊 | 无法判断是否完成 | 用可量化标准替代 |
| 缺少 Stop if | 可能无限循环 | 始终定义安全退出条件 |
| Scope 过大 | Agent 容易偏移 | 拆分为多个小目标 |
| 忽略 Token 预算 | 成本失控 | 设置合理预算和阈值 |

### 8.3 目标拆分策略

大目标 → 中目标 → 小目标，形成目标树：

```
大目标：实现完整的用户系统
├── 中目标1：用户注册
│   ├── 小目标1.1：注册 API
│   ├── 小目标1.2：输入验证
│   └── 小目标1.3：密码安全
├── 中目标2：用户登录
│   ├── 小目标2.1：登录 API
│   └── 小目标2.2：Token 管理
└── 中目标3：用户信息
    ├── 小目标3.1：查询 API
    └── 小目标3.2：更新 API
```

每个小目标独立执行，完成后触发下一个。
