## MiniMax Mavis Agent Teams 实战

### 一、核心痛点

传统单 Agent 存在三大问题：
1. **中断频繁**：写报告写三段就停下来问「需要继续吗」
2. **质量下滑**：任务跑到后半段，前后矛盾，输出质量下降
3. **自我审查盲区**：自己写的代码自己审，缺陷藏在盲区里

**根源**：一个 AI 干所有活，又当选手又当裁判，上下文越塞越满，质量顶不住。

---

### 二、Agent Teams 核心设计

Mavis 是团队 Leader，下面挂着一群成员，分成三个角色：

| 角色 | 职责 |
|------|------|
| Leader | 拆任务、组团队、分活、监控进度 |
| Worker | 具体执行任务（写代码、爬数据等） |
| Verifier | 验收、挑刺、打回返工 |

**特点**：
- 每个 Agent 有独立的上下文和工具权限
- Worker 和 Verifier 是对抗关系
- Team Engine 状态机驱动循环

---

### 三、实战案例：高频面试题排行榜

**任务**：从小林大模型面试题网站抓取 74 道题，做成高频面试题排行榜网页。

**执行过程**：
1. Mavis 自动拆任务、组团队
2. 使用爬虫技能抓取网站数据
3. 自动生成网页（蓝紫色 AI 风格）
4. 可通过技能商店安装 UI 优化技能更换风格

**交付结果**：
- 完整网页，74 道题全部抓取
- 按高频排序
- 每道题有面试视角解读和学习建议
- 可跳转到原文

### 四、实战案例：全栈销售数据看板

**需求**：
- 后端：Python FastAPI REST API
- 前端：React + 图表库
- 功能：销售趋势、Top 产品、地区分布
- 要求：模拟数据、单元测试、集成测试、代码审查

**执行过程**：
1. Leader 判断需要组团，制定计划
2. 后端、前端、测试三条线并行
3. Verifier 发现前后端 API 端点和数据结构对不上
4. 自动打回返工，直到 Verifier 点头

**关键点**：
- FastAPI 后端和 React 前端同时进行
- 53 个测试全过，覆盖率 99%
- 对抗式验收确保质量

---

### 五、运行时基础设施

Agent Team 背后是一整套运行时系统：

**Team Engine 职责**：
- 任务创建来源管理（用户发起、Agent 拆分、定时触发）
- 消息路由（用户-Agent、Agent-Agent、定时任务、IM）
- 状态机驱动流程
- 进度实时更新

**与单纯提示词的区别**：
- 提示词只是「工作手册」，告诉角色职责
- 系统层面需要：项目看板、沟通工具、权限控制、日志追溯

---

### 六、成本与边界

**成本**：
- Token 消耗是单 Agent 的 1.5-2 倍
- 但通过以下方式优化：
  - 每个 Agent 只接收自己任务相关的摘要
  - Agent 之间走文件交接和留言板，按需获取
  - 状态机管流程，避免空转

**适用场景**：
- **适合**：多步骤、多角色、需要交叉验证的复杂任务
- **不适合**：改错别字、查天气、翻译等简单任务

**长期收益**：
- 每跑一次任务，经验沉淀成记忆和 Skill
- 下次遇到类似任务自动生效
- 系统持续进步

多 Agent 协作是行业方向：

- MiniMax Mavis：在对抗式验收和上下文隔离上走出特色

**核心价值**：

- 比单 Agent 闷头跑更靠谱

---

### 九、总结

Agent Teams 的核心优势：
1. **分工明确**：Leader、Worker、Verifier 各司其职
2. **对抗式验收**：Worker 和 Verifier 互相制衡
3. **持续积累**：经验沉淀成记忆和 Skill
4. **实时响应**：主 Agent 随时汇报进度
5. **并行推进**：子任务后台各自进行

**适合场景**：涉及多角色、多步骤、必须交叉验证的项目。
