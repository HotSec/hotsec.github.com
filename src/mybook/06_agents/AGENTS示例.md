# AGENTS.md — AI 代码生成规范

本文件为 AI 编码工具（Cursor、Trae、Copilot、Claude Code 等）提供统一的代码生成规范，确保生成的代码质量一致、风格统一、安全可靠。

---

## 1. 通用原则

### 1.1 先理解再动手

- 修改代码前，先阅读相关文件和上下文，理解现有架构和设计意图
- 不要假设某个库可用，先检查项目依赖（package.json、go.mod、requirements.txt、Cargo.toml 等）
- 遵循项目已有的代码风格和模式，不要引入新的风格

### 1.2 最小变更

- 只做被要求的修改，不做额外改动
- 不主动添加注释，除非用户明确要求
- 不主动创建文档文件（README.md 等），除非用户明确要求
- 不主动提交代码，除非用户明确要求

### 1.3 可验证性

- 修改完成后，运行项目的构建和测试命令验证
- 如果不知道测试命令，先查找 README、Makefile、package.json 中的 scripts 字段
- 构建或测试失败时，修复问题直到通过

## 2. 代码风格

### 2.1 通用规则

- 不添加注释，除非用户要求
- 使用项目已有的命名约定，不要混用风格
- 缩进跟随项目现有风格（tab 或 space），不混用
- 行尾无多余空格
- 文件末尾保留一个换行符

### 2.2 Go

- 使用 `gofmt` 格式化，不做任何偏离
- 错误处理：不忽略 error 返回值，必须检查或显式忽略（`_ =`）
- 命名：驼峰命名，导出用大写开头，未导出用小写开头
- 包导入：标准库 / 第三方库 / 项目内部，分组空行分隔
- 日志：使用 `log/slog`，不使用 `log.Printf`
- 错误响应：不向客户端暴露内部错误详情，使用通用消息

### 2.3 Python

- 使用 `ruff format` 格式化（Black 兼容），88 字符行宽
- 使用 `ruff check` 检查，遵循规则修复
- 类型注解：函数签名必须加类型注解
- 命名：函数/变量用 snake_case，类用 PascalCase，常量用 UPPER_SNAKE_CASE
- 导入排序：标准库 / 第三方库 / 本地模块，使用 `isort` 或 ruff `I` 规则
- 异步：优先使用 `async/await`，避免混用线程和协程

### 2.4 JavaScript / TypeScript

- 使用项目配置的格式化器（Prettier / Biome），无配置时 2 空格缩进
- 优先使用 `const`，其次 `let`，不用 `var`
- 使用模板字符串代替字符串拼接
- 使用可选链 `?.` 和空值合并 `??`
- 异步使用 `async/await`，不用 `.then()` 链
- 模块使用 ES Module（`import/export`），不用 CommonJS（`require`）

### 2.5 Rust

- 使用 `cargo fmt` 格式化
- 使用 `cargo clippy` 检查，遵循建议修复
- 命名：函数/变量 snake_case，类型/ trait PascalCase，常量 SCREAMING_SNAKE_CASE
- 错误处理：使用 `Result<T, E>`，不使用 `unwrap()` 除非确定不会 panic
- 优先使用 `&str` 而非 `String` 作为函数参数

### 2.6 C / C++

- 使用 `clang-format` 格式化，跟随项目 `.clang-format` 配置
- C++ 风格：优先使用现代 C++（智能指针、RAII、移动语义）
- 头文件：使用 `#pragma once` 或传统 include guard
- 命名：函数/变量 snake_case，类/结构体 PascalCase

## 3. 安全规范

### 3.1 绝对禁止

- 不在代码中硬编码密钥、密码、Token、API Key 等敏感信息
- 不在日志中输出敏感信息
- 不在错误响应中暴露内部实现细节（堆栈跟踪、SQL 语句、文件路径等）
- 不使用 `eval()`、`exec()` 等动态代码执行，除非有严格的安全沙箱

### 3.2 必须遵守

- SQL 查询使用参数化，不拼接 SQL 字符串
- 用户输入必须校验和转义
- 文件路径操作必须防路径穿越（`../`）
- HTTP 响应设置安全头（CSP、X-Content-Type-Options 等）
- CORS 配置不使用 `*` + credentials 模式

### 3.3 认证与授权

- API 端点必须检查认证和权限
- 密码使用 bcrypt/argon2 哈希，不用 MD5/SHA
- JWT Token 验证签名和过期时间
- WebSocket 连接验证 Origin

## 4. 架构与设计

### 4.1 项目结构

- 遵循项目已有的目录结构和分层模式
- 新文件放在符合职责的目录中，不随意创建新目录
- 配置集中管理，不散落在代码各处

### 4.2 依赖管理

- 优先使用项目已有的库，不引入新的依赖
- 如需引入新依赖，选择社区活跃、维护良好的库
- 不重复造轮子，使用标准库或已有依赖实现功能

### 4.3 错误处理

- 错误必须向上传播或处理，不能静默忽略
- 区分可恢复错误和不可恢复错误
- 网络请求必须有超时和重试机制
- 资源（连接、文件句柄）必须确保释放（defer / with / finally）

### 4.4 并发安全

- 共享状态必须加锁或使用并发安全的数据结构
- 避免在锁内执行 IO 操作
- Channel / 队列使用有界缓冲，防止内存无限增长
- 协程 / goroutine 必须有退出机制，防止泄漏

## 5. 数据库

### 5.1 查询优化

- 频繁查询的字段添加索引
- 大量数据使用分页查询，不一次性加载
- 写操作使用事务保证原子性
- 避免 N+1 查询

### 5.2 迁移

- 数据库结构变更使用迁移脚本，不手动修改
- 迁移脚本必须幂等（可重复执行不出错）
- 新增列提供默认值，避免破坏现有数据

---

## 6. API 设计

### 6.1 RESTful 规范

- 资源用名词复数，动作用 HTTP 方法（GET/POST/PUT/DELETE）
- 路径参数用于标识资源，查询参数用于过滤和分页
- 响应格式统一：`{"data": ..., "error": ...}` 或 `{"error": "message"}`

### 6.2 状态码

- `200` 成功 / `201` 创建成功
- `400` 请求参数错误 / `401` 未认证 / `403` 无权限 / `404` 不存在
- `409` 冲突（如重复创建）/ `422` 参数校验失败
- `500` 服务器内部错误（不暴露详情）

### 6.3 版本与兼容

- API 路径包含版本号（`/api/v1/`）或使用 Header 版本控制
- 响应字段只增不减，废弃字段标记 `deprecated` 而非直接删除

## 7. 测试

### 7.1 原则

- 修改代码后运行已有测试，确保不破坏现有功能
- 新增功能如果项目有测试习惯，补充对应测试
- 测试覆盖：正常路径 + 边界条件 + 错误路径

### 7.2 命名

- 测试函数名描述行为：`TestXxx_WhenCondition_ExpectedResult`
- 不使用含糊的名称如 `TestFunction1`、`test_it_works`

## 8. Git 提交

### 8.1 提交信息格式

```
<type>: <简短描述>

<可选的详细说明>
```

type 类型：
- `feat`：新功能
- `fix`：修复 bug
- `refactor`：重构（不改变行为）
- `perf`：性能优化
- `docs`：文档
- `test`：测试
- `chore`：构建/工具/依赖

### 8.2 提交粒度

- 每次提交只做一件事，不混合多个不相关的修改
- 提交前确保构建和测试通过
- 不提交 IDE 配置、临时文件、敏感信息

## 9. 知识库项目特殊规则

当操作知识库（mybook）目录时，额外遵守以下规则：

### 9.1 目录命名

- 顶层目录：`{双数字编号}_{中文名称}`，如 `01_go/`、`02_python/`
- 子目录：同样双数字编号，如 `01_语言基础/`、`02_并发编程/`
- 编号连续，不跳号；插入新内容用小数编号 `02.1_类型推断.md`

### 9.2 文件命名

- 标准格式：`{双数字编号}_{中文名称}.md`
- 特殊文件不受编号限制：README.md、index.md、SUMMARY.md、assets/

### 9.3 添加知识点流程

1. 检查是否已存在相关笔记
2. 如果不存在，在合适的目录下创建新笔记
3. 如果存在，判断内容是否需要完善或更新
4. 检查是否需要更新 ALL.md 索引

### 9.4 ALL.md 索引格式

- 文件链接：`> [📄 文件名.md](./mybook/路径/文件名.md)`
- 目录链接：`> [📁 目录名/](./mybook/路径/目录名/)`
- 使用 `<details>` 折叠标签组织内容

## 10. 工具链速查

| 语言 | 格式化 | Lint | 测试 | 构建 |
|------|--------|------|------|------|
| Go | `gofmt` | `go vet` | `go test ./...` | `go build ./...` |
| Python | `ruff format` | `ruff check` | `pytest` | `uv build` |
| JS/TS | `prettier --write` | `eslint` | `vitest` / `jest` | `tsc --noEmit` |
| Rust | `cargo fmt` | `cargo clippy` | `cargo test` | `cargo build` |
| C/C++ | `clang-format` | `clang-tidy` | CTest / GTest | `cmake --build` |
