# 智能体开发

智能体（Agent）是能够感知环境、做出决策并采取行动的自主实体。在 LLM 时代，智能体以大模型为"大脑"，结合工具调用、记忆和规划能力，完成复杂任务。本文梳理智能体开发的核心概念、设计原则、架构模式和框架选型。

---

## 一、核心概念

### 1.1 什么是 AI Agent

AI Agent = LLM + 记忆 + 工具 + 规划

| 组件 | 说明 | 示例 |
|------|------|------|
| LLM | 推理与决策的核心 | GPT-4o、Claude、Gemini |
| 记忆 | 短期（上下文）+ 长期（知识库） | 对话历史、向量数据库 |
| 工具 | 与外部世界交互的能力 | 搜索、数据库、API、代码执行 |
| 规划 | 任务分解与执行策略 | ReAct、Plan-and-Execute、Reflexion |

### 1.2 Agent 与普通 LLM 调用的区别

| 维度 | 普通 LLM 调用 | Agent |
|------|-------------|-------|
| 交互模式 | 单轮请求-响应 | 多轮自主决策循环 |
| 工具使用 | 无 | 可调用外部工具 |
| 状态管理 | 无状态 | 有记忆和状态 |
| 执行方式 | 一次性输出 | 观察-思考-行动循环 |
| 错误处理 | 需人工介入 | 可自主重试和修正 |

### 1.3 Agent 的能力层级

```
Level 0: 纯对话（Chat）           — 无工具，无记忆
Level 1: 工具调用（Tool Use）     — 单轮工具调用
Level 2: ReAct 循环               — 观察-思考-行动循环
Level 3: 多步规划（Planning）     — 任务分解 + 逐步执行
Level 4: 多 Agent 协作（Multi-Agent）— 角色分工 + 协同工作
```

## 二、设计原则

### 2.1 单一职责

每个 Agent 只负责一个明确的职责。职责越清晰，输出越可靠。

| 做法 | 示例 |
|------|------|
| ✅ 一个 Agent 一个角色 | 研究员负责调研，作家负责写作，审校负责审核 |
| ❌ 一个 Agent 做所有事 | "万能助手"既调研又写作又审核 |

### 2.2 最小权限

Agent 只能访问其职责所需的工具和数据，避免越权操作。

| 角色 | 需要的工具 | 不需要的工具 |
|------|-----------|------------|
| 研究员 | 搜索、网页抓取 | 数据库写入、文件删除 |
| 代码执行器 | 代码运行（沙箱） | 生产数据库访问 |
| 审核员 | 只读访问 | 任何写入操作 |

### 2.3 可观测性

Agent 的每一步决策和行动都应可追踪、可调试。

- 记录每步的输入、输出和推理过程
- 关键决策点支持人工审批（Human-in-the-loop）
- 提供执行日志和回放能力

### 2.4 容错与重试

Agent 必须能处理工具调用失败、LLM 输出异常等场景。

| 场景 | 处理策略 |
|------|---------|
| 工具调用失败 | 重试 + 降级方案 |
| LLM 输出格式错误 | 解析重试 + 结构化输出约束 |
| 循环死锁 | 最大轮次限制 + 超时机制 |
| 任务未完成 | 持久化状态 + 断点恢复 |

### 2.5 成本控制

不同任务使用不同模型层级，避免"全程用最贵模型"。

| 任务类型 | 推荐模型层级 | 理由 |
|---------|------------|------|
| 路由/分类 | 小模型（haiku/mini） | 速度快、成本低 |
| 日常执行 | 中阶模型（sonnet/4o-mini） | 性价比最优 |
| 规划/评审 | 高阶模型（opus/4o） | 需要深度推理 |

## 三、架构模式

### 3.1 ReAct（推荐起点）

最经典的 Agent 模式：观察（Observe）→ 思考（Think）→ 行动（Act）循环。

```
用户输入 → LLM 思考 → 选择工具 → 执行 → 观察结果 → 继续思考或输出
                ↑                                    |
                └────────────────────────────────────┘
```

适用场景：简单到中等复杂度的任务，需要工具调用的单 Agent 场景。

### 3.2 Plan-and-Execute

先规划再执行，适合复杂多步任务。

```
用户输入 → Planner 分解任务 → Executor 逐步执行 → 验证结果
                ↑                              |
                └──── 发现问题，重新规划 ────────┘
```

适用场景：任务步骤多、依赖关系复杂、需要全局视角的场景。

### 3.3 Supervisor（多 Agent 推荐）

一个中心 Supervisor 调度多个专职 Agent。

```
                    Supervisor（调度中心）
                   /    |    \     \
              Agent1 Agent2 Agent3 Agent4
               ↑      ↑      ↑      ↑
               └──────┴──────┴──────┘
                  结果汇总回 Supervisor
```

适用场景：任务涉及多个领域、需要角色分工的团队协作。

### 3.4 Swarm（对等协作）

Agent 之间直接交接任务，无中心调度。

```
Agent A → 完成子任务 → 交接给 Agent B → 完成子任务 → 交接给 Agent C
```

适用场景：流程相对固定、Agent 间依赖关系明确的流水线。

### 3.5 层级式（Hierarchical）

多层管理结构，适合大型项目。

```
              CEO Agent
             /         \
        Manager1     Manager2
        /    \         /    \
     Worker1 Worker2 Worker3 Worker4
```

适用场景：团队规模大、需要分层管理的复杂项目。

### 3.6 架构选择指南

| 场景 | 推荐架构 | 理由 |
|------|---------|------|
| 单一任务 + 工具调用 | ReAct | 简单直接，上手快 |
| 复杂多步任务 | Plan-and-Execute | 先规划后执行，减少盲目性 |
| 多角色协作 | Supervisor | 中心调度，可控性强 |
| 固定流水线 | Swarm | 去中心化，低延迟 |
| 大型团队 | 层级式 | 分层管理，职责清晰 |

## 四、关键设计要素

### 4.1 系统提示词（System Prompt）

系统提示词是 Agent 的"岗位说明书"，直接决定行为质量。

**好提示词的结构**：
```
你是一个 [角色名]。

## 职责
[1-2 句话描述核心职责]

## 工作方式
1. [具体步骤 1]
2. [具体步骤 2]
3. [具体步骤 3]

## 约束
- [禁止事项 1]
- [禁止事项 2]

## 输出格式
[期望的输出格式]
```

**关键原则**：
- 明确角色边界，避免职责重叠
- 提供具体的工作步骤，而非模糊描述
- 列出禁止事项，比正面描述更有效
- 指定输出格式，减少解析错误

### 4.2 工具设计

| 原则 | 说明 | 示例 |
|------|------|------|
| 描述精确 | 工具描述决定 LLM 何时调用 | ✅ "搜索技术文档，返回摘要" ❌ "搜索东西" |
| 参数明确 | 每个参数有类型、描述和约束 | `city: str = Field(description="城市名称，如'北京'")` |
| 错误友好 | 工具返回可理解的错误信息 | ✅ "未找到城市'xyz'，请检查拼写" ❌ `None` |
| 幂等安全 | 相同输入产生相同结果，无副作用 | 查询类工具天然幂等，写入类需谨慎 |

### 4.3 记忆设计

| 记忆类型 | 用途 | 实现方式 |
|---------|------|---------|
| 短期记忆 | 当前对话上下文 | 消息列表 / State |
| 工作记忆 | 当前任务进度 | boulder 状态 / tasks.md |
| 长期记忆 | 跨会话知识 | 向量数据库 / notepad wisdom |
| 语义记忆 | 领域知识 | RAG / 知识图谱 |

### 4.4 人机交互（Human-in-the-Loop）

| 交互点 | 触发条件 | 实现方式 |
|--------|---------|---------|
| 计划审批 | 规划完成后 | interrupt_before + 人工确认 |
| 关键操作 | 涉及写入/删除 | 工具调用前确认 |
| 质量检查 | 验证不通过 | 人工审核 + 修改后继续 |
| 异常处理 | Agent 无法解决 | 暂停并通知人工 |

### 5.1 主流框架对比

| 维度 | AutoGen | CrewAI | LangGraph |
|------|---------|--------|-----------|
| 编排方式 | 对话驱动 | 角色扮演 | 图状态机 |

| 灵活性 | 中 | 中 | 高 |
| 循环/分支 | 有限（对话轮次） | 有限（顺序/层级） | 完整支持（条件边） |
| 持久化 | 有限 | 有限 | Checkpoint（内存/SQLite/Postgres） |
| 人机协作 | 强（human_input_mode） | 中（human_input） | 强（interrupt_before） |
| 流式输出 | ✅ | ✅ | ✅ |
| 学习曲线 | 低 | 低 | 中 |
| 适用场景 | 代码生成/对话协作 | 团队角色协作 | 复杂工作流/生产级应用 |
| 维护方 | 微软 | CrewAI Inc | LangChain 团队 |

## 六、MCP 协议

MCP（Model Context Protocol）是 AI 模型与外部工具/数据的标准通信协议，为 Agent 提供统一的工具接入层。

### 6.1 架构

```
Host (LLM App) ←→ Client (MCP 客户端) ←→ Server (工具/数据)
```

Server 提供三类能力：
- **Tools**：可调用的函数
- **Resources**：可读取的数据
- **Prompts**：预定义的提示词模板

### 6.2 MCP Server 示例

```python
from mcp.server import Server
from mcp.types import Tool, TextContent

server = Server("my-tools")

@server.list_tools()
async def list_tools():
    return [
        Tool(
            name="get_weather",
            description="获取城市天气",
            inputSchema={
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"}
                },
                "required": ["city"],
            },
        )
    ]

@server.call_tool()
async def call_tool(name, arguments):
    if name == "get_weather":
        city = arguments["city"]
        weather = fetch_weather(city)
        return [TextContent(type="text", text=f"{city}: {weather}")]
```

## 七、开发实践清单

### 7.1 开发前

- [ ] 明确 Agent 的职责边界（做什么 / 不做什么）
- [ ] 选择合适的架构模式（ReAct / Supervisor / Swarm）
- [ ] 设计 State 结构（传递什么数据）
- [ ] 列出所需工具及其接口定义
- [ ] 确定人机交互点

### 7.2 开发中

- [ ] 系统提示词清晰具体，包含角色/步骤/约束/输出格式
- [ ] 工具描述精确，参数有类型和约束
- [ ] 实现错误处理和重试逻辑
- [ ] 添加执行日志和可观测性
- [ ] 设置最大轮次 / 超时防止死循环

### 7.3 开发后

- [ ] 用典型场景测试 Agent 行为
- [ ] 检查边界情况（工具失败、格式错误、循环）
- [ ] 评估 token 消耗和延迟
- [ ] 添加持久化（长时间任务）
- [ ] 编写使用文档和示例

### 7.4 常见陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|---------|
| 角色模糊 | Agent 输出不一致 | 精简系统提示词，明确职责边界 |
| 工具过多 | Agent 选错工具 | 每个Agent 限制 3-5 个工具 |
| 无限循环 | Agent 反复调用同一工具 | 设置 max_round + 循环检测 |
| 状态膨胀 | State 越来越大 | 定期清理，只保留必要字段 |
| 幻觉工具调用 | 调用不存在的工具 | 严格约束工具列表，添加校验 |
| 上下文溢出 | 超出 token 限制 | 摘要压缩 + 滑动窗口 |
