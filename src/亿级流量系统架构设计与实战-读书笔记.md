## 第一篇：架构知识篇

### 第1章 大型互联网公司的基础架构

#### 1.1 单机房内部架构

一个用户请求的完整链路：

```
客户端 → DNS/HTTPDNS → LVS(四层) → Nginx(七层) → HTTP服务 → RPC服务 → 存储层
                                                            → 服务发现
                                                            → 消息中间件
```

各角色职责：
- **DNS/HTTPDNS**：域名到公网IP的映射，客户端连接机房的第一跳
- **LVS**：四层负载均衡，对外提供机房入口VIP，高性能转发（内核态）
- **Nginx**：七层反向代理，按HTTP URL路由到不同业务服务，支持Lua脚本热更新upstream
- **HTTP服务**：校验用户请求、打包响应，核心逻辑委托RPC执行（即HTTP对外的接口层）
- **RPC服务**：执行核心业务逻辑，是真正的"微服务"
- **存储层**：分布式缓存(Redis) + 关系型数据库(MySQL) + NoSQL
- **服务发现**：维护服务实例的动态地址列表，支持注册/发现/订阅推送
- **消息中间件(Kafka)**：异步化、解耦、流量削峰填谷

#### 1.2 DNS（域名系统）

**域名层次结构**：根 → 顶级域名(.com/.net/.cn) → 二级域名(google.com) → 三级域名(mail.google.com)

**4类域名服务器**：
1. **根DNS**：全球13台IPv4根服务器，管理全部顶级域名
2. **顶级DNS**：管理二级域名，返回权威DNS地址
3. **权威DNS**：最终决定域名→IP的映射，大型厂商自建
4. **本地DNS**：运营商提供，缓存解析结果，加速查询

**递归解析流程**：
```
客户端缓存 → 本地DNS → 根DNS(返回顶级DNS) → 顶级DNS(返回权威DNS) → 权威DNS(返回IP)
```

**解析记录格式**：
```
Domain             TTL    Class   Type     Rdata
www.baidu.com      600s   IN      A        1.1.1.1
```

#### 1.3 HTTPDNS

**DNS的三大问题**：
1. 递归查询导致高延迟（实际可达1s以上）
2. 运营商调度不准（获取的是本地DNS IP而非真实用户IP，且存在域名转发）
3. **DNS劫持**（腾讯2014年日解析异常超80万条）

**HTTPDNS原理**：
- 客户端通过HTTP协议直连HTTPDNS服务器（固定IP，如5.5.5.5），绕过运营商本地DNS
- HTTDNS服务器向权威DNS查询，基于真实客户端IP返回最优地址

**实现策略**：
- 安全：使用HTTPS
- IP选取：多个最优IP按顺序下发，客户端校验连通性后选择
- 批量拉取：冷启动或网络切换时批量预拉取域名映射表
- 容灾：HTTPDNS → 降级本地DNS → 兜底IP（服务端下发）

**对比**：
| 维度 | DNS | HTTPDNS |
|------|-----|---------|
| 延迟 | 递归多级，可达1s+ | 直连，毫秒级 |
| 劫持风险 | 高 | 无 |
| 调度精度 | 本地DNS IP | 真实客户端IP |
| 生效速度 | 受TTL缓存限制 | 实时 |

#### 1.4 接入层技术演进

**1.4.1 Nginx（七层负载均衡）**

常见负载均衡策略：
| 策略 | 原理 | 适用场景 |
|------|------|----------|
| 轮询 | 时间序列轮流分配 | 默认策略 |
| 加权轮询 | weight值越大分配越多 | 服务器性能不均 |
| ip_hash | 同一IP固定访问同一服务器 | 需要Session保持 |
| least_conn | 分配给连接数最少者 | 请求处理时间差异大 |
| url_hash | 按URL哈希 | 提高缓存命中 |
| fair | 综合响应时间、失败数等 | 动态负载均衡 |

**Nginx配置文件示例（核心结构）**：
```nginx
worker_processes 3;
events { worker_connections 1024; }

http {
    upstream api_friendy_feed {
        server 10.1.0.1:8080;
        server 10.1.0.2:8080;
    }
    server {
        listen 80;
        server_name api.friendy.com;
        location /feed {
            proxy_pass http://api_friendy_feed;
        }
    }
}
```

**动态服务发现**：Lua脚本定时（3s）从服务注册中心拉取最新地址列表 + ngx_http_dyups_module热更新

**1.4.2 LVS（四层负载均衡）**

核心概念：DS(Director Server)、RS(Real Server)、VIP(虚拟IP)、RIP(Real IP)、CIP(Client IP)

4种转发模式对比：

| 模式 | 机制 | 优势 | 劣势 |
|------|------|------|------|
| NAT | 修改目标IP+端口 | RS无需配置VIP | DS需做网关，响应也经DS，性能一般 |
| FULLNAT | NAT + 修改源IP | 网络环境要求低 | 丢失客户端IP |
| TUN | IP隧道封装 | 响应不经DS，性能好 | 需支持IP隧道，RS配VIP |
| DR | 修改MAC地址 | 性能最好 | DS/RS同物理网络，RS配VIP在lo网卡 |

**推荐**：FULLNAT（通用性强）或DR（极致性能）

**最终接入层架构**：
```
DNS轮询 → 多LVS节点(多个VIP) → Keepalived主从热备(VIP漂移) → Nginx集群 → 业务HTTP服务
```

**Keepalived + VIP 主从热备**：
- 主节点通过ARP告知局域网：VIP对应MAC-A
- 从节点监听到主节点宕机后，发送ARP包：VIP对应MAC-B
- 网络设备自动转向从节点，对客户端透明

#### 1.5 服务发现

**核心能力**：服务注册 + 服务发现 + 地址推送

**注册与发现流程**：
```
1. 服务B实例启动 → 注册地址到服务注册中心
2. 调用者A → 查询/订阅服务B的地址
3. 注册中心 → 返回可用地址列表
4. A → 选择实例发起RPC调用
```

**可用地址管理**：
- 心跳探活（推荐）：实例定期(30s)发送心跳包，注册中心超过阈值(150s)未收到即摘除
- 主动探活（仅适合小型系统）
- **地址摘除保护**：摘除比例超过30%则停止摘除并报警，防止误摘

**地址变更推送**：
- 增量推送优于全量推送
- 推拉结合防推送风暴：最多推N个节点，其余定期(1min)拉取

#### 1.6 RPC服务

**RPC vs HTTP**：
- HTTP服务：面向外部，校验请求、打包响应（类似网关）
- RPC服务：面向内部，执行核心业务逻辑

**RPC通信流程**：
```
调用方：对象 → 序列化 → 编码 → 网络发送
被调用方：网络接收 → 解码 → 反序列化 → 执行方法 → 序列化结果返回
```

**RPC示例（Thrift协议定义）**：
```thrift
namespace go calculator

struct BinaryReq {
    1: required i64 Operator1,
    2: required i64 Operator2,
}

struct Response {
    1: required i64 Result,
}

service CalculatorService {
    Response Add(1: BinaryReq req)
    Response Sub(1: BinaryReq req)
    Response Multiply(1: BinaryReq req)
    Response Division(1: BinaryReq req)
}
```

#### 1.7 MySQL高可用

**1.7.3 主从模式（基础）**

主从复制三步：
1. Master：提交事务 → 写入binlog
2. Slave I/O线程：读取Master binlog → 写入本地relay log
3. Slave SQL线程：从relay log读取 → 重新执行SQL → 数据回放

- **异步复制**：Master提交即返回，Slave可能未收到 → 可能丢数据
- **半同步复制**：Master等待至少一个Slave确认收到binlog(ACK)后才提交
- **复制风暴**：太多Slave拖垮Master → Slave级联复制

**1.7.4 MHA（推荐）**

MHA = MHA Manager(决策层) + MHA Node(数据节点)

故障转移流程：
1. Manager连续4次心跳探测失败 → 判定Master宕机
2. 选择binlog最新（数据最接近Master）的Slave作为备选
3. Node尝试SSH获取Master binlog，补差异数据
4. 备选Slave提升为新Master，其他Slave重新指向

**配合半同步复制可大幅降低数据丢失风险**（因为至少有一个Slave与Master数据一致）

**1.7.5 MMM（不推荐）**
- 双Master架构，通过write_vip漂移切换
- 社区无人维护，不支持MySQL GTID

**1.7.6 MGR（强一致场景）**
- 基于Paxos共识算法，至少3节点
- 事务须经组内超过半数节点决议通过方可提交
- 单主模式（推荐）vs 多主模式（冲突多）
- 写性能不及异步/半同步，但数据不丢失

#### 1.8 Redis高可用

**1.8.1 主从模式**
```
Slave连接 → 发送PSYNC → Master执行BGSAVE生成RDB快照 → 全量传输
→ Slave加载RDB到内存 → Master传输增量命令 → Slave回放
```

**1.8.2 哨兵模式**
- 若干Sentinel节点持续监控Master/Slave心跳
- 超过N个Sentinel判定Master宕机 → 协商选举新Master
- 客户端先访问Sentinel获取Master地址，故障后自动获取新地址

**1.8.3 集群模式（Redis Cluster）**

核心机制：**16384个哈希槽**，CRC16(Key) mod 16384 → 槽位 → 对应Master

Gossip协议消息类型：
- **meet**：通知节点加入集群
- **ping**：交换状态和槽位信息
- **pong**：响应meet/ping，也可主动广播变更
- **fail**：通知某节点宕机

节点故障转移：主观下线（单节点判定） → 客观下线（超过半数判定） → 从节点接管槽位并提升为Master

**Gossip风暴问题**：节点成千上万时，Gossip通信占用大量网络带宽

**1.8.4 中心化集群（Codis，推荐大规模使用）**

Codis = Codis Server(改造的Redis) + Codis Proxy(Twemproxy思路) + ZooKeeper集群 + Codis Dashboard/FE

**槽位分配**：CRC32(Key) mod N（N默认1024）

**平滑扩缩容**：
```
源节点(A)迁移槽位S到目标节点(B)：
1. A复制槽位S数据到B（A仍对外服务）
2. 请求到达A且数据属于槽位S → 强制将此数据迁移到B → 转发请求到B处理
3. 完成迁移
```

**集群模式 vs Codis对比**：
| 维度 | Redis Cluster | Codis |
|------|--------------|-------|
| 架构 | 去中心化 | 中心化(Proxy) |
| 扩缩容 | 需手动管理 | Dashboard可视化 |
| 大规模节点 | Gossip风暴 | ZooKeeper协调 |
| 运维复杂度 | 较高 | 较低(Dashboard) |

#### 1.9 LSM Tree（对数结构合并树）

核心洞察：**磁盘顺序读写性能远高于随机读写**（适用于HDD和SSD）

**组成部分**：
| 组件 | 存储位置 | 特性 |
|------|---------|------|
| MemTable | 内存 | Key有序，写请求直接处理 |
| Immutable MemTable | 内存 | MemTable满后变只读，等待刷盘 |
| SSTable | 磁盘 | Level组织，Key有序不可变，稀疏索引 |
| WAL | 磁盘 | 预写日志，保证数据可靠性 |

**写流程**：
```
WAL(记录命令) → MemTable(内存写入) → Immutable MemTable(满即冻结) 
→ SSTable(持久化到L0) → Compaction(合并下沉到L1、L2...)
```

**读流程**：MemTable → Immutable MemTable → L0 SSTable → L1 → ... → Ln（逐层查找，首次命中即返回）

**写操作处理**：
- 新增：直接插入MemTable
- 修改：覆盖或插入
- 删除：标记为tombstone（墓碑），不物理删除

**Compaction（合并压缩）**：
- LCS策略：每层SSTable大小一致(默认160MB)，高层总大小阈值更高
- Ln满 → 选择1个SSTable + Ln+1中有交集的SSTable合并
- 合并后去冗余（同Key保留最新值），新SSTable下沉到Ln+1

#### 1.11 Kafka消息中间件

**3大用途**：
1. **异步化**：非核心服务异步处理，大幅降低用户请求响应时间
2. **流量削峰**：消费者按自身处理能力拉取，10000QPS平滑为100QPS
3. **解耦**：生产者投递事件到Topic，消费者订阅，互不影响

**核心概念**：
```
Producer → Topic → [Partition1(Leader+Follower), Partition2, ...] → Consumer Group
```

**Kafka关键设计**：
- Partition内消息有序(按Key)，Partition间无序
- Consumer Group内每个Partition只能被一个消费者消费
- ZooKeeper负责：Broker注册、Topic元信息、生产者/消费者负载均衡、消费进度Offset
- 消费者拉模式（pull）：自己控制消费速度

**高可用（ISR机制）**：
- 每个Partition有1个Leader + 若干Follower（分布在不同的Broker上）
- ISR = 与Leader保持数据一致的Follower列表
- 写入成功条件：ISR中所有Follower都确认收到
- Leader宕机 → Controller（通过ZooKeeper分布式锁选举）从ISR选新Leader
- ISR是同步复制和异步复制的折中

#### 1.12-1.14 多机房架构三阶段

**1.12 主备机房**
- 备机房完全复制主机房架构，通过专线做存储层主从复制
- 主机房故障 → 备机房从库提升为主库 → DNS指向备机房
- 缺点：资源浪费（备机房闲置），切换有损

**1.13 同城双活（最常用）**

关键设计：
1. **存储层**：A机房主库，B机房从库；B机房写请求跨机房访问A机房主库（通过专线，延迟仅+5ms）
2. **读请求**：各机房处理本机房读请求
3. **分流策略**：按DeviceID哈希映射，分流配置平台准实时下发
4. **切流**：客户端+配置平台(`lower/upper`范围映射到域名)，比DNS更灵活

**两地三中心**：同城双活 + 异地灾备中心

**1.14 异地多活（全球级）**

两大要素：
1. **各机房闭环写**：每个机房独立部署存储主库，写请求本机房处理
2. **数据互通**：各机房主库通过DRC双向复制数据

**MySQL DRC核心要点**：
- **伪从**：Sync-out模拟Slave协议获取binlog（Canal/Databus开源）
- **断点续传**：利用GTID定位binlog位置
- **数据防重**：Sync-in保存已写入GTID集合
- **防止数据回环**：辅助表标记，Sync-out检查不传输来自其他机房的事务
- **数据冲突**：LWW策略(最后写入者胜利)不精确 → 尽量靠分流避免冲突（分布式ID避免自增主键）

**Redis DRC核心要点**：
- 伪从：Sync-out模拟从库向主库复制
- GTID替代：自研单调递增ID绑定每条写命令
- 防回环：改造Redis客户端标志(`REDIS_SYNC_IN`/`REDIS_SYNC_OUT`)，主库识别Sync-in命令不复制

**分流策略**：
- DNS按地域配置 → 结合注册国策略（用户注册时记录国家，后续固定路由到该国对应的机房）
- 长期出国用户自动变更注册国

**数据复制链路**：
- N个机房间网状双向复制链路数：C(N,2)，易激增
- 优化为星状结构：指定中心机房中转，减少链路数

### 第2章 通用的高并发架构设计

#### 2.1 高并发三要素

1. **高性能指标**：PCTn分位值优于平均值
   - PCT50 = 1ms, PCT99 = 800ms, PCT999 = 1.2s
   - 经验标准：平均200ms + PCT99 = 1s 满足高性能

2. **高可用性指标**：N个9

| 可用性 | 一年故障时间 | 一日故障时间 |
|--------|-------------|-------------|
| 90% (1个9) | 36.5天 | 2.4h |
| 99% (2个9) | 3.65天 | 14.4min |
| 99.9% (3个9) | 8h | 1.44min |
| 99.99% (4个9) | 52min | 8.6s |
| 99.999% (5个9) | 5min | 0.86s |

推荐：99.95%（3个9+1个5）作为告警阈值

3. **可扩展性** = 吞吐量提升比例 / 集群节点增加比例，70%-80%即满足要求

**高并发场景分类**：高并发读（读写分离/缓存/CQRS）和高并发写（数据分片/异步化）

---

#### 2.2 高并发读方案1：读写分离

架构：Master写 + 多Slave读，通过主从复制同步

路由方式：
- Proxy代理：MySQL-Proxy、MyCat（中心化代理，transparent）
- 应用内嵌：ShardingJDBC、gorm（客户端路由）

**主从延迟3种解决方案**：
1. **同步复制**：Master等所有Slave确认后才返回（性能差，低并发场景适用）
2. **强制读主**：高一致性要求场景不走Slave，直接读Master
3. **会话分离**：写操作后短时间内该会话的读请求强制读主（时长略高于主从延迟）

---

#### 2.3 高并发读方案2：本地缓存

**淘汰策略对比**：

| 策略 | 原理 | 优缺点 |
|------|------|--------|
| FIFO | 先进先出 | 命中率极低，少用 |
| LFU | 访问计数最低者淘汰 | 新数据易淘汰，旧高频数据赖着不走 |
| LRU | 最近最少使用淘汰 | 批量访问/偶发访问会冲掉热点 |
| **W-TinyLFU** | LFU+LRU结合 | 高命中率+低内存，Redis/Caffeine使用 |

**W-TinyLFU详解**：
- Window LRU段(1%空间)：LRU策略，首次访问数据放这里
- Segment LRU段(99%空间)：
  - probation段(20%)：最近访问1次
  - protected段(80%)：最近访问≥2次
- 淘汰时比较probation段即将淘汰数据和新数据的访问频率

**访问频率记录**：Count-Min Sketch算法
- M个哈希函数 × N列二维数组，每次访问对M个位置+1
- 查询时取M个位置的最小值
- 每位置仅4bit（0-15），时间衰减：全局计数达阈值时所有值÷2

**缓存击穿与SingleFlight**：

问题：热点数据过期瞬间，大量并发请求穿透到数据库

**SingleFlight核心原理**：
- 使用WaitGroup控制：第一个请求Add(1)+执行数据获取，其他请求Wait()阻塞
- 数据获取完成Done()唤醒所有等待请求，共享结果
- 10个并发请求仅执行1次数据库查询

**核心源码逻辑**：
```go
type call struct {
    wg sync.WaitGroup
    val interface{}
    err error
    dups int
}

func (g *Group) Do(key string, fn func() (interface{}, error)) {
    g.mu.Lock()
    if c, ok := g.m[key]; ok {
        c.dups++
        g.mu.Unlock()
        c.wg.Wait()  // 等待正在执行的请求完成
        return c.val, c.err, true
    }
    c := new(call)
    c.wg.Add(1)
    g.m[key] = c
    g.mu.Unlock()
    g.doCall(c, key, fn)  // 执行fn
    return c.val, c.err, c.dups > 0
}
```

#### 2.4 高并发读方案3：分布式缓存

Redis vs Memcached：
| 维度 | Redis | Memcached |
|------|-------|-----------|
| 数据类型 | String/List/Set/Hash/ZSET等 | 仅String |
| 持久化 | RDB + AOF | 无 |
| 高可用 | 主从/哨兵/集群 | 无内置 |
| 分布式 | Cluster/Codis/Twemproxy | 客户端一致性哈希 |

**缓存穿透**：访问不存在的非法Key → 布隆过滤器 + 缓存空值
- 布隆过滤器：m位向量 + k个哈希函数，存在可能误判，不存在一定准确

**缓存雪崩**：大量Key同时过期 → 过期时间加随机偏移

**缓存更新策略对比**：

| 策略 | 流程 | 一致性 | 适用场景 |
|------|------|--------|---------|
| **Cache Aside** | 先更新DB → 再删除缓存 | 最终一致 | 推荐 |
| Read/Write Through | 缓存层代理读写 | 强一致 | 对缓存要求高 |
| Write Behind | 先写缓存 → 异步写DB | 弱一致 | 写密集场景 |

**为什么是"先更新DB删缓存"而非"先删缓存更新DB"**？
- 并发场景：先删缓存 → B读到旧数据回填缓存 → A更新DB → 缓存与DB永久不一致
- 先更新DB删缓存：概率极低（A更新DB后删缓存，B此时读到旧数据需A未删缓存+DB主从延迟+B读在A删前）

#### 2.5 高并发读总结：CQRS

**CQRS = 读写分离的终极形态**：

```
写侧：Command服务 → MySQL主库（处理事务、强一致）
读侧：Query服务 → MySQL从库 + Redis + ES + 搜索索引
同步：binlog → 消息队列 → 异步构建各种读视图
```

适用条件：读远大于写、读写模型差异大

#### 2.6 高并发写方案1：数据分片

**垂直拆分**：
- 分库：不同业务归属不同数据库（解耦 + 独立扩容）
- 分表：核心字段 vs 大字段分离（提高核心数据缓存命中率，减少磁盘IO）
  ```
  商品表 → 商品基本信息表(名称、价格、图片) + 商品详情表(描述、说明，字段大)
  ```

**水平拆分**：
- 分库：同结构多库分散在不同服务器 → 提升并发处理能力
- 分表：同库内多表 → 解决单表数据量过大
- 分库分表：两者结合 → 分布式效果

**数据路由算法**：

| 算法 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| 范围分区 | ID/时间等按区间 | 查询友好，扩容方便 | 易产生热点 |
| 哈希分区 | Hash(Key) → 范围映射 | 分布均匀 | 扩容需迁移 |
| 一致性哈希 | 哈希环 + 顺时针查找 | 增减节点仅影响相邻 | 节点少时数据偏斜 |

**一致性哈希虚拟节点**：每个物理节点映射多个虚拟节点到哈希环，均匀分布防偏斜

**扩容方案：从库升级法（翻倍扩容）**：
1. 各分库已有从库（通过主从复制）
2. 主库封禁写请求
3. 确认主从数据一致 → 断开主从关系
4. 原主库数据范围缩为前一半，从库提升为新主库覆盖后一半
5. 上游感知路由变更 → 解封写请求
6. 离线任务删除各库冗余的半边数据

**其他数据分片形式**：
- Kafka Partition并行写入提升吞吐
- 秒杀系统：库存分N段 + N个分布式锁，并行度提升N倍
- ConcurrentHashMap：分段锁，减少竞争

#### 2.7 高并发写方案2：异步写与写聚合

**异步写**：
```
业务服务 → 消息队列(Kafka) → 消费者批量写DB
```
用户请求立即返回，写操作异步执行，降低响应时间。

**写聚合**：短时间内同一Key的多次写合并为一次写入（如点赞数，1s内积累后统一次写入）

### 第3章 通用的服务可用性治理手段

#### 3.1 微服务与网络调用问题

微服务通过多级网络调用形成依赖链，网络天然脆弱（超时、抖动、断开），需要：
- **容错性设计**：接受故障现实，有容错方案
- **流量控制**：既防止上游打垮自己，也感知下游质量下滑

---

#### 3.2 重试

**幂等接口 = 可安全重试的前提**

读接口天然幂等。写接口实现幂等方案：

| 方案 | 实现 | 有效期 |
|------|------|--------|
| Redis分布式锁 | `SET UUID EX 3600 NX` | 由EX参数控制 |
| 数据库防重表 | UUID做唯一索引，insert即去重 | 永久 |
| Token令牌 | 先取token再携带调用，删token防重 | 一次 |

**CAS思想实现幂等更新**：
```sql
-- 非幂等
UPDATE table1 SET coll=coll+1 WHERE col2=Y
-- 幂等
UPDATE table1 SET coll=coll+1 WHERE version=X AND col2=Y
```

**重试时机**：
- 业务逻辑错误 → 不重试
- 服务质量异常 → 用退避策略（指数退避，给下游恢复时间）
- 网络错误 → 立即重试（随机性大）

**退避策略**：
| 策略 | 行为 | 适用 |
|------|------|------|
| 无退避 | 立即 | 网络错误 |
| 线性退避 | 等待固定时间 | 简单场景 |
| 指数退避 | 1s→2s→4s→8s... | 服务质量异常 |
| 综合退避 | 指数+随机 | 消息中间件 |

**重试风暴**：
- 问题：多级重试叠加放大流量
- 解决：限制最大重试次数（建议最多重试2次） + 重试请求比监控告警

---

#### 3.3 熔断与隔离

**服务雪崩**：下游故障 → 上游线程池耗尽 → 级联崩溃

**熔断器三态**：
```
Closed(正常) --失败率超阈值--> Open(熔断，快速失败)
Open --等待冷却时间--> Half-Open(放少量请求试探)
Half-Open --成功--> Closed | --失败--> Open
```

代表实现：Hystrix、Resilience4j、Sentinel

**舱壁隔离**：不同依赖使用独立线程池/信号量，一个下游故障不拖垮其他接口。

---

#### 3.4 限流

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 固定窗口 | [0,s]计数 | 简单 | 窗口边界流量翻倍 |
| 滑动窗口 | 窗口持续滑动 | 平滑 | 实现复杂 |
| 漏桶 | 恒定速率流出 | 流量规整 | 无法应对突发 |
| **令牌桶** | 恒定速率生成令牌，请求取令牌 | 允许突发 | 最常用 |

**全局限流**：Redis中心化计数，实现集群级限流

---

#### 3.5 自适应限流

根据实时系统指标动态调整阈值：
- 基于请求排队时间
- 基于延迟比率（P99）
- 基于系统负载（CPU/内存/队列长度）

---

#### 3.6 降级策略

- **服务依赖度降级**：强依赖保留，弱依赖可关闭（如推荐服务宕机不影响核心发帖）
- **读请求降级**：返回缓存/兜底数据（不保证实时性）
- **写请求降级**：异步写消息队列，后续补写（允许短暂数据不一致）

### 第4章 唯一ID生成器

#### 分布式唯一ID要求

全局唯一 + 趋势递增（或单调递增） + 高性能 + 高可用

**单调递增 vs 趋势递增**：
- 单调递增：严格递增（如Redis INCRBY），适合对ID顺序有要求的场景
- 趋势递增：整体递增但有局部抖动（如Snowflake），性能更高

---

#### 4.2 单调递增方案

**Redis INCRBY**：原子自增，依赖Redis可用性 → 需AOF持久化 + 主从保证

**数据库自增主键**：`AUTO_INCREMENT` + `REPLACE INTO`技法（先删后插获取新ID） → 需高可用架构

---

#### 4.3 Snowflake算法（趋势递增）

**ID结构（64bit）**：
```
| 1bit(符号位，0) | 41bit(毫秒时间戳) | 10bit(机器ID) | 12bit(序列号) |
```

- 41bit时间戳：可用约69年
- 10bit机器ID：1024个服务实例
- 12bit序列号：每毫秒4096个ID

**时钟回拨**：NTP同步导致时间倒退
- 检测到回拨 → 拒绝服务或等待追回
- 备选：上次时间戳不再依赖系统时钟，改用本地递增

**机器ID分配**：ZooKeeper顺序节点/数据库自增分配

---

#### 4.4 号段模式（趋势递增，基于DB）

- 从DB批量获取一段ID（如step=1000），缓存在本地
- 双Buffer：当前号段用到一定比例时，异步加载下一段
- 优点：性能极高（本地分配），对DB压力小

---

#### 4.5 美团Leaf

- **Leaf-segment**：号段模式 + 双Buffer优化 + 动态调整step
- **Leaf-snowflake**：Snowflake + ZooKeeper分配WorkerID + 时间戳与时钟回拨保护

### 第9章 排行榜服务

#### 9.1 Redis ZSET方案

```bash
ZADD rank:{board_id} {score} {user_id}     # 更新分数
ZREVRANK rank:{board_id} {user_id}         # 获取排名（0-based）
ZREVRANGE rank:{board_id} 0 99 WITHSCORES  # Top 100
```

**幂等更新**：点赞+1/取消-1 → 先查当前分数再更新（或使用ZINCRBY处理正负增量）

**同积分处理**：按ZSET的字典序（默认按member），或调整score包含时间戳：`score = main_score + (1 - timestamp / MAX_TIMESTAMP)`

#### 9.2 大Key问题

单个ZSET过大 → 分片策略：按分数范围拆分为多个ZSET
- 如：rank:board_0_9999, rank:board_10000_19999, ...
- 查TopN：从最高分段的ZSET开始取，不够再到下一段

#### 9.3 粗估排行榜（线段树）

核心思想：将分数范围划分为固定数量的区间(bucket)，每个区间统计人数

**数据结构**：线段树，叶子节点为分数区间，非叶子节点为区间汇总

**查询排名**：累加所有高于目标分数的区间人数 + 目标区间内的精确排序

**复杂度**：O(log M)，M为区间数，比ZSET的O(log N)更快且几乎不受N影响

**精度计算**：
```
精度 ≈ 排名误差 / 总上榜人数
排名误差 ∈ [0, 区间人数]
区间越细 → 精度越高，但存储开销越大
```

#### 9.4 精确+粗估结合

- 列表展示：粗估排名（速度快，体验好）
- 点击查看详情：精确排名（按需计算，ZREVRANK）
- 热门榜单（如小时榜/日榜）：定期预计算精确排名，缓存结果

### 第10章 用户关系服务

#### 10.1 三方案对比

| 方案 | 存储模型 | 查询关注 | 查询粉丝 | 互关判断 | 扩展性 |
|------|---------|---------|---------|---------|--------|
| Redis ZSET | `following:{uid}`(关注时间→关注者ID) | ZREVRANGE快 | 需单独维护粉丝ZSET | ZINTERSTORE | 内存限制 |
| MySQL分库分表 | following表 + follower表 | SELECT +索引 | SELECT +索引 | JoIn/子查询 | 分片扩展 |
| 图数据库 | (User)-[:FOLLOWS]->(User) | 遍历一度关系 | 查入边 | 查双向边 | 天然扩展 |

#### 10.2 MySQL方案核心设计

**Following表**（我关注了谁）：
```sql
CREATE TABLE following (
    user_id BIGINT NOT NULL,        -- 用户ID
    following_id BIGINT NOT NULL,   -- 关注的用户ID
    created_at TIMESTAMP,           -- 关注时间
    PRIMARY KEY (user_id, following_id),
    INDEX idx_user_time (user_id, created_at)  -- 分页查询"我关注的人"
);
```

**Follower表**（谁关注了我）：
```sql
CREATE TABLE follower (
    user_id BIGINT NOT NULL,        -- 用户ID
    follower_id BIGINT NOT NULL,   -- 粉丝ID
    created_at TIMESTAMP,
    PRIMARY KEY (user_id, follower_id),
    INDEX idx_user_time (user_id, created_at)  -- 分页查询"我的粉丝"
);
```

**分库分表**：按user_id哈希分片，保证同一用户的数据在同一分片。

**索引优化防回表**：
```sql
-- 覆盖索引：查询字段全部在索引中，不回表
CREATE INDEX idx_user_following (user_id, following_id, created_at);
SELECT following_id, created_at FROM following WHERE user_id = ? ORDER BY created_at LIMIT 20;
```

**关注数/粉丝数**：Redis计数器（HINCRBY），定时与数据库对齐（最终一致）。

#### 10.3 缓存策略

- **缓存内容**：关注列表（分页）、粉丝列表（分页）、是否互关、关注数/粉丝数
- **更新策略**：Cache Aside（先更新DB → 删除缓存）
- **本地缓存**：热点用户（大V）的关注/粉丝数本地缓存

### 第11章 Timeline Feed服务

#### 11.1 三种模式对比

| 模式 | 写入时 | 读取时 | 存储模型 | 适用场景 |
|------|--------|--------|---------|---------|
| 拉模式 | 无操作 | 从所有关注者拉取 | 仅发件箱 | 关注数少、实时性低 |
| 推模式 | 写入所有粉丝收件箱 | 直接读收件箱 | 每个粉丝收件箱 | 粉丝数少（普通用户） |
| **推拉结合** | 选择性推 | 推的读+拉的合并 | 收件箱+发件箱 | 实际生产环境 |

#### 11.2 推拉结合策略

```
普通用户(粉丝<1万)：纯推模式 → 发文后推送到所有粉丝收件箱
活跃用户/大V(粉丝≥1万)：推拉结合
  - 推给在线粉丝
  - 离线粉丝上线后拉取
  - 大V的发件箱额外维护
```

#### 11.3 收件箱存储

**Redis ZSET方案**：
```
timeline:{user_id} → ZSET
  score = timestamp(发文时间)
  member = feed_id(内容ID)
```

- 读取：`ZREVRANGE timeline:{uid} 0 19`（最新20条）
- 写入：`ZADD timeline:{follower_id} {timestamp} {feed_id}`
- 容量控制：`ZREMRANGEBYRANK` 保持最多5000条

**MySQL方案**：
```sql
CREATE TABLE inbox (
    user_id BIGINT,
    feed_id BIGINT,
    author_id BIGINT,
    created_at BIGINT,
    PRIMARY KEY (user_id, created_at, feed_id)
);
```

#### 11.4 推送子任务

大V发文 → 将推送任务拆分为多个子任务 → 消息队列异步分发 → 各worker推送部分粉丝

控制并发：限制每个大V的推送worker数量，避免打爆系统

#### 11.5 读取请求

```
GET /timeline?last_id={last_feed_id}&limit=20
```

游标分页（last_id），防止Feed流重复/丢失（按时间排序时新内容插入导致偏移量失效）

### 第12章 评论服务

#### 12.1 三种评论模式

| 模式 | 结构 | 示例 | 复杂度 |
|------|------|------|--------|
| 单级模式 | 平铺列表 | 早期微博 | 低 |
| 盖楼模式 | 递归嵌套(`1.3.5`) | 网易新闻 | 中（递归展示） |
| **二级模式** | 一级评论+二级回复 | 微博、B站 | 高（多维度排序+高并发） |

#### 12.2 单级模式

```sql
CREATE TABLE comment (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    content_id BIGINT NOT NULL,    -- 被评论的内容ID
    user_id BIGINT NOT NULL,       -- 评论者
    content TEXT,
    created_at TIMESTAMP,
    INDEX idx_content_time (content_id, created_at DESC)
);
```

#### 12.3 盖楼模式

**路径存储法**（推荐）：
```sql
CREATE TABLE comment (
    id BIGINT PRIMARY KEY,
    content_id BIGINT,
    user_id BIGINT,
    content TEXT,
    path VARCHAR(500),             -- 楼层路径：如 "1$3$5"
    level INT DEFAULT 1,           -- 层级深度
    INDEX idx_content_path (content_id, path)
);
```
- 查所有评论：`ORDER BY path`即可得到嵌套顺序
- 回复楼中楼：path = 父评论path + "$" + 本评论ID

#### 12.4 二级模式（生产最常用）

**表设计**：

```sql
-- 一级评论表
CREATE TABLE comment_l1 (
    id BIGINT PRIMARY KEY,
    content_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    content TEXT,
    like_count INT DEFAULT 0,
    reply_count INT DEFAULT 0,     -- 二级回复数
    hot_score DOUBLE DEFAULT 0,    -- 热度分（排序用）
    status TINYINT DEFAULT 0,      -- 审核状态
    created_at TIMESTAMP,
    INDEX idx_content_hot (content_id, hot_score DESC),
    INDEX idx_content_time (content_id, created_at DESC)
);

-- 二级回复表
CREATE TABLE comment_l2 (
    id BIGINT PRIMARY KEY,
    l1_comment_id BIGINT NOT NULL, -- 关联一级评论
    user_id BIGINT NOT NULL,
    content TEXT,
    reply_to_uid BIGINT,           -- 回复某用户
    status TINYINT DEFAULT 0,
    created_at TIMESTAMP,
    INDEX idx_l1_time (l1_comment_id, created_at ASC)
);
```

#### 12.5 热度排序

**Wilson Score置信区间下限**（解决小样本高好评率问题）：

```
score = (p + z²/(2n) - z*√(p(1-p)/n + z²/(4n²))) / (1 + z²/n)

where:
  p = 点赞数 / (点赞数 + 点踩数)  -- 好评率
  n = 点赞数 + 点踩数            -- 总评分数
  z = 1.96 (95%置信度)
```

特点：n越小，置信区间越宽，下限越保守 → 确保新评论不会因偶然高好评率排到前面。

#### 12.6 高并发处理

- 一级评论列表缓存（Redis ZSET，按hot_score排序）
- 点赞数/回复数由计数系统维护
- 审核结果异步回调 → 更新评论状态 → 重建缓存
- 二级回复按时间正序，天然适合游标分页

#### 12.7 架构总览

```
客户端 → 评论服务 → [缓存层(热门评论)] → [评论DB(一级+二级)] → [计数系统(回复数)]
                    → [审核中心(异步)] → [消息队列(Kafka)]
                    → [搜索索引(ES)]
```

### 第13章 IM服务

#### 13.1 核心能力

可靠投递 + 消息有序性 + 会话管理 + 消息回执

#### 13.2 消息投递模型

| 特性 | 写扩散 | 读扩散 |
|------|--------|--------|
| 写入 | 向每个收件人各写一份 | 仅写入一次到发件箱 |
| 读取 | 每个收件人从自己的收件箱读 | 从所有参与者的发件箱聚合 |
| 存储 | N份（N个收件人） | 1份 |
| 适用 | 单聊、小群 | 大群 |

**决策**：单聊用写扩散（简单），大群用读扩散（省存储）

#### 13.3 消息有序性保证

**乱序原因**：网络延迟差异、服务端并行处理

**解决方案**：

```
客户端 → 为每条消息分配本地序号(monotonic)
服务端 → 同一会话消息路由到同一队列/分区（单点顺序处理）
        或使用会话锁保证并发写入顺序
客户端 → 根据本地序号+服务端消息ID排序+去重
```

#### 13.4 存储设计

```sql
-- 消息表
CREATE TABLE message (
    session_id BIGINT NOT NULL,
    msg_id BIGINT NOT NULL,         -- 服务端生成的有序ID
    sender_id BIGINT NOT NULL,
    msg_type TINYINT,               -- 文本/图片/语音/视频/系统
    content TEXT,
    created_at BIGINT NOT NULL,
    PRIMARY KEY (session_id, msg_id)
);

-- 已读表
CREATE TABLE read_cursor (
    user_id BIGINT NOT NULL,
    session_id BIGINT NOT NULL,
    last_read_msg_id BIGINT,        -- 已读到的最后一条消息ID
    PRIMARY KEY (user_id, session_id)
);
```

**热冷分离**：最近消息 → Redis，历史消息 → MySQL/HBase

#### 13.5 会话管理

- 单聊会话：双方共用一个session_id（如 `min(uid1,uid2)_max(uid1,uid2)`）
- 群聊会话：group_id与session_id一一对应
- 命令消息：加入群聊/移除群成员等系统通知

#### 13.6 消息回执

- 客户端收到新消息 → 异步上报已读确认（含最后seen_msg_id）
- 服务端更新read_cursor表
- 其他用户查询会话时返回未读数 = 最新msg_id - last_read_msg_id

#### 13.7 高并发架构

```
客户端 → 接入层(长连接) → 消息队列(Kafka，分级Topic) → IM核心服务 → 存储层 + pusher推送
```

**消息分级**：普通消息、优先消息、系统消息分别使用不同优先级的Topic

**直播间弹幕**：广播模式，不存储到个人收件箱，单次写入群发推送（牺牲可靠性换吞吐）

## 核心知识点速查

### 架构设计五大原则

1. **分层架构**：接入层→服务层→存储层，层层解耦
2. **水平扩展**：无状态服务可无限扩展，有状态服务用数据分片
3. **缓存为王**：本地缓存(L1)→分布式缓存(L2)→数据库(L3)，缓存层次越深性能越差
4. **异步解耦**：消息队列是分布式系统的"万能胶"
5. **读写分离**：CQRS模式，读写模型独立优化

### 高并发三板斧

| 斧 | 手段 | 技术选型 |
|----|------|---------|
| 缓存 | 本地(微秒)+分布式(毫秒) | Caffeine + Redis |
| 异步 | 削峰填谷 | Kafka |
| 分片 | 水平拆分 | 一致性哈希 + 从库升级扩容 |

### 高可用三板斧

| 斧 | 目标 | 实现 |

| 限流 | 自我保护 | 令牌桶(允许突发)/漏桶(恒速) |
| 降级 | 有损可用 > 不可用 | 服务依赖度降级/读写降级 |
